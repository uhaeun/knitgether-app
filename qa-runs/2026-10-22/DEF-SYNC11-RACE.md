# QA-SYNC11-RACE — 겹친 저장 요청이 모두 성공해 한쪽 메모가 덮어써짐

기준 커밋: `75a9882eb841044aba1067ddbc703a985a4515d2` / 실행일: 2026-10-22 KST.

분류: **제품 결함, 신규 발견 시나리오**. 기존 [#14](https://github.com/uhaeun/knitgether-app/issues/14)(낙관적 잠금)와 같은 영향 영역이지만, 기존 회귀 테스트의 순차 PATCH와 구분되는 동시 실행 결함이다. 이슈 #14 본문·종료 코멘트와 저장소 QA 카탈로그·테스트를 대조했으며, 이 겹침 시나리오의 기존 등록은 확인하지 못했다. 전체 GitHub 이슈의 중복 검색을 완료했다는 뜻은 아니다. GitHub 이슈 생성·기존 이슈 재개는 수행하지 않았다. 심각도 제안: **Major / 우선 수정 검토**. 최종 심각도와 릴리즈 판단은 제품 오너가 결정한다.

## 재현 및 근거

1. 전용 PostgreSQL과 현재 코드의 Nest 서버에서 새 계정·새 프로젝트 생성.
2. 같은 `updatedAt`을 `baseUpdatedAt`으로 갖는 전체 프로젝트 요청 본문 2개 준비. 메모만 A/B로 다르게 설정.
3. Python `threading.Barrier(2)`로 두 클라이언트 스레드의 전송 시작을 맞추고 두 PATCH를 동시에 전송.
4. 양쪽 응답 코드·응답 본문과 PostgreSQL `Project.memo`, `updatedAt` 직접 조회값 저장.

기대: 같은 기준 버전에서 성공은 1개, 후행 저장은 409 `PROJECT_CONFLICT`. 실제: 프록시 경유 10/10회, 프록시 없는 직접 연결 9/10회에서 `[200, 200]`. 직접 연결 나머지 1회는 `[200, 409]`였다. 전체 20회 중 19회 결함 재현. DB 최종 메모는 두 입력 중 하나여서 성공 응답을 받은 다른 입력이 남지 않는다. 기록은 [프록시 경유 원본](evidence/api-concurrency.json), [실행 로그](evidence/api-concurrency.log), [직접 연결 원본](evidence/api-concurrency-direct.json), [로그](evidence/api-concurrency-direct.log)에 있다. 이슈의 과거 원문은 [조회 당시 증거](evidence/github-issue14.json)에 보존했다.

**이 검사는 실제 서버·DB를 대상으로 한 API 통합 검사이며 iOS E2E가 아니다.** 클라이언트가 409를 처리하는지와 별개로 서버의 최후 방어선을 확인한다.

## 원인 분석과 수정 제안

`server/src/projects/projects.service.ts`의 `updateProject`는 트랜잭션 내부에서 프로젝트를 읽고(약 238행), `assertNoSaveConflict`로 메모리의 버전을 확인한 뒤(약 255행), `where: { id }`만으로 갱신한다(약 258행). 두 트랜잭션이 같은 이전 버전을 읽으면 양쪽 모두 비교를 통과할 수 있다. 트랜잭션으로 묶었다는 사실만으로 읽기와 버전 조건부 갱신이 원자적으로 수행되지는 않는다.

제안: 저장 기준 버전까지 UPDATE 조건에 포함하는 compare-and-set 또는 프로젝트 행 잠금 후 비교를 검토한다. 조건부 갱신 실패 시 409를 반환하고 자식 레코드 변경도 같은 트랜잭션에서 롤백해야 한다. 정수 버전 도입은 같은 밀리초의 연속 저장까지 구분할 대안이다. 재검증에는 동시 성공 수 1개, 거부된 요청의 부모·자식 무변경, 정상 재저장 성공을 포함한다.

제품 코드 수정은 수행하지 않았다.
