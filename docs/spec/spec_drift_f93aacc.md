## 2. 커밋 메시지에 없는 동작 변경

### 2.1 프로젝트 저장 충돌 감지 (SPEC-SYNC-11 변경)

코드에서 확인한 동작:

1. 클라는 저장 요청에 baseUpdatedAt(마지막으로 알고 있던 서버 updatedAt)을 실어 보낸다. 오프라인에서 만든 항목의 첫 업로드는 nil로 보내 충돌 검사를 건너뛴다. (RemoteProjectRepository 43, 55행)
2. 서버는 baseUpdatedAt이 있고 서버 updatedAt이 그보다 뒤면 409 PROJECT_CONFLICT와 함께 서버 최신 본을 details.latest로 돌려준다. baseUpdatedAt이 없으면 검사하지 않는다. (projects.service.ts 1425~1455행)
3. 클라는 409를 받으면 로컬 수정본을 롤백 스냅샷으로 되돌리고, 서버 본을 다시 받아 캐시에 반영한 뒤, 오류를 뷰모델로 던진다. (OfflineFirstProjectRepository isProjectConflict, refreshServerCopyAfterConflict)
4. 뷰모델은 목록을 다시 불러오고 "다른 기기에서 수정된 내용이 있어요. 서버에 저장된 최신 내용을 다시 불러왔으니 확인 후 다시 시도해 주세요."를 표시한다. (MyKnittingViewModel, ProjectWorkspaceViewModel)

문서와의 차이:

| 문서 | 현재 서술 | 코드 |
| --- | --- | --- |
| 02 SPEC-SYNC-11 | last-write-wins 한시 허용, 충돌 감지 도입 전제 | 감지 도입됨. 정책은 first-write-wins (서버 본 우선), 사용자 수정본은 폐기 |
| 02 SYNC-11 코드 일치 판정 | 조건부 일치 | 재판정 필요 |

| 기능정의서 정의 없음 15번 | 충돌 감지와 병합 안내 없음 | 감지와 안내 있음. 병합은 없음 |

판단이 필요한 지점 (하은):

- 정책 자체. 사용자가 방금 입력한 수정 내용이 화면에서 사라진다. 안내는 있으므로 RC-01(무이력 유실)은 아니지만, 01 치명도 1위(데이터 유실)와 맞닿아 있다. "되돌린 수정본을 어디에도 남기지 않는다"를 스펙으로 받아들일지, 아니면 임시 보관(예: 폼에 되살리기)을 요구할지.
- 적용 범위. 프로젝트 저장 경로에만 있고 카운터 개별 API, 작업 세션, 창고 항목에는 없다. 카운터는 여전히 last-write-wins다. 범위 차이를 스펙에 명시할지.
- baseUpdatedAt이 없는 요청은 검사를 건너뛴다. 구버전 클라나 직접 호출은 여전히 덮어쓴다. 서버 단독으로는 보장이 안 된다는 점을 07 문서에 남길지.

- 작업 세션: Postman으로 endedAt < startedAt, 24시간+1초 전송 시 400. 클라에서 4시간 넘게 방치 대신 시각 조작으로 절단과 메모 확인 (테스트 가능성: 상수 주입 여부 확인 필요)
- UUID 충돌: 기존 프로젝트 id로 POST /projects 시 409와 code 확인
- Keychain 삭제 실패: 재현 방법 없음. 코드 리뷰로만 확인. 미대조로 기록
