# Appium UI 스위트 구축 작업 기록

작성일 2026-08-27, 최종 갱신 2026-08-29. 이 문서는 실행 기록이고, 포트폴리오 본문은 별도로 작성한다.

기준 커밋 계보는 `a710227`(스위트 전체 구축) 이후이며, 앱 수정분은 Phase D 항목에 정리했다.

## 1. 만든 것

케이스 설계 시트의 UI-01부터 UI-78까지를 Appium POM 스위트로 옮겼다.

| 항목 | 수치 |
|---|---|
| 테스트 파일 | 18개 (TC 단위) |
| 테스트 함수 | 78개 (pytest 실행 항목 80건, 2026-09-19 정정) |
| 페이지 객체 | 12개 |
| 지원 모듈 | 6개 |
| 코드 | 약 3,700줄 |

시트 케이스 78건, 함수 78개, 실행 항목 80건이다(2026-09-19 정정). UI-04~06은 함수 하나를 파라미터 3종으로 돌리고, 두 건은 함수를 쪼갰다. UI-42는 시뮬레이터 동작(42a)과 실기기 실제 촬영(42b)으로 나눴고, UI-51은 검색 이탈 복귀(스텝3)와 탭 복귀(스텝2)로 나눴다.

기존 루트의 `def15_test.py`, `counter_increment_test.py`, `count_seed.py`는 새 구조로 흡수하고 삭제했다.

### 구조

```
qa/appium/
  conftest.py          드라이버 풀, 격리, 실패 스크린샷
  support/             simctl, seed, texts, server_api, netgate, paths
  pages/               base + 화면별 11개
  tests/               test_tc01 ~ test_tc16
qa/mutation/           결함 주입 도구 (injections.py, run_mutation.py)
```

### 설계 원칙 두 가지

이동은 반드시 도착까지 확인한다. 탭만 하고 넘어가면 애니메이션이 끝나기 전에 다음 요소를 찾게 되고, 엉뚱한 화면의 동명 요소를 눌러도 조용히 통과한다. 실제로 홈의 이어서 뜨기 카드가 DEF-17로 미동작이라 이 함정에 빠진 적이 있다.

오버레이는 좌표로 다룬다. 컨텍스트 메뉴, 액션 시트, 롱프레스, 시트 안 목록 행은 `element.click()`이 조용히 무시된다. 시트 안 목록 행은 라벨이 왼쪽 정렬이라 가운데가 히트 영역 밖인 경우도 있었다.

## 3. 검출력 검증

전건 통과는 제품이 정상이라는 뜻일 수도 있고 테스트가 아무것도 보지 않는다는 뜻일 수도 있다. 둘을 가르려고 두 층으로 확인했다.

### C-1 전제 제거 대조

`--empty-given` 스위치로 Given 주입을 끄고 전체를 돌렸다. 53건이 무너졌고 검출력 없는 테스트는 0건이었다. 통과한 20건은 전부 Given이 원래 빈 케이스이거나 계정을 API로 만드는 서버 케이스였다.

한계가 하나 있다. 이 스위치는 파일 시딩만 끄기 때문에 서버 케이스 14건에는 아무 신호도 주지 못한다.

### C-2 결함 주입 대조

앱과 서버에 대표 결함 6종을 하나씩 심고 지정한 케이스만 정확히 실패하는지 확인했다. 최종 결과는 6종 모두 검출, 과잉 결합 0건이다.

여기 도달하기까지 검증 도구가 세 번 잘못된 답을 냈다.

1. 결과 파서가 실패를 읽지 못했다. 실패 스크린샷 훅이 `FAILED`를 다른 줄로 밀어내서, 콘솔 파싱이 실패를 전부 놓쳤다. 첫 결과 6종 전부가 거짓 놓침이었다. junit XML 파싱으로 바꿔 해결했다.
2. 카운터 주입이 한 층만 건드렸다. 하한이 뷰의 버튼 비활성화와 ViewModel의 0 하한으로 이중 방어라 한쪽만 무너뜨리면 드러나지 않았다.
3. 서버가 재시작되지 않았다. 3000 포트를 쥔 것은 `node dist/src/main.js`인데 `pkill -f 'nest start'`로는 잡히지 않았고, 새 서버는 `EADDRINUSE`로 죽어 원본이 계속 응답했다. dist 재빌드도 빠져 있었다.

세 번 모두 그대로 믿었으면 스위트에 검출력이 없다는 정반대 결론이 나왔을 것이다. 실제 검출력 공백은 UI-64 한 건뿐이었고, Given을 파일 시딩으로 처리해서 저장 경로를 건너뛴 설계 잘못이었다.

### 부수적으로 확인된 제품 사실

카운터 하한은 뷰와 ViewModel 두 층에서 막혀 있다. 서버 계정 격리는 세 층이다. 목록 `where` 절, 자식 레코드 필터, `toResponse`의 소유자 확인이 각각 독립적으로 막는다. 단일 지점 결함으로는 뚫리지 않으며, 서버 로그의 `Skipped project` 기록이 3층이 실제로 작동한 증거다.

## 4. 결함 수정과 회귀 재판정

미수정 결함 4건을 고치고 회귀 케이스 6건을 정상 케이스로 승격했다.

| 결함 | 수정 위치 | 회귀 케이스 |
|---|---|---|
| DEF-17 lastWorkedAt 미저장 | `ProjectRepository.swift` 기본 `saveWorkSession` | UI-33, 35, 38 |
| DEF-18 보기 모드 드로잉 미표시 | `ProjectPatternFocusView.swift` 캔버스 상시 배치 | UI-49 |
| DEF-19 탭 복귀 페이지 초기화 | `PDFKitView.swift` 페이지 기억과 복원 | UI-51 스텝2 |
| SPEC-PROJ-01 이름 길이 미구현 | 클라 폼 30자 캡과 카운터, 서버 `@MinLength(1) @MaxLength(30)` | UI-17 |

수정마다 해당 회귀 케이스가 `XPASS(strict)`로 터지는 것을 확인한 뒤 마커를 제거했다. 결함이 살아있을 때는 조용하다가 고쳐지는 순간 스위트가 빨개지는 구조라, 수정이 실제로 먹었다는 자동 증거가 된다.

DEF-19는 설계 선택이 있었다. 앱은 `workspaceSheetPosition` 같은 UI 상태를 프로젝트 모델에 저장하므로 일관성만 보면 페이지도 거기 넣는 것이 맞지만, Prisma 스키마와 서버 DTO까지 건드려야 해서 UserDefaults에 프로젝트별로 저장하는 방식을 택했다. 나중에 옮길 수 있다.

## 5. 플레이키 해소

오버레이 메뉴 항목의 탭이 간헐적으로 유실됐다. SwiftUI 컨텍스트 메뉴는 요소 클릭이 먹지 않아 좌표로 눌러야 하는데, 그 좌표가 메뉴 애니메이션 중에 움직인다.

먼저 실패율을 실측했다. 메뉴를 쓰는 세 케이스(UI-40, UI-41, UI-61)를 5회 반복해 15회 시도한 결과 3회 실패로 20퍼센트다. 라운드별로는 3/3, 2/3, 2/3, 2/3, 3/3이었고 실패 케이스가 매번 달랐다. 특정 케이스가 약한 것이 아니라 오버레이 메뉴 조작 자체가 일정 확률로 유실된다는 뜻이었다.

원인은 두 가지였고 각각 따로 고쳤다.

### 오버레이 요소 바인딩 (`a784be7`)

컨텍스트 메뉴와 액션 시트 항목은 기본 바인딩에서 `element.click()`이 예외 없이 조용히 유실된다. 세션 생성 직후 `boundElementsByIndex`를 켜서 오버레이 항목이 클릭을 받도록 했다. 설정 적용이 거부되어도 스위트를 죽이지 않고 기존 좌표 탭 경로로 진행한다.

영향 경로는 롱프레스 메뉴를 쓰는 TC05, TC06, TC09, TC10a, TC10c, TC12다.

### 게이지 행 롱프레스 좌표 (`04095bd`)

UI-61만 따로 5회 돌려 기준선을 다시 쟀더니 3회 실패했다. 실패는 매번 같은 자리였다.

```
AssertionError: 롱프레스 메뉴에 '연결 해제'가 없음
```

제목 StaticText만 눌러서 컨텍스트 메뉴가 붙은 행 컨테이너에 닿지 않는 경우가 있었다. 제목 줄과 코수 줄의 영역을 합쳐 컨테이너 중심을 계산하고 그 좌표를 누르도록 바꿨다.

| 조건 | 결과 |
|---|---|
| 기준선 (제목 텍스트) | 3 failed / 2 passed |
| 수정본 (행 컨테이너 중심) | 5 passed / 0 failed |

### 앱 코드는 건드리지 않았다

당초 근본 해결책으로 04 문서의 테스트 가능성 예외를 적용해 메뉴 항목에 접근성 식별자를 붙이는 방안을 올렸고 오너 승인을 받았다. 조건은 식별자 추가만 담은 별도 커밋과 04 예외 항목 기록이었다.

**이 예외는 쓰지 않았다.** 원인 조사 결과 식별자 부재가 아니라 드라이버 바인딩 설정과 좌표 계산이 문제였기 때문이다. 자동화 코드 쪽 수정만으로 해소됐으므로 bf2b001 코드 동결 원칙이 유지된다.

### 남은 관찰

같은 조작을 쓰는 다른 케이스(UI-43 창고 연결, UI-44 수동 입력, UI-45 교체, UI-46 해제, UI-50 그리기 삭제)는 세 번의 최종 실행에서 전건 통과했다. UI-40과 UI-41은 수정 전후를 케이스 단위로 따로 재지 않았고, 근거는 전체 실행 3회 무실패다.

## 6. 시트에 반영할 관찰

구현하면서 시트가 관찰 후 기입으로 비워둔 칸이 여럿 채워졌다.

작업 화면에 들어가면 세션이 자동으로 시작된다. UI-33 스텝2의 작업 시작 클릭은 실제 동작과 다르다. 작업 시간 패널은 카운터 시트를 펼쳐야 나온다. 바늘 등록은 이름과 종류와 사이즈가 필수이고 도구 등록은 이름과 종류가 필수다. 도구는 스냅샷이 아니라 참조라 창고에서 수정하면 프로젝트 표시도 따라간다. 창고 도안은 삭제 입구가 스와이프뿐이다. 실과 바늘 상세는 모달 시트이고 작업 화면에는 탭바가 없다.

시뮬레이터에서 문서 스캐너가 실제로 열린다. `VNDocumentCameraViewController.isSupported`가 true를 돌려주기 때문에, 앱이 준비한 한글 폴백인 문서 스캔을 사용할 수 없어요는 이 환경에서 실행되지 않는 경로다. 실기기에서는 정상 동작할 것으로 보이므로 결함이 아니라 환경 의존 관찰로 기록한다.

## 7. 실행 방법

사전 준비는 다음과 같다.

```bash
docker compose -f server/docker-compose.yml up -d
cd server && npm run build && node dist/src/main.js
appium
xcrun simctl boot <UDID>
```

전체 실행은 세션이 오래 유지되면 WebDriverAgent가 버티지 못하므로 파일 단위 분할을 권한다.

```bash
cd qa/appium
for f in tests/test_tc*.py; do ./.venv/bin/python -m pytest "$f" -q; done
```

검출력 검증은 두 가지다.

```bash
./.venv/bin/python -m pytest tests/ --empty-given    # C-1 전제 제거 대조
python3 qa/mutation/run_mutation.py --all            # C-2 결함 주입 대조
```

## 8. 주의사항

시뮬레이터는 세션이 하나뿐이다. 두 개의 pytest를 동시에 돌리면 나중 세션이 앞 세션을 죽인다. 이 작업 중 두 번 겹쳐 돌려 멀쩡한 케이스가 거짓 실패로 나왔다.

시뮬레이터를 재부팅하면 Appium도 함께 재시작해야 한다. 그러지 않으면 죽은 WDA 연결을 붙들고 있어 모든 세션 생성이 실패한다.

`simctl privacy grant`는 대상 앱을 종료시킨다. 권한을 부여한 뒤 앱을 다시 띄워야 한다.

앱을 재설치하면 권한 부여가 초기화된다. 온보딩 케이스가 재설치를 하므로 세션을 새로 열 때마다 권한을 다시 준다.

macOS 파일 시스템은 파일 이름을 NFD로 저장한다. 한글 파일명을 테스트에 쓰면 파이썬 리터럴과 비교가 어긋난다.
