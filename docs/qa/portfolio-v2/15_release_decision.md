#### 6. 판정

허용 정책은 04의 9-1에 있다. 등급 기준은 Critical 0건, Major 2건 이하, Minor는 릴리즈 노트 기재로 허용이다. 등급과 무관하게 불허하는 계열 둘(RC-01 데이터 유실, RC-02 계정 간 노출)을 더했고, 잔존 건수는 닫힌 이슈 수가 아니라 실행으로 확인된 수로 센다.

**판정: Go (조건 해제 완료, 2026-09-15)**

9/15의 첫 판정은 조건부 Go였다. 해제 조건 3건을 같은 날 처리해 Go로 올렸다. 조건별 처리 내역과 남은 한계를 아래에 그대로 둔다. 판정이 바뀐 경위가 판정 자체보다 중요하다.

근거

등급 기준은 충족한다. 9/6 수정으로 Critical 잔존 0건, Major 잔존 0건, 열린 이슈 0건이 됐고 서버 e2e 143, API 계약 64, 앱 단위 348, Appium 81 passed로 세 층이 통과했다. 9/15 수정분을 포함한 7차 회귀(2026-09-19)에서도 147, 69, 351, Appium 82 passed로 실패 0건이다.

첫 판정이 Go가 아니었던 이유는 두 가지다. 둘 다 등급이 아니라 정책의 나머지 절반에 걸렸다.

첫째, RC-01 계열이 완전히 닫히지 않았다. POST 업서트 경로가 남아 있었다. 9/15에 두 단계로 닫았다.

- 사용자가 닿는 경로가 하나 더 있었다(`3d76cb7`). 첫 판정은 POST 업서트를 "오프라인 생성 재전송 전용이라 정상 앱은 밟지 않는다"고 적었는데 틀렸다. 오프라인 수정이 거부되면 프로젝트가 `conflict`로 보존되고(SYNC-10), 사용자가 충돌 배지를 보고 그것을 다시 고치면 그 저장이 POST로 나가면서 낙관적 잠금을 건너뛰었다. 충돌을 보고 고치려 드는 것은 자연스러운 행동인데 고치는 순간 보호가 꺼지는 셈이었다.
- 서버 쪽을 닫았다(`5582c3b`). 기존 id에 대한 POST를 409 `PROJECT_ALREADY_EXISTS`로 거부하고, 클라이언트가 서버 본을 조회해 기준값을 얻은 뒤 수정으로 다시 보내게 했다. 서버가 스스로 순서를 판정할 재료가 없어 검사 대신 경로를 바꿨다. 멱등성은 유지된다. 행은 하나이고 재전송의 목적은 수정 경로로 달성된다.

"정상 앱은 밟지 않는다"는 판단은 코드를 읽지 않고 설계 의도만으로 내린 것이었다. **예외를 승인하려면 그 예외가 정말 닿지 않는 자리인지를 실행으로 확인해야 한다.** 이번에는 확인하는 과정에서 결함이 나왔다. 예외를 그대로 승인했다면 결함은 남고 문서에는 안전하다고 적혀 있었을 것이다.

둘째, DEF-23을 실행으로 확인하지 못했다. 코드에 백그라운드 종료 처리가 있고 단위 케이스가 동작을 고정하지만 원래 보고된 증상인 과다 기록 자체는 이 사이클 내내 재현되지 않았다. 정책이 실행으로 확인된 수로 세기로 했으므로 이 건은 Critical 잔존 0건에 포함되지 않는다.

정책을 등급만으로 뒀다면 첫 판정은 Go였다. 계열 조건과 실행 확인 조건을 넣은 결과가 조건부 Go다. 두 조건을 넣은 이유는 04의 9-1에 적었다. DEF-10이 Major에서 Critical로 재분류된 전례가 있고, 등급은 판단이지만 사라지는 데이터의 양은 판단과 무관하다.

조건 2. DEF-23 재현 불가 확정

9/3의 65초 백그라운드는 iOS가 앱을 정지시켜 과다 기록 대신 세션 소멸이 났다. 9/15의 8초 백그라운드도 수정 전 빌드에서 세션 소멸이었다. 세 번째 시도가 결론을 뒤집었다. 대조군을 돌려 보니 수정 전 빌드는 백그라운드를 거치지 않아도 세션을 저장하지 않았다. 그러면 앞의 두 실패는 백그라운드 때문이 아니므로 아무것도 말해 주지 않는다. 오래된 빌드에 현재 케이스를 돌리면 결함이 아니라 세대 차이를 재게 된다. 대조군이 없었다면 "수정 전에서 실패했으니 검출력이 있다"고 잘못 결론 냈을 것이다.

현재 빌드의 동작은 두 케이스가 실행으로 보장한다. 짧은 구간 케이스의 검출력은 확인되지 않았다. 확인하려면 현재 빌드에서 백그라운드 처리만 되돌린 변형이 필요하고 13의 뮤테이션 6종과 같은 절차다.

RC-08 숫자는 개발 환경이라 스위트 반복 실행분이 섞여 있어 운영 수치로 읽으면 안 된다. 정리하는 주체가 아무도 없다는 사실은 숫자와 무관하게 확인된다. 역방향 1건은 고아화와 반대 방향이고 다운로드 실패로 이어지므로 원인을 따로 봐야 한다.

OBS-4-01은 세 항목 중 유일하게 그 자체로 배포를 막는 항목이었고 같은 날 닫았다. 잠긴 동안에는 맞는 비밀번호도 거부한다. 이 조건이 없으면 틀린 비밀번호만 세고 맞으면 통과시키는 구현도 "제한이 있다"로 통과한다. 공격자는 맞을 때까지 시도하므로 그런 제한은 아무것도 막지 못한다. 잠금 여부로 계정의 존재를 알 수 없게 두었다. 이 서버는 원래 존재 여부를 숨기고 있으므로(INVALID_CREDENTIALS 단일 코드) 잠금 코드가 있는 계정에서만 나오면 그 성질이 깨진다. IP 기준 제한은 넣지 않았다. 존재하지 않는 이메일에 대한 시도는 계정 카운터로 셀 수 없다. 계정 하나를 노린 대입은 막지만 여러 계정을 훑는 시도는 막지 못한다. 남은 공백으로 02에 기록했다.

OBS-4-02는 `npm audit fix` 뒤 서버 e2e 143건과 API 계약 65건으로 회귀를 확인했다(`package-lock.json` 변경). 남은 7건 중 multer를 포함한 4건은 NestJS 11에서 12로 올려야 해결되며 이 사이클의 범위가 아니다. 업로드 엔드포인트 3개에 직결된 DoS가 남는다는 사실을 배포 판단에 올린다.

남은 것

해제 조건 3건이 모두 처리돼 판정은 Go로 올라간다. 조건이 해제된 것과 아무것도 남지 않은 것은 다르다.

| 남은 것 | 성격 |
| --- | --- |
| IP 기준 로그인 제한 | 계정 기준만 넣었다. 여러 계정을 훑는 시도는 막지 못한다 |
| RC-08 파일 고아화 | 정리 주체가 없다는 사실은 확인됐고 자동 정리는 넣지 않았다 |
| multer DoS | NestJS 12 메이저 업그레이드가 필요해 이 사이클 범위 밖이다 |
| DEF-23 케이스 검출력 | 실패하는 것을 본 적이 없어 확인되지 않았다 |

이 항목들은 허용 정책의 어느 조건에도 걸리지 않는다. Critical도 Major도 아니고 RC-01, RC-02 계열도 아니다. 정책대로라면 Go다. 그러나 이것들이 릴리즈 노트에 적히지 않으면 판정은 모르는 것을 모른 채 통과시킨 것이 된다.

릴리즈 노트 기재 사항

| 항목 | 기재 내용 |
| --- | --- |
| DEF-25 | 창고 삭제 시 연결 프로젝트 고지는 서버 연결 상태에서만 표시된다. 오프라인에서는 고지 없이 삭제된다 |
| 단위 설정 제거 | 기존 사용자의 저장값(US, Imperial)은 서버에 남지만 앱은 cm로 동작한다 |
| 저장 충돌 | 다른 기기가 먼저 수정한 경우 저장이 거부된다. 입력한 내용은 화면에 남고 다시 저장하면 이 기기 내용으로 저장된다 |
| 로그인 제한 | 연속 5회 실패 시 15분 잠금. 계정 기준이며 여러 계정을 훑는 시도는 막지 못한다 |
| 서버 저장소 | 연결 해제된 도안 파일이 서버에 남는다. 자동 정리 없음 |
| 알려진 취약점 | 업로드 엔드포인트의 multer DoS가 남아 있다. NestJS 12 업그레이드 전까지 유지 |

판정을 막은 것은 네 번 바뀌었다. 9/1 초안이 판정을 못 내린 이유는 허용 정책의 부재였고, 정책을 세운 뒤 막은 것은 잔존 결함이었고, 그것을 닫으니 남은 것은 배포 전 조치였고, 그것마저 닫으니 남은 것은 적어 두어야 할 한계다. 네 번 모두 "테스트가 끝났는가"와 다른 질문이었다.

#### 7. 이 판정이 포트폴리오에서 뜻하는 것

실제 배포가 없는 프로젝트에서 릴리즈 판정을 쓰는 이유는 하나다. "테스트가 끝났다"와 "내보내도 된다"를 구분해서 말할 수 있는가. 이것이 릴리즈 게이트 원칙(09, 13의 6절)과 이어진다. 판정이 No-Go나 조건부 Go여도 손해가 아니다. **근거가 문서로 추적되는지가 평가 대상이다.**
