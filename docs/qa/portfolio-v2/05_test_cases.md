# 05_테스트케이스

> 2026-09-18 재작성. 케이스 ID, 절차, 판정 기준, 실행 결과는 8월 원본(`docs/qa/portfolio/05`, 1차 설계 8/3~8/4, 2차 설계 8/10)과 06, 11의 판정을 그대로 옮겼다. 바뀐 것은 배치다. 22건 전문을 옮기지 않고 기법별 대표 케이스로 설계 의도를 보인다. 케이스별 절차와 SQL 전문은 원본이 정본이다.

#### 이 문서의 위치

ISTQB 4.0 테스트 프로세스의 설계 활동 산출물이다. 설계 활동은 분석에서 나온 테스트 조건을 테스트 케이스로 구체화하고, 어떤 기법으로 커버리지 아이템을 뽑았는지를 정하는 일이다. 이 문서의 테스트 조건은 02의 SPEC이고, 우선순위는 03의 RC 등급을 따른다. 29119-3 기준으로는 테스트 케이스 명세에 해당한다. 원본은 케이스마다 절차를 같은 블록에 적었으므로 테스트 절차 명세도 겸한다. SPEC과 케이스의 추적성 매트릭스(RTM)는 09가, 탐색적 테스팅의 차터는 16이 맡는다.

2차 사이클 자동화 케이스(UI-01~78, API-01~25)의 설계 정본은 구글 시트다. 이 문서는 1차 케이스 22건과 2차 수동 트랙 15건을 다루고, 자동화 케이스는 09에서 본다.

#### 3. 공통 판정 규칙

모든 케이스는 PASS와 FAIL 외에 두 판정을 더 쓴다. 이 두 칸이 있어서 조건이 성립하지 않은 실행을 PASS로 세지 않는다.

| 판정 | 쓰는 경우 | 예 |
| --- | --- | --- |
| RETRY_REQUIRED | 검증하려는 조건이 실행에서 성립했음을 증명하지 못했다 | TC-SYNC08-01에서 기기2의 PATCH 성공을 확인하지 못하면 충돌이 일어났다는 증거가 없다 |
| 전제 미성립 | 사전 상태가 설계와 다르다. 별도 결함 여부를 따로 검토한다 | TC-SYNC09-01에서 오프라인 생성 직후 localOnly로 저장되지 않은 경우 |

공통 환경 조건은 원본 "TC 상세" 머리에 있다. 요지는 셋이다. API만 중단할 때는 NestJS 프로세스를 종료하고 PostgreSQL 컨테이너는 유지한다. 로컬 상태는 앱 데이터 컨테이너의 `projects.json`에서 `syncStatus` rawValue(`Local Only`, `Pending Upload`, `Synced`, `Pending Delete`)로 판정한다. 서버 상태는 psql로 판정하고, 화면은 보조 증적이다.

#### 4. 경계값 분석

TC-CNT01-01이 대표다. 02의 CNT-01은 하한 0을 약속하고 상한은 약속하지 않는다. 그래서 하한은 양쪽에서 두드리고, 상한은 "없음"을 확인하는 값을 골랐다.

| 입력 | 기대 | 설계 의도 |
| --- | --- | --- |
| 0에서 감소 1회 | 0 유지 | 하한 경계 |
| 0에서 감소 10회 연속 | 0 유지 | 연타로 경계를 넘는지 |
| 직접 입력 `-1` (키 입력이 막히면 붙여넣기) | 거부 또는 0 보정 | 하한 바로 아래 값 |
| 0에서 증가 1회 | 1 | 1회 입력이 정확히 +1인지 |
| 0에서 증가 10회 | 10 | 입력 유실이나 중복 반영 |
| 9999에서 증가 1회 | 10000 | 네 자리 고정 상한이 숨어 있지 않은지 |
| 재진입 후 화면과 psql `currentRow` | 10000 일치 | 표시값과 저장값 정합성 |

첫 실행은 UX 개편 빌드에서 FAIL이었다. 카운터 0에서 감소 버튼이 값을 1로 올렸다(DEF-15). 겹침 구조를 걷어낸 `34f3c00` 이후 재실행에서 PASS다. 이 경계는 2차에서 UI-54(시작 전에서 감소)와 UI-55(직접 입력 10000, 0, -5)로 자동화 회귀에 옮겨졌다.

2차 자동화 케이스에도 같은 방식의 경계가 있다. 판정 결과는 09에 있다.

| 케이스 | 규칙 | 고른 값 |
| --- | --- | --- |
| UI-05, 06, 07과 API-02 | 비밀번호 8~256자 (서버 규칙 코드 확인) | 빈칸, 7자, 257자는 거부. API-02는 8자와 256자의 201도 확인 |
| UI-17 | 프로젝트 이름 1~30자 (SPEC-PROJ-01) | 1/30, 30/30, 31자 입력 뒤 30자 |
| UI-25 | 목표일 D-day 표시 | D+1, D-Day, D-1 |

원본은 동등 분할을 별도 기법 태그로 쓰지 않았다. UI-04~06의 무효 입력 묶음이 분할에 가깝지만 원본 태그는 에러 기대와 경계값이라 여기서도 그대로 둔다.

#### 5. 상태 전이

동기화 영역은 04가 정한 syncStatus 4상태 전이를 따라 설계했다. TC-SYNC01-01, TC-SYNC06-01, TC-SYNC09-01, TC-SYNC10-01을 전이 표로 합치면 다음과 같다. 금지 열은 각 케이스의 FAIL 조건이다.

| 현재 상태 | 이벤트 | 기대 | 금지 | 케이스와 판정 |
| --- | --- | --- | --- | --- |
| 없음 | API 단절 중 생성 | Local Only, 목록에 1건 | 생성 실패, 로컬 미저장 | SYNC01, PASS |
| Local Only | API 단절 상태로 앱 재실행 | 같은 ID와 입력값 유지 | 소멸 | SYNC01, PASS |
| Local Only | API 복구, 목록 조회 전 | 변화 없음 | 자동 POST (SYNC-07 위반) | SYNC01, PASS |
| Local Only | 목록 조회 | POST 1회 성공 후 Synced | 상태 미전환, 중복 POST, 잘못된 owner | SYNC01, PASS |
| Synced | API 단절 중 삭제 | 화면에서 사라지고 삭제 대기(tombstone) 보존 | 화면 잔존, tombstone 소실 | SYNC06, PASS |
| 삭제 대기 | 목록 조회 | DELETE 1회 후 로컬 제거, 재조회 시 추가 DELETE 없음 | 조회 전 DELETE, 중복 DELETE | SYNC06, PASS |
| Local Only | 서버가 POST를 400으로 거부 | 로컬 유지, 실패 안내, 재시도 가능 | 삭제, 접근 불가, 무통보 | SYNC09, FAIL (DEF-03) |
| Pending Upload | 서버가 PATCH를 400으로 거부 | 수정본 유지, 실패 안내 | 안내 없이 서버본으로 복원 | SYNC10, FAIL (DEF-04) |

정상 전이는 전부 통과했고 거부 이벤트에서 나가는 전이는 전부 실패했다. 06은 두 실패를 DEF-12와 함께 "서버 거부 시 무통보 폐기" 계열로 묶었다. 트리거를 "API 복구"가 아니라 "목록 조회"로 고정한 것은 SYNC-07이 재시도 시점을 조회로 정했기 때문이다. 복구와 조회를 한 단계로 합치면 자동 업로드가 일어나도 구분하지 못한다.

#### 6. 결정 테이블

TC-LINK01-01은 원본에서 의사결정 테이블로 태그했다. 조건은 확인창 표시, 확인창의 드로잉 삭제 안내, 사용자 선택 셋이다. 기대 결과 1~8을 규칙으로 옮기면 다음과 같다.

| 규칙 | 확인창 | 삭제 안내 | 선택 | 기대 결과 | 판정 |
| --- | --- | --- | --- | --- | --- |
| R1 | 없음 | 해당 없음 | 해당 없음 | 즉시 교체 | FAIL (LINK-01) |
| R2 | 있음 | 없음 | 해당 없음 | 데이터 소실 안내 미흡 | FAIL |
| R3 | 있음 | 있음 | 취소 | D1, 드로잉, DB의 `drawingStorageKey` 전부 유지 | PASS. 하나라도 바뀌면 취소 원자성 FAIL |
| R4 | 있음 | 있음 | 교체 | D2로 전환, D1 드로잉 미표시, 새 복사본 드로잉 키 비어 있음, 재실행 후에도 유지 | PASS. 드로잉이 계승되거나 재등장하면 FAIL |

사전 조건에서 D1 드로잉의 저장과 재조회를 먼저 증명하게 했다. 지울 드로잉이 실제로 있었는지 모르면 R3과 R4 모두 판정할 수 없어서다(RETRY_REQUIRED).

실행 결과는 R1과 R2에 동시에 해당했다. 확인창도 경고도 없이 교체되고 기존 드로잉이 삭제됐다(DEF-10). 네 진입점 모두에 확인창을 넣은 `8f1a4ad` 이후 2차에서 UI-45와 TC-REG-01(네 진입점 전수)이 회귀를 맡는다.

#### 7. 에러 기대 (오류 주입)

04는 에러 추정과 에러 기대를 한 묶음으로 둔다. ISTQB 4.0의 오류 추정은 경험 기반 기법이고, 원본의 에러 기대는 서버 거부, 네트워크 단절, 조회 실패를 의도적으로 주입하고 그때의 기대 동작을 명시한 케이스다. 주입 방식이 판정을 좌우하므로 설계에서 주입 방법까지 정했다.

TC-SYNC09-01과 TC-SYNC10-01이 대표다.

- 대상 상태를 먼저 만든다. API만 중단한 채 생성하거나 수정해서 Local Only 또는 Pending Upload를 `projects.json`에서 확인한다.
- 거부는 서버가 실제로 거부한 것이어야 한다. TC-SYNC10-01은 정상 PATCH를 서버에 전달한 뒤 응답 코드만 400으로 바꾸는 방식을 금지했다. 서버 DB가 바뀌면 거부 시나리오가 성립하지 않은 것이므로 RETRY_REQUIRED다. TC-SYNC09-01 실행에서는 허용되지 않은 필드 `createdAt`을 주입해 서버가 실제 400을 반환하게 했다. 응답 코드를 변조하지 않았다.
- TC-SYNC09-01은 FAIL을 세 갈래로 나눴다. 로컬에서 삭제되면 데이터 유실, 로컬에는 있으나 목록에서 접근할 수 없으면 숨김, 안내가 없으면 무통보 실패다. 어느 갈래로 실패했는지가 수정 범위를 정한다.

DEF-03은 첫째 갈래였다. 화면과 로컬 파일 모두에서 사라졌고 안내도 없었다. DEF-04는 수정본이 안내 없이 서버본으로 돌아가고 상태가 Synced로 바뀌어 TC-SYNC10-01의 기대 결과 2, 4, 5를 위반했다.

#### 8. 거짓 PASS를 막는 설계

8/4 상세 검토에서 여러 케이스를 두 구간 이상으로 쪼갰다. 캐시나 다른 경로가 실패를 가려 통과처럼 보이는 경우를 분리하기 위해서다.

| 케이스 | 가릴 수 있는 것 | 설계 |
| --- | --- | --- |
| TC-CNT03-01 | 기존 로컬 캐시가 원격 조회 실패를 가린다 | A warm cache(기존 시뮬레이터)와 B cold cache(새로 설치한 시뮬레이터)로 분리 |
| TC-LINK03-01 | 스킬 캐시가 조회 실패를 정상 빈 상태처럼 보이게 한다 | A 삭제 스킬 제외, B 정상 빈 상태, C 조회 실패(500 주입)를 별도 구간으로 판정 |
| TC-SYNC05-01 | 수동 실행에서는 PATCH 실패 시 GET이 실행되지 않아 병합 로직을 거치지 않는다 | 실행 계층을 Mock 저장소 단위 테스트로 옮기고 fetch 호출과 병합 실행을 먼저 단언 |
| TC-PAT02-01 | 서버 재다운로드나 외부 원본이 로컬 복사 누락을 가린다 | A 내부 복사(경로와 SHA-256), B 콜드 런치, C 원본 삭제와 API 중단을 동시에 건 재열람 |

TC-CNT03-01의 A 구간은 실행에서 설계 의도대로 작동했다. 서버는 목록 전체에 500을 반환했고, 앱은 오류 안내 없이 이전 캐시만 보여 줬다. 서버의 P2 카운터를 99로 바꿔도 화면이 22를 유지해 캐시가 가리고 있음을 증명했다(DEF-08). 02는 이 결함을 클라이언트 디코딩 실패로 추정했지만 실제 결함 층은 서버였다.

#### 9. 시나리오와 회귀

시나리오와 회귀는 원본 태그이지만 ISTQB 4.0의 테스트 기법 목록에 대응하는 항목이 없다. 4.0은 유스케이스 테스팅을 블랙박스 기법 목록에서 뺐고, 회귀 테스팅은 기법이 아니라 변경 관련 테스트 유형이다. 그래서 억지로 매핑하지 않고 설계 의도만 적는다.

TC-CUJ1-01은 두 경로의 결과가 같은지를 본다. 비교 대상은 프로젝트명, 도안, 실, 바늘, 도구의 연결 여부와 표시값, 대표 실 지정, 창고 원본의 생성 여부와 개수다. 객체 ID, ownerId, 생성과 수정 시각은 비교에서 뺐다. 경로마다 다를 수밖에 없는 시스템 관리값을 넣으면 매번 FAIL이 나기 때문이다. 실행에서는 psql 3종 대조로 전 항목이 동등해 PASS였다.

TC-PAT02-01은 개발 중 발견하고 수정한 외부 파일 참조 문제의 재발을 본다. 8절의 A, B, C 구간으로 PASS였고 원본과 복사본의 해시가 일치했다.

원본 고유 태그 가운데 비교 테스트(TC-LINK05-01), 상태 분리(TC-CNT03-01, TC-LINK03-01), 계정 격리(TC-AUTH04-01, TC-AUTH05-01)도 표준 기법명으로 바꾸지 않았다.
