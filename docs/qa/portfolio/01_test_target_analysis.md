# 01_테스트 대상 분석

> 2026-09-02 재작성. 치명도 순위, CUJ, 항목별 연결 규칙은 8월 원본(`docs/qa/portfolio/01`)의 판정을 그대로 옮겼다. 바뀐 것은 배치다. 치명도를 검증 질문 형식으로 다시 쓰고 테스트 베이시스 절을 앞에 붙였다.

#### 이 문서의 위치

ISTQB 4.0 테스트 프로세스의 분석 활동 산출물이다. 분석 활동은 테스트 베이시스를 읽고 테스트 조건을 뽑아 우선순위를 매기는 일이다. 이 문서는 그중 "무엇을 근거로 봤나"(테스트 베이시스)와 "무엇이 깨지면 가장 나쁜가"(우선순위의 영향도 축)를 맡는다. 개별 테스트 조건은 02가 SPEC 48건으로 정의하고, 영향도와 발생가능성을 합친 등급은 03이 매긴다.

#### 1. 테스트 베이시스

분석의 근거로 읽은 것은 셋이다.

| 근거 | 무엇을 얻었나 | 신뢰도 |
| --- | --- | --- |
| QA 인수인계 문서 (커밋 `bf2b001` 시점) | 아키텍처, 데이터 흐름, API 목록, known issue | 개발 완료 시점의 시스템 안내서. 동작의 1차 근거 |
| 코드와 스키마 실측 (`schema.prisma`, Repository 계층) | 항목별 연결 방식, FK 제약조건 유무, 옵셔널과 필수의 불일치 | 실측이라 가장 정확하나 코드가 곧 정답은 아니다 |
| 사전 기획서 (`docs/spec/원본_v2.2.md`) | 제품 의도, 화면 구성 | 구현 중 데이터 구조가 바뀌어 현재 코드와 괴리. 의도 참고용 |

세 근거가 어긋날 때 코드를 정답으로 삼지 않았다. 기획 의도와 대조해 불일치로 기록하고 02에서 항목마다 판정했다.

#### 2. 누구의 어떤 문제를 푸는가

타겟 사용자는 뜨개질 초보자다. 이 앱의 존재 이유는 도안과 단수 카운터를 한 화면에서 보는 것이다. 물리 카운터로는 불가능한 조합이다. 초보자는 도안을 읽다가 모르는 기술이 나오면 검색으로 이탈하고, 돌아왔을 때 몇 단까지 떴는지를 잃는다. 앱은 이 맥락 손실을 없앤다.

이 문서에서 쓰는 뜨개 용어는 넷뿐이다. 도안은 설계도 문서(PDF, 이미지)이고 앱에서는 파일 자산이다. 단수는 완성한 줄 수이고 앱에서는 버튼으로 누적하는 카운트 값이다. 게이지는 밀도 측정 기록이고 앱에서는 프로젝트에 연결되는 측정 데이터다. 창고는 보유한 실, 바늘, 도구, 스킬의 목록이고 앱에서는 자산 마스터 데이터다.

핵심 구조는 뜨개 프로젝트를 가운데 두고 창고와 라이브러리를 프로젝트에 연결하는 것이다. 그래서 이 제품의 가치는 개별 기능이 아니라 **연결의 정합성**에 있다. 프로젝트를 열었을 때 연결해 둔 도안, 도구, 기록이 그대로 있어야 한다.

항목별로 연결 방식이 다르다.

| 항목 | 연결 방식 | 무결성을 누가 보장하나 |
| --- | --- | --- |
| 도안 | 프로젝트당 1개 복사본 (`ProjectPatternCopy`, projectId unique) | DB |
| 실 | 사용 기록 다중 + 연결 시점 스냅샷 | DB + 앱 |
| 바늘 | 참조 + 스냅샷. FK 제약조건 부재 | 앱 |
| 도구 | N:M 공유 연결 (`ProjectToolLink`, projectId와 toolId unique) | DB |
| 스킬 | ID 배열 참조. FK 제약조건 부재 | 앱 |

바늘과 스킬은 참조 무결성이 애플리케이션 책임이다. 연결 방식이 다르면 맞는 동작의 기준도 다르므로 검증은 항목별 규칙을 따른다(5절).

#### 3. 제품 책임 경계

| 구분 | 내용 | 테스트 관점 |
| --- | --- | --- |
| 앱이 푸는 것 | 도안, 카운터, 재료를 한 작업 공간에서 관리 | 기능 검증 대상 |
| 앱이 보장할 것 | 누른 만큼 정확히 센다. 입력한 만큼 저장되고, 저장된 것은 유실되지 않는다 | 최우선 검증 대상 |
| 앱이 못 푸는 것 | 사용자가 세는 것 자체를 까먹는 문제 (누르지 않은 입력) | 테스트 범위 밖 |

이 경계가 판정 기준이다. 카운트가 실제 뜬 단수와 다를 때, 입력 누락이면 결함이 아니고 입력이 있었는데 반영되지 않았거나 보존되지 않았으면 결함이다.

#### 4. 무엇이 깨지면 가장 나쁜가

치명도 순위다. 03 리스크맵의 영향도 축이 이 순위를 그대로 쓴다. 각 순위를 QA가 실제로 던진 질문으로 적고, 어디가 가장 깨지기 쉬운 자리인지를 같이 적었다.

| 순위 | 검증 질문 | 왜 이 순위인가 | 가장 깨지기 쉬운 자리 | 03 대응 |
| --- | --- | --- | --- | --- |
| 1 | 입력한 만큼 저장되고 저장된 것은 유실되지 않는가. 동기화가 덮어쓰거나 조용히 버리지 않는가 | 수십 시간 쌓은 작업 기록이 사라지면 복구 불가, 이탈 직결. 로컬 저장 실패만이 아니라 서버 동기화의 덮어쓰기와 유실을 포함한다 | 서버의 하드 삭제, 클라이언트의 무통보 폐기, 다중 기기 오프라인 복귀 | RC-01 (P1), RC-06 (P3) |
| 2 | 프로젝트를 열었을 때 연결해 둔 도안, 재료, 기록이 그대로 있는가. 창고 원본을 고치거나 지웠을 때 프로젝트 쪽이 어떻게 되는가 | 데이터는 있는데 작업 공간이 무너진다. 핵심 구조가 연결이라 이 제품에서는 준유실급 | FK 제약조건 부재 참조(바늘, 스킬). DB가 무결성을 보장하지 않는다 | RC-03, RC-05 (P2), RC-07 (P3) |
| 3 | 계정을 바꿨을 때 남의 데이터가 보이거나 내 데이터가 남의 계정으로 가지 않는가 | 기능 결함을 넘어 개인정보 문제. 실서비스면 단독 릴리즈 차단 사유 | 계정을 구분하지 않는 단일 캐시 파일 | RC-02 (P1) |
| 4 | 누른 만큼 정확히 세는가 | 3절 보장의 직접 위반 | 카운터 하한 0 경계 (CNT-01) | 03 클래스 없음. 05 표준 TC |
| 5 | 파일이 있는데 도안이 안 열리는 일이 없는가 | 작업 자체가 중단된다 | 복사본 로컬 캐시 | 03 클래스 없음. CUJ 회귀 수준 |

이 순위는 DBMS QA 관점의 연장이다. 데이터 유실과 정합성을 최상위에 두는 것, FK 제약조건이 부재한 참조를 최우선 의심 지점으로 잡는 것은 DB 레벨 무결성 검증을 앱 레이어에 적용한 결과다.

#### 5. 핵심 사용자 흐름 (CUJ)

초보 사용자가 가치를 얻기까지의 최단 경로다. 이 흐름이 끊기면 개별 기능이 멀쩡해도 제품이 실패한 것으로 본다. 2026-09-01 재분류로 3개다.

**CUJ-1. 첫 사용에서 첫 작업까지** (신규 사용자, 2경로)

- 1a 프로젝트 우선: 회원가입과 로그인 → 온보딩 → 프로젝트 생성 → 프로젝트 안에서 도안, 실, 바늘, 도구 추가 → 작업 화면에서 도안과 카운터 확인 → 카운트 증가 → 앱 종료
- 1b 창고 우선: 회원가입과 로그인 → 온보딩 → 창고에 도안, 실, 바늘, 도구 먼저 등록 → 프로젝트 생성 → 등록해 둔 항목을 프로젝트에 연결 → 작업 화면 확인 → 카운트 증가 → 앱 종료
- 경로 동등성 판정: 1a와 1b 완료 후 프로젝트 상태(연결된 항목 목록, 창고 원본, 서버 DB 레코드)가 같아야 한다. 어느 경로로 만들었는지가 이후 동작에 영향을 주면 결함이다

**CUJ-2. 재방문에서 작업 재개까지** (핵심 보장 검증)

앱 재실행 → 로그인 상태 유지 확인 → 기존 프로젝트 진입 → 마지막 단수, 도안, 연결된 재료가 그대로인지 확인 → 이어서 카운트

**CUJ-3. 모르는 기술 만남** (존재 이유 검증)

작업 중 행안내의 스킬 태그에서 모르는 기술 발견 → 스킬 상세 학습 → 닫기 또는 뒤로가기로 작업 화면 복귀 → 카운트와 도안 페이지 번호 보존 확인. 확대율과 페이지 내 스크롤 위치는 보존 대상에서 뺀다. 직접 사전, 스킬 검색 경로는 같은 맥락 보존 기준을 개별 TC로 검증한다.

각 CUJ는 05에서 시나리오 테스트로 설계한다. CUJ 도중 실패는 같은 기능의 단위 결함보다 심각도를 한 단계 높인다. 단 상향은 결과가 데이터 유실, 계정 간 노출, 앱 사용 불가일 때만 적용한다(04 개정).

#### 6. 연결의 생애주기 (CUJ 밖, 치명도 2위 심층 검증)

1차 설계에서는 이것을 CUJ-3으로 잡았다. 실행하면서 사용자 여정이 아님을 확인해 2026-09-01에 분리했다. 사용자가 한 자리에서 가치를 얻는 경로가 아니라 원본을 수정하고 삭제하는 과정을 따라가며 정합성을 보는 검증 시나리오이고, 사용자 눈에 보이는 연결 보존은 CUJ-2가 이미 덮는다. 케이스 ID `TC-CUJ3-01`은 실행 판정과 결함(DEF-21) 추적이 걸려 있어 그대로 둔다. 분류가 바뀐 것이지 케이스가 바뀐 것이 아니다.

항목별 규칙이다.

| 항목 | 확인 절차 | 맞는 동작 |
| --- | --- | --- |
| 도구 (다중 공유) | A와 B에 모두 연결 → A에 같은 도구 재연결 → A에서 해제 → 창고에서 도구 삭제 | 양쪽 표시, 중복 없음, B와 원본 유지, 삭제 시 A와 B 모두 해제 |
| 도안 (복사본) | 창고 도안을 프로젝트에 등록 → 창고 원본 수정과 삭제 → 도안이 있는 프로젝트에 다른 도안 등록 | 프로젝트 도안(제목, 파일, 메모 드로잉) 불변. 재등록은 교체인지 거부인지를 02가 정한다 |
| 실 (스냅샷) | A의 대표 실 지정 후 사용 기록 여러 개 → 같은 실을 B의 대표 실로 → 창고에서 삭제 | 각 프로젝트 화면과 사용 기록에 실 정보가 스냅샷으로 남는다 |
| 바늘 (FK 부재, 스냅샷) | 프로젝트에 바늘 지정 → 창고에서 삭제 | 스냅샷 유지, 깨진 화면이나 오류 없음 |
| 스킬 (ID 배열, FK 부재) | 스킬 여러 개 연결 → 하나 삭제 | 사라지는지, 빈 항목이 뜨는지, 오류가 나는지를 관찰해 02로 확정 |

스냅샷 항목(실, 바늘) 공통 규칙이 하나 더 있다. 원본이 창고에 살아 있는 상태에서 원본을 수정해도 기존 프로젝트는 연결 시점 스냅샷을 유지한다. 수정 이후 새로 연결한 프로젝트에만 변경된 값이 저장된다. 원본 삭제 후에도 각 프로젝트는 자신의 스냅샷을 계속 표시하며, 같은 프로젝트의 모든 화면은 같은 값을 보여야 한다.

#### 7. 어디를 넓게 보고 어디를 깊게 볼 것인가

실행은 CUJ 완주를 우선한다(넓이). 릴리즈 판정의 기본선은 사용자 흐름이 끊기지 않는 것이다. 그 위에 치명도 1~3위 클래스(데이터 유실, 연결 정합성, 계정 간 노출)는 정상 흐름에서 드러나지 않으므로 네트워크 단절, 동시 수정, 계정 전환, 전송 중단 같은 악조건 시나리오로 따로 심층 검증한다(깊이). 배분의 상세는 04에 있다.

#### 8. 성공 기준

정성 목표("초보자가 뜨개질에 잘 접근하게 한다")는 그대로 검증할 수 없다. 테스트 가능한 대리 기준으로 바꾼다. CUJ 3개가 끊김 없이 완주되는가.
