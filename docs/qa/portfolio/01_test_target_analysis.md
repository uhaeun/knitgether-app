# 01_테스트 대상 분석

> 원본: Notion `01_테스트 대상 분석` (최종 갱신 2026-08-03) / repo 이관 2026-08-27

#### 용어

이 문서에서 쓰는 뜨개 용어는 4개뿐이다.

- 도안: 뜨개 작업의 설계도 문서(PDF/이미지). 앱에서는 파일 자산이다.
- 단수: 뜨개에서 완성한 줄 수. 앱에서는 사용자가 버튼으로 누적하는 카운트 값이다.
- 게이지: 뜨개 밀도 측정 기록. 앱에서는 프로젝트에 연결되는 측정 데이터다.
- 창고: 사용자가 보유한 실, 바늘, 도구, 스킬의 목록. 앱에서는 자산 마스터 데이터다.

#### 누구의 어떤 문제를 푸는가

타겟 사용자는 뜨개질 초보자다.

이 앱의 존재 이유는 도안과 단수카운터를 한 화면에서 보는 것이다. 물리 카운터로는 불가능한 조합이다. 초보자는 도안을 읽다가 모르는 기술이 나오면 검색으로 이탈하고, 돌아왔을 때 몇 단까지 떴는지를 잃는다. 앱은 이 맥락 손실을 없앤다.

핵심 구조는 뜨개 프로젝트를 중심에 두고 창고(실, 바늘, 도구, 스킬)와 라이브러리를 프로젝트에 연결하는 것이다. 따라서 이 제품의 가치는 개별 기능이 아니라 **연결의 정합성**에 있다. 프로젝트를 열었을 때 연결해둔 도안, 도구, 기록이 그대로 있어야 한다.

항목별로 연결 방식이 다르다. 도안은 프로젝트당 1개의 복사본으로 들어가고, 실과 바늘은 참조와 함께 연결 시점의 정보를 스냅샷으로 저장하며, 도구는 여러 프로젝트가 공유하는 연결이고, 스킬은 ID 배열로 참조한다. 바늘과 스킬의 참조에는 FK 제약조건이 부재해 참조 무결성 보장이 애플리케이션 책임으로 넘어가 있다. 연결 방식이 다르면 맞는 동작의 기준도 다르므로, 검증은 항목별 규칙을 따른다.

#### 제품 책임 경계

| 구분 | 내용 | 테스트 관점 |
| --- | --- | --- |
| 앱이 푸는 것 | 도안, 카운터, 재료를 한 작업 공간에서 관리 | 기능 검증 대상 |
| 앱이 보장할 것 | 누른 만큼 정확히 센다. 입력한 만큼 저장되고, 저장된 것은 유실되지 않는다 | 최우선 검증 대상 |
| 앱이 못 푸는 것 | 사용자가 세는 것 자체를 까먹는 문제 (누르지 않은 입력) | 테스트 범위 밖 |

이 경계가 판정 기준이 된다. 카운트가 실제 뜬 단수와 다를 때, 사용자 입력 누락이면 결함이 아니고 입력이 있었는데 반영되지 않았거나 보존되지 않았으면 결함이다.

#### 무엇이 깨지면 가장 치명적인가 (영향도 축)

치명도 순위이며, 03 품질리스크맵의 영향도 축 근거가 된다.

1. 작업물 데이터 유실. 수십 시간 쌓은 프로젝트와 작업 기록이 사라진다. 복구가 불가능하고 사용자 이탈로 직결된다. 로컬 저장 실패뿐 아니라 서버 동기화 과정의 덮어쓰기와 유실을 포함한다.
2. 연결 정합성 깨짐. 프로젝트와 창고, 도안 사이 연결이 끊기거나 다른 항목을 가리킨다. 데이터는 있는데 내 작업 공간이 무너진다. 핵심 구조가 연결이므로 이 제품에서는 준유실급으로 본다. FK 제약조건이 부재한 참조(바늘, 스킬)는 DB가 무결성을 보장하지 않으므로 최우선 의심 지점이다.
3. 계정 간 데이터 노출. 계정 전환이나 동기화 과정에서 다른 계정의 데이터가 보이거나, 내 데이터가 다른 계정으로 저장된다. 기능 결함을 넘어 개인정보 문제이며, 실서비스라면 단독으로 릴리즈 차단 사유가 된다.
4. 카운트 부정확. 누른 것과 저장된 값이 다르다. 누른 만큼 정확히 센다는 보장의 직접 위반이다.
5. 도안 열람 불가. 파일은 있는데 열리지 않아 작업 자체가 중단된다.

이 순위 판단은 DBMS QA 관점의 연장이다. 데이터 유실과 정합성을 최상위에 두는 것, FK 제약조건이 부재한 참조를 최우선 의심 지점으로 잡는 것은 DB 레벨 무결성 검증을 앱 레이어에 적용한 결과다.

#### 핵심 사용자 흐름 (CUJ, Critical User Journey)

초보 사용자가 가치를 얻기까지의 최단 경로다. 이 흐름이 끊기면 개별 기능이 멀쩡해도 제품이 실패한 것으로 본다.

**CUJ-1. 첫 사용 → 첫 작업** (신규 사용자, 2경로)

- 1a. 프로젝트 우선: 회원가입/로그인 → 온보딩 → 프로젝트 생성 → 프로젝트 안에서 도안, 실, 바늘, 도구 추가 → 작업 화면에서 도안+카운터 확인 → 카운트 증가 → 앱 종료
- 1b. 창고 우선: 회원가입/로그인 → 온보딩 → 창고에 도안, 실, 바늘, 도구 먼저 등록 → 프로젝트 생성 → 등록해둔 항목을 프로젝트에 연결 → 작업 화면 확인 → 카운트 증가 → 앱 종료
- 경로 동등성 판정: 1a와 1b 완료 후 프로젝트 상태(연결된 항목 목록, 창고 원본, 서버 DB 레코드)가 동일해야 한다. 어느 경로로 만들었는지가 이후 동작에 영향을 주면 결함이다.

**CUJ-2. 재방문 → 작업 재개** (핵심 보장 검증)

앱 재실행 → 로그인 상태 유지 확인 → 기존 프로젝트 진입 → 마지막 단수, 도안, 연결된 재료가 그대로인지 확인 → 이어서 카운트

**CUJ-3. 모르는 기술 만남** (존재 이유 검증)

작업 중 행안내의 스킬 태그에서 모르는 기술 발견 → 해당 스킬 상세 학습 → 정상적인 닫기 또는 뒤로가기로 작업 화면 복귀 → 카운트와 도안 페이지 번호 보존 확인. 확대율과 페이지 내 스크롤 위치는 보존 대상에서 제외한다. 직접 사전, 스킬 검색 경로는 동일한 맥락 보존 기준을 적용하는 개별 TC로 검증한다.

각 CUJ는 05에서 시나리오 테스트로 설계한다. CUJ 도중 실패는 같은 기능의 단위 결함보다 심각도를 한 단계 높여 판정한다. 단 상향은 결과가 데이터 유실, 계정 간 노출, 앱 사용 불가에 해당할 때만 적용한다(04 개정).

#### 연결의 생애주기 (CUJ 밖, 치명도 2위 심층 검증)

1차 설계에서는 이것을 CUJ-3으로 잡았으나, 실행하면서 사용자 여정이 아님을 확인해 2026-09-01에 분리했다. 사용자가 한 자리에서 가치를 얻는 경로가 아니라 원본을 수정하고 삭제하는 과정을 따라가며 정합성을 보는 검증 시나리오이고, 사용자 눈에 보이는 연결 보존은 CUJ-2가 이미 덮는다. 케이스 ID `TC-CUJ3-01`은 실행 판정과 결함(DEF-21) 추적이 걸려 있어 그대로 둔다. 분류가 바뀐 것이지 케이스가 바뀐 것이 아니다.

항목별로 연결 방식이 다르므로 각각의 규칙대로 검증한다.

- 도구 (다중 공유 연결): 도구를 프로젝트 A와 B에 모두 연결 → 양쪽에서 보이는지 확인 → 같은 도구를 A에 한 번 더 연결 시도 시 중복이 생기지 않는지 확인 → A에서 연결 해제 시 B의 연결과 창고 원본이 유지되는지 확인 → 창고에서 도구 자체를 삭제 시 A, B 모두에서 연결이 사라지는지 확인
- 도안 (프로젝트당 1개, 복사본): 창고 도안을 프로젝트에 등록 → 창고 원본을 수정, 삭제해도 프로젝트의 도안(제목, 파일, 메모 드로잉)이 그대로인지 확인 → 이미 도안이 있는 프로젝트에 다른 도안 등록 시 동작 확인(교체인지 거부인지)
- 실 (대표 1개 + 사용 기록 다중, 스냅샷): 프로젝트 A의 대표 실로 지정 후 사용 기록 여러 개 작성 → 같은 실을 프로젝트 B의 대표 실로도 지정(공유 확인) → 창고에서 그 실을 삭제 → 각 프로젝트의 화면과 사용 기록에 실 정보가 스냅샷으로 남는지 확인
- 바늘 (FK 제약조건 부재 + 스냅샷): 프로젝트에 바늘 지정 → 창고에서 그 바늘을 삭제 → 프로젝트에 바늘 정보가 스냅샷으로 남는지, 깨진 화면이나 오류가 없는지 확인
- 스킬 (ID 배열, FK 제약조건 부재): 프로젝트에 스킬 여러 개 연결 → 그중 하나를 삭제 → 프로젝트의 스킬 목록이 어떻게 표시되는지 확인(사라지는지, 빈 항목이 뜨는지, 오류가 나는지)
- 스냅샷 항목 공통 (실, 바늘): 원본이 창고에 살아있는 상태에서 원본을 수정해도 기존 프로젝트는 연결 시점 스냅샷을 유지한다. 수정 이후 새로 연결한 프로젝트에만 변경된 값이 저장된다. 원본 삭제 후에도 각 프로젝트는 자신의 연결 시점 스냅샷을 계속 표시하며, 같은 프로젝트의 모든 화면은 동일한 값을 보여야 한다.

#### 어디를 넓게 보고 어디를 깊게 볼 것인가

테스트 실행은 CUJ 완주를 우선한다(넓이). 릴리즈 판정의 기본선은 사용자 흐름이 끊기지 않는 것이다. 그 위에 치명도 1~3위 결함 클래스(데이터 유실, 연결 정합성, 계정 간 노출)는 정상 흐름에서 드러나지 않으므로, 네트워크 단절, 동시 수정, 계정 전환, 전송 중단 같은 악조건 시나리오로 별도 심층 검증한다(깊이). 이 배분의 상세는 04 테스트전략에서 다룬다.

#### 성공 기준

정성 목표("초보자가 뜨개질에 잘 접근하게 한다")는 그대로는 검증할 수 없으므로 테스트 가능한 대리 기준으로 치환한다. CUJ 3개가 끊김 없이 완주되는가.
