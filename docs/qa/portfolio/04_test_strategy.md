# 04_테스트전략

> 2026-09-18 재작성, 2026-09-19 원본 9/15 갱신분(잔존 결함 허용 정책 신설) 반영. 접근법, 기법, 환경, 결함 관리, 종료 기준, 잔존 결함 허용 정책의 판정은 원본(`docs/qa/portfolio/04`, v1.1과 2차 사이클 전략, 8/29 심각도 규칙 개정, 9/15 허용 정책)을 그대로 옮겼다. 바뀐 것은 배치다. 29119-3 테스트 계획서의 전략 항목 순서로 다시 놓고 레벨, 유형, 기법에 ISTQB 4.0 분류를 붙였다.

#### 이 문서의 위치

ISTQB 4.0 계획 활동의 산출물이다. 29119-3 테스트 계획서를 셋으로 나눠 맡는다. 00이 맥락(대상, 범위, 가정과 제약, 이해관계자)을, 03이 리스크 레지스터를, 이 문서가 테스트 접근법을 담는다. 접근법에는 테스트 레벨과 유형, 설계 기법, 환경, 결함 관리, 종료와 중단 기준, 잔존 결함 허용 정책, 일정이 든다. 종료 기준은 여기서 정하고 모니터링과 제어(12)에서 대조하며 완료(15)에서 최종 확인한다.

#### 1. 접근법

리스크 기반 테스팅이다. 무엇을 먼저, 얼마나 깊게 볼지는 03의 등급이 정한다. 실행은 두 축으로 배분한다.

| 축 | 대상 | 방식 | 근거 |
| --- | --- | --- | --- |
| 넓이 | CUJ 3개 | 완주가 릴리즈 판정의 기본선이다. 개별 기능이 멀쩡해도 여정이 끊기면 실패로 본다 | 01의 5절 |
| 깊이 | P1 2클래스 (RC-01, RC-02) | 네트워크 단절, 서버 거부 주입, 계정 전환, 다중 기기 동시 수정 같은 악조건을 인위적으로 만든다 | 03의 4절. 정상 흐름에서는 드러나지 않는다 |

CUJ는 2026-09-01 재분류로 3개다. 연결의 생애주기는 CUJ에서 빠져 정합성 심층 검증으로 옮겼다(01의 6절).

문서마다 조직 축이 다르다. 03은 결함 클래스(무엇이 위험한가), 05는 SPEC과 CUJ(무엇을 확인하는가), 06은 화면(어떤 순서로 도는가, 같은 화면의 TC를 몰아 실행), 08은 POM의 Page(화면)와 Test(여정) 분리다. 축을 문서 역할에 맞게 바꾸는 것도 설계 판단이다.

| 전송 중 실패 재현 | Charles breakpoint로 전송 도중 실패와 응답 변조를 만든다 |

도구는 프로젝트 조건(iOS 시뮬레이터, HTTP 평문 통신, 로컬 단일 서버, 1인 QA, 단기 일정)에 맞춰 대안과 비교해 골랐다.

| 카테고리 | 선택 | 검토한 대안 | 선택 근거 | 재검토 조건 |
| --- | --- | --- | --- | --- |
| 네트워크 프록시 | Charles | Proxyman, mitmproxy, Fiddler | breakpoint, throttle, 응답 주입을 모두 지원하고 TC가 Charles 기준으로 설계됐다. HTTP 평문이라 Proxyman의 SSL 자동 설정 이점이 상쇄된다 | HTTPS 프로덕션 앱이면 Proxyman. CI 자동화가 필요하면 mitmproxy |
| UI 자동화 | XCUITest | Appium, Maestro, KIF | iOS 단일 플랫폼, Swift 코드베이스, 1인 프로젝트에서는 네이티브가 속도와 안정성에서 우세하고 Xcode 내장이다 | 크로스플랫폼이 필요하면 Appium. Maestro는 차기 검토 |

#### 7. 테스트 가능성 예외

00의 기준 커밋 고정 원칙에 테스트 가능성 확보를 위한 최소 변경만 예외로 둔다. 모든 변경은 기능 수정과 분리한 별도 커밋으로 관리하고 관련 문서에 기록한다.

- UI 자동화 식별자로 `accessibilityIdentifier`를 추가할 수 있다.
- Charles 관찰용 base URL을 바꿀 수 있다. Local Simulator 스킴의 `127.0.0.1`은 loopback이라 macOS 프록시를 거치지 않고, `.local` 호스트명은 시스템 프록시 bypass 목록에 걸린다. 서버가 `0.0.0.0`에 바인드돼 있어 2026-08-04~08 사이클의 스킴 환경값을 맥 LAN IP 주소로 바꿨다. `.xcscheme`은 커밋 대상이라 별도 testability 커밋으로 분리한다.
- Wi-Fi 재연결이나 네트워크 변경 뒤에는 Charles 기반 TC 전에 `ipconfig getifaddr en0`으로 LAN IP를 다시 확인하고, 바뀌었으면 스킴 환경값을 갱신해 변경 이력에 남긴다.
- 통신이 HTTP 평문이라 SSL Proxying 설정은 필요 없다. Charles GUI에서 LAN IP 요청이 캡처되는지 1회 확인하기 전에는 Charles 기반 TC를 실행하지 않는다.

#### 8. 결함 관리

발견 즉시 GitHub Issue로 등록한다. 제목, 재현 절차, 기대와 실제, 근거(스크린샷, psql 결과, 로그), 관련 SPEC ID를 담는다. 발견 시점은 개발 중 발견, 핸드오프 known issue, QA 신규 발견 셋으로 구분한다(00의 4절).

| 심각도 | 결과 |
| --- | --- |
| Critical | 데이터 유실, 계정 간 노출과 오염, 앱 사용 불가 |
| Major | 기능 실패, 정합성 표시 오류 |
| Minor | 안내 문구, 사용성 |

CUJ 도중 발생한 결함은 한 단계 올린다(01 규칙). **Major에서 Critical로 올리는 것은 결과가 데이터 유실, 계정 간 노출, 앱 사용 불가일 때만이다.** 보던 위치를 잃는 것처럼 회복 가능한 상태 손실은 CUJ 안에서 나와도 Major에 머문다. 이 단서는 2026-08-29에 붙였다. DEF-19를 판정하다가 기존 규칙이 유실과 위치 손실을 같은 등급으로 만든다는 것을 발견했다.

중단 기준은 둘이다. 기준 커밋에서 빌드나 서버 기동이 안 될 때, 테스트 환경이 오염됐을 때(DB 초기화 실패, 기준 커밋 이탈)다. 발생하면 실행을 멈추고 원인을 해소한 뒤 재개한다.

대조 결과는 11의 10절과 15의 2절에 있다. 1차 기준은 2026-08-30에, 2차 기준은 8/29 실행으로 충족됐다. 1차 계획과 2차 전략에는 잔존 결함 허용 정책(등급별로 몇 건까지 두고 나갈 수 있나)이 없었다. 15는 이 공백 때문에 종료 기준 충족 뒤에도 릴리즈 판정을 내리지 못했다. 정책은 2026-09-15에 신설했다(9-1).

##### 9-1. 잔존 결함 허용 정책 (2026-09-15 신설)

종료 기준과 별개다. 종료 기준은 "테스트를 충분히 했는가"를 묻고 이 정책은 "이 상태로 내보내도 되는가"를 묻는다. 앞이 충족돼도 뒤가 No일 수 있다. 29119-3 테스트 계획서에서는 완료 기준의 일부로 읽는다. 적용 결과는 15의 6절에 있다.

| 등급 | 허용 |
| --- | --- |
| Critical | 잔존 0건 |
| Major | 잔존 2건 이하 |
| Minor | 릴리즈 노트 기재로 허용 |

등급과 무관하게 불허하는 계열이 둘 있다.

| 계열 | 허용 |
| --- | --- |
| RC-01 데이터 유실 | 0건. 등급이 Minor로 매겨져도 불허 |
| RC-02 계정 간 노출 | 0건. 같음 |

계열 조건을 따로 둔 이유는 등급이 사후에 바뀐 전례가 있어서다. DEF-10(도안 교체 시 확인창 없이 드로잉 삭제)은 처음 RC-03으로 분류돼 Major였다가 8/29에 RC-01로 재분류되면서 Critical이 됐다. 등급만 보는 정책이었다면 재분류 전에 통과했을 것이다. 통과 시점에 사라지는 데이터의 양은 재분류 여부와 무관하게 같다. 등급은 판단이고 계열은 결과다. 판단이 틀릴 수 있으므로 결과 쪽에도 잠금을 건다.

**잔존 결함 건수는 닫힌 이슈 수가 아니라 실행으로 확인된 수로 센다.** 재현 없이 코드 대조만으로 닫은 건은 이 정책의 0건에 포함되지 않으며 15의 판정문에 개별로 적는다.
