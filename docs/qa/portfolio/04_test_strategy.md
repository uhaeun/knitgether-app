#### 접근법

리스크 기반 테스트를 기본으로 한다. 무엇을 먼저, 얼마나 깊게 볼지는 03의 등급이 결정한다. 실행은 두 축으로 배분한다.

- 넓이: CUJ 3개의 완주가 릴리즈 판정의 기본선이다(2026-09-01 재분류. 연결의 생애주기는 CUJ가 아니라 정합성 심층으로 옮겼다. 01 참조). 개별 기능이 멀쩡해도 여정이 끊기면 실패로 본다.
- 깊이: P1 클래스 2건은 정상 흐름에서 드러나지 않으므로 네트워크 단절, 서버 거부 주입, 계정 전환, 다중 기기 동시 수정 같은 악조건을 인위적으로 만들어 검증한다.

문서마다 조직 축이 다르다. 03은 결함 클래스(무엇이 위험한가), 05는 SPEC과 CUJ(무엇을 확인하는가), 06은 화면(어떤 순서로 도는가, 같은 화면의 TC를 몰아 실행), 08은 POM의 Page(화면)와 Test(여정) 분리다. 축을 문서 역할에 맞게 바꾸는 것 자체가 설계 판단이다.

#### 테스트 레벨과 유형

- 단위 테스트: 개발 단계 산출물로 이미 존재한다(Swift Testing 기반 @Test 329건, 41개 파일, Repository 계층 중심). QA 사이클에서 재작성하지 않고 09의 CI 게이트에서 회귀 장치로 활용한다.
- 통합 검증: 클라이언트와 서버 사이 데이터 흐름을 07에서 검증한다. API 응답만 보지 않고 psql로 서버 DB의 실제 상태까지 대조한다.
- 시스템(시나리오) 테스트: CUJ 3개와 연결 정합성, P1 악조건 시나리오를 06에서 수동 실행한다.
- UI 자동화: 핵심 여정 일부를 08에서 XCUITest로 구현한다.
- 정적 테스트: 02 작성 과정의 코드 실측이 이에 해당하며, 실행 전에 불일치 의심 8건을 식별했다.

#### 범위

포함: 기능 동작(02의 SPEC 30건), CUJ 3개와 연결 정합성 심층, RC-01~07, API와 서버 DB 정합성, 네트워크 이상 조건. RC-08은 07에서 실증한다.

제외와 근거는 다음과 같다.

- 실기기 다수 매트릭스: 시뮬레이터 중심으로 대신한다. 리스크 상위가 전부 데이터와 동기화 계층이라 기기 파편화보다 정합성 검증의 우선순위가 높고, 1인 리소스에서 기기 확보 비용 대비 발견 가치가 낮다고 판단했다.
- 성능과 부하 테스트: 로컬 단일 사용자 앱 특성상 동시 부하 시나리오가 없고, 데이터 정합성 리스크 검증을 우선한다. 다음 사이클에 넣는다면 목록 조회(프로젝트 수백 건)와 도안 파일 로딩의 응답 시간 스모크부터 시작한다.
- 접근성, 국제화: 이번 사이클 범위 밖으로 선언한다.

#### 설계 기법

05의 TC는 다음 기법을 적용하고 각 TC에 적용 기법을 태깅한다.

- 경계값 분석: 카운터 하한 0, 10초 미만 세션, 빈 목록과 1건 목록
- 상태 전이: syncStatus 4상태(localOnly, pendingUpload, pendingDelete, synced) 전이, 타이머의 포그라운드/백그라운드 전이
- 에러 추정과 에러 기대: 서버 거부, 네트워크 단절, fetch 실패 시 화면 구분
- 시나리오 테스트: CUJ 3개와 연결 생애주기, 경로 동등성(1a vs 1b)
- 회귀: 개발 중 발견돼 수정된 문제들(타이머 중복 저장, 정렬 의존 등)의 재발 확인

#### 테스트 환경

- 클라이언트: iOS 시뮬레이터. 다중 기기 시나리오는 시뮬레이터 2대로 동일 계정 동시 사용을 재현한다.
- 서버: PostgreSQL은 Docker Compose로 기동하고, NestJS API는 호스트에서 `npm run start:dev` 프로세스로 실행한다. 사이클 시작 시 DB를 초기화해 재현성을 확보한다.
- 도구: Postman(API 호출), psql(서버 DB 실측과 악조건 데이터 주입), Charles(단절, throttle, breakpoint, 응답 변조), Xcode(XCUITest).
- 네트워크 이상 재현: PostgreSQL 컨테이너는 유지한 채 NestJS의 `npm run start:dev` 프로세스를 `Ctrl+C`로 종료하면 API 완전 단절을 재현할 수 있다. API 복구는 같은 명령으로 다시 기동한다. Charles breakpoint는 전송 도중 실패, 응답 변조를 재현한다.

#### 자동화 전략

전부 자동화하지 않는다. 어디에 둘지의 판단이 전략이다.

- 자동화하는 것(08): 반복 가치가 높고 판정이 안정적인 CUJ 핵심 여정 1~2개. XCUITest POM으로 구현해 회귀 장치로 남긴다. Page(화면 단위 객체)와 Test(여정 단위 시나리오)를 분리해 화면 변경과 시나리오 변경의 수정 범위를 격리한다.
- 자동화하지 않는 것: P1 악조건 시나리오. 다중 기기, 네트워크 조작, psql 주입이 얽혀 자동화 비용이 발견 가치를 초과한다. 수동 실행과 도구 조합이 효율적이다.
- CI 게이트(09): 빌드와 기존 단위 테스트를 GitHub Actions에서 실행하고 실패 시 artifact를 수집한다. 사람이 잊어도 기계가 잡는 최소 회귀선이다.

#### 테스트 가능성 예외

00의 기준 커밋 고정 원칙에 테스트 가능성(testability) 확보를 위한 최소 변경만 예외로 허용한다. 모든 변경은 기능 수정과 분리한 별도 커밋으로 관리하고 수정 내역을 관련 문서에 기록한다.

- UI 자동화 식별자: XCUITest가 요소를 안정적으로 식별할 수 있도록 `accessibilityIdentifier`를 추가할 수 있다.
- Charles 관찰용 base URL: Local Simulator 스킴의 `http://127.0.0.1:3000/api/v1`은 loopback 트래픽이라 macOS 프록시를 통과하지 않는다. `haeun.local`도 시스템 프록시 bypass 목록의 `*.local`에 해당하고 127.0.0.1로 해석되므로 사용하지 않는다. 서버가 `0.0.0.0`에 바인드되어 있으므로, 2026-08-04~08 사이클의 Local Simulator 스킴 환경값은 맥 LAN IP를 사용한 `http://192.168.219.111:3000/api/v1`로 변경한다. `.xcscheme`은 커밋 대상이므로 별도 testability 커밋으로 분리한다.
- DHCP 변동 확인: Wi-Fi 재연결 또는 네트워크 변경 후 Charles 기반 TC를 실행하기 전에 `ipconfig getifaddr en0`으로 맥 LAN IP를 재확인한다. IP가 달라졌으면 Local Simulator 스킴 환경값도 같은 주소로 갱신하고 별도 testability 변경 이력에 남긴다.
- 실행 전 확인: 통신은 HTTP 평문이므로 Charles SSL Proxying 설정은 필요 없다. Charles GUI에서 LAN IP 요청이 실제 캡처되는지 1회 확인하고, 확인 전에는 Charles 기반 TC를 실행하지 않는다.

#### 결함 관리

- 등록: 발견 즉시 GitHub Issue로 등록한다. 제목, 재현 절차, 기대와 실제, 근거(스크린샷, psql 결과, 로그), 관련 SPEC ID를 포함한다.
- 심각도: Critical(데이터 유실, 계정 간 노출과 오염, 앱 사용 불가), Major(기능 실패, 정합성 표시 오류), Minor(안내 문구, 사용성). CUJ 도중 발생한 결함은 한 단계 상향한다(01 규칙). 단, **Major → Critical 상향은 결과가 데이터 유실·계정 간 노출·앱 사용 불가에 해당할 때만** 적용한다. 보던 위치를 잃는 것처럼 회복 가능한 상태 손실은 CUJ 안에서 나와도 Major에 머문다. (8/29 개정 — DEF-19 판정 과정에서 규칙이 유실과 위치 손실을 같은 등급으로 만드는 문제를 발견)
- 시점 표기: 개발 중 발견 / 인수인계 문서 known issue / QA 신규 발견을 구분한다(00 규칙).

#### 잔존 결함 허용 정책 (2026-09-15 신설)

종료 기준과 별개다. 종료 기준은 "테스트를 충분히 했는가"이고 이 정책은 "이 상태로 내보내도
되는가"다. 앞이 충족돼도 뒤가 No일 수 있다. 1차 사이클에서 15가 판정을 내리지 못한 이유가
이 정책의 부재였으므로 여기에 먼저 둔다.

| 등급 | 허용 |
| --- | --- |
| Critical | 잔존 0건 |
| Major | 잔존 2건 이하 |
| Minor | 릴리즈 노트 기재로 허용 |

**등급과 무관하게 불허하는 계열이 둘 있다.**

| 계열 | 허용 |
| --- | --- |
| RC-01 데이터 유실 | 0건. 등급이 Minor로 매겨져도 불허 |
| RC-02 계정 간 노출 | 0건. 같음 |

계열 조건을 따로 두는 이유는 등급이 사후에 바뀐 전례가 있기 때문이다. DEF-10(도안 교체 시
확인창 없이 드로잉 삭제)은 처음 RC-03으로 분류돼 Major였다가 8/29에 RC-01로 재분류되면서
Critical이 됐다. 등급만 보는 정책이었다면 재분류 전에 통과했을 것이고, 통과 시점에 사라지는
데이터의 양은 재분류 여부와 무관하게 같았다.

등급은 판단이고 계열은 결과다. 판단이 틀릴 수 있으므로 결과 쪽에도 잠금을 건다.

**적용 조건.** 잔존 결함 건수는 "닫힌 이슈 수"가 아니라 "실행으로 확인된 수"로 센다.
재현 없이 코드 대조만으로 닫은 건은 이 정책의 0건에 포함되지 않으며, 15의 판정문에
개별로 적는다.

#### 부록. 도구 선택 근거 (Tool Selection Rationale)

각 도구는 대안을 검토한 뒤 이 프로젝트 조건(iOS 시뮬레이터, HTTP 평문 통신, 로컬 단일 서버, 1인 QA, 단기 일정)에 맞춰 선택했다. 선택의 방어 논리와 한계, 차기 검토 대상을 함께 기록한다.

| 카테고리 | 선택 | 검토한 대안 | 선택 근거 | 한계, 차기 검토 |
| --- | --- | --- | --- | --- |
| 네트워크 프록시 | Charles Proxy | Proxyman, mitmproxy, Fiddler | 자료와 레퍼런스가 풍부하고 breakpoint, throttle, 응답 주입 등 필요 기능을 모두 지원. 이 사이클의 TC가 Charles 기준으로 설계됨. HTTP 평문 통신이라 대안(Proxyman)의 핵심 강점인 SSL 인증서 자동설정 이점이 상쇄됨 | Proxyman이 iOS 시뮬레이터 통합과 SSL 설정에서 우세(커뮤니티에서 Charles→Proxyman 이동 추세). HTTPS 프로덕션 앱을 검증한다면 Proxyman 재검토. mitmproxy는 Python 스크립팅으로 CI 자동화가 필요할 때 검토 |
| UI 자동화 | XCUITest | Appium, Maestro, KIF | iOS 단일 플랫폼 + Swift 코드베이스 + 1인 프로젝트에는 네이티브 프레임워크가 속도와 안정성에서 우세하고 Xcode 내장이라 별도 설치가 없음. Appium의 유일한 강점인 크로스플랫폼이 이 프로젝트엔 불필요 | 크로스플랫폼(iOS+Android 동시)이 필요하면 Appium. 단 무거운 런타임과 flakiness가 트레이드오프. Maestro(YAML 기반, flakiness 자동 처리)는 진입장벽이 낮은 최신 대안으로 차기 검토 |
| API 테스트 | Postman | Insomnia, Bruno, curl/httpie | 컬렉션, 환경변수, CI 연동(newman)이 성숙하고 자료가 많음. API 수동 호출과 서버 응답 확인이라는 용도에 충분 | Bruno(오픈소스, 로컬 파일 기반)가 부상 중. 팀 협업이나 버전관리가 중요해지면 차기 검토 |
| DB 검증 | psql (CLI) | TablePlus, DBeaver, pgAdmin, Postico | 실행한 쿼리가 텍스트로 남아 재현 가능한 실측 기록이 됨. GUI 클릭보다 "이 쿼리로 이 결과를 얻었다"가 QA 증거로서 강함(DBMS QA 관점의 연장) | 대량 결과 탐색이나 시각적 스키마 확인이 필요하면 GUI(TablePlus 등) 병행 |

**도구 도입 원칙**: 이 프로젝트는 이미 설계된 TC와 단기 일정에 묶여 있으므로, "지금 도구를 교체할 것인가"와 "차기 사이클에 무엇을 검토할 것인가"를 분리해 판단했다. 현재 선택은 유지하되, 각 카테고리의 우세한 대안과 그것을 택하지 않은 이유를 명시함으로써 도구 선택이 관성이 아니라 조건 기반 판단임을 남긴다.
