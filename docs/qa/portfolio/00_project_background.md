# 00_프로젝트 배경

> 2026-09-02 재작성. 판정과 실행 기록은 8월에 쓴 원본(`docs/qa/portfolio/00~15`)이 정본이다. 이 판은 같은 사실을 ISTQB CTFL 4.0 테스트 프로세스와 ISO/IEC/IEEE 29119-3 산출물 체계에 맞춰 다시 배치한 것이다. 숫자와 판정은 원본에서 옮겼고 새로 만든 것은 없다.

#### 이 문서의 위치

ISTQB 4.0은 테스트 프로세스를 계획, 모니터링과 제어, 분석, 설계, 구현, 실행, 완료의 7개 활동으로 정의한다. STLC라는 별도 생명주기는 쓰지 않고, 테스트를 개발 프로세스 안에 통합된 활동으로 본다. 이 문서는 계획 활동의 산출물인 테스트 계획서 가운데 맥락(context) 부분이다. 29119-3 테스트 계획 템플릿의 1절에 해당하고 테스트 대상, 범위, 가정과 제약, 이해관계자를 담는다. 리스크 레지스터는 03, 전략과 종료 기준은 04가 맡는다.

#### 1. 프로젝트와 테스트 대상

KnitGether(Knit + Together)는 뜨개질 초보자를 위한 iOS 작업 관리 앱이다. 도안을 보다가 모르는 기술이 나오면 유튜브와 검색을 오가야 하고, 실과 바늘과 도구는 흩어져 관리된다. 이 왕복과 분산을 앱 하나 안에서 없애는 것이 제품 목표다. 사용자가 진행하는 뜨개 프로젝트를 가운데 두고 창고(실, 바늘, 도구, 스킬)를 프로젝트에 연결한다. 도안, 단수 카운터, 스킬 학습을 작업 화면 하나에서 오간다.

테스트 대상은 둘이다.

| 대상 | 구성 | 기준 |
| --- | --- | --- |
| iOS 클라이언트 | SwiftUI. 로컬 저장과 원격 저장을 offline-first로 감싼 Repository 구조, 토큰 기반 인증 | 커밋 `bf2b001` |
| 서버 | NestJS, Prisma, PostgreSQL. 인증과 파일 스토리지 포함 | 같은 커밋 |

기준 커밋 `bf2b001`은 QA 인수인계 문서가 커밋된 시점이다. 1차 사이클 트랙 A는 이 커밋 빌드로 판정했다. 트랙 B와 C는 UX 개편 빌드이고 그 구분은 12의 측정 기준에 있다. 수정 커밋은 1차 실행이 끝난 뒤에 들어갔다.

#### 2. 범위

포함하는 것은 기능 동작이다. 데이터 저장과 동기화, 창고 항목과 프로젝트의 연결, 카운터, 도안 열람, 인증과 계정 격리. 각 영역의 검증 기준선은 02에 SPEC 48건으로 있다(2026-09-15 AUTH-08 승격 반영).

포함하지 않는 것도 적어 둔다. 실기기 다수 매트릭스는 시뮬레이터 중심으로 대신했다. 성능과 부하는 1인 QA 리소스에서 데이터 정합성 리스크 검증을 우선하기로 판단해 뺐다. 접근성은 이번 사이클 밖이다. 보안은 기능 사이클 밖이지만 9/1에 정적 점검 한 번을 따로 했고 기록은 `docs/dev/security_review.md`에 있다. 각 판단의 근거는 04에 있다.

#### 3. 가정과 제약

- 구현은 AI 기반 바이브코딩으로 했다. 기획 명세를 프롬프트로 써서 AI 검토를 거쳐 확정하고, 그 명세로 개발된 MVP가 QA 대상이다. 사람이 리뷰하지 않은 코드에서 무엇이 깨지는지가 이 QA의 실전 질문 하나다.
- 사전 기획 문서(`docs/spec/원본_v2.2.md`)는 있었다. 구현 과정에서 데이터 구조가 바뀌어 현재 코드와 괴리가 생겼고, 그래서 검증 기준선은 코드 실측에서 역산해 02로 세웠다. 코드를 정답으로 삼지 않으려고 기획 의도와 대조해 불일치를 따로 관리한다.
- 기준 커밋 시점의 자동 테스트(단위, XCUITest, 서버 e2e, pytest)는 전부 AI 작성분이다. 포트폴리오 증거로 세지 않고 CI 회귀 장치로만 쓴다.
- 1인이다. 기획, 개발 검토, QA를 한 사람이 했다. ISTQB가 정의하는 테스트 관리와 테스팅 두 역할이 한 사람에게 있다.

#### 4. 이해관계자와 역할 분리

기획자가 자기 제품을 검증한다. 아는 경로만 테스트하는 편향이 구조적으로 생긴다. 다섯 원칙으로 통제했고, 각 원칙이 실제로 작동했는지는 뒤 문서의 특정 열에서 확인할 수 있게 했다.

| 원칙 | 내용 | 작동 여부를 보는 곳 |
| --- | --- | --- |
| 판정 기준의 외부화 | 합격과 불합격은 기억이나 의도가 아니라 02에 문서화된 기준으로만 판정한다 | 06과 11의 판정 열 |
| 근거의 실측화 | 근거는 코드와 DB 실측으로 남긴다. 실측되지 않은 숫자는 쓰지 않는다 | 07의 psql 대조, 12의 출처 열 |
| 결함의 공개 관리 | 발견한 결함은 GitHub Issue로 공개 관리한다 | 10의 이슈 열 |
| 기준 커밋 고정 | `bf2b001` 기준으로 수행하고 사이클 중 코드를 수정하지 않는다 | 10의 수정 커밋 날짜 |
| 시점의 구분 | 발견 시점을 개발 중 발견, 인수인계 known issue, QA 신규 발견 세 범주로 나눠 기록한다 | 10의 1절 |

원칙이 실제로 지켜졌는지의 자기 평가는 최종 페이지 7절(회고)에서 한다.

#### 5. 이 QA의 목적

DBMS QA 경력(4년 이상, 데이터 정합성, 장애 복구, 동시성 검증)을 앱과 웹 서비스 QA로 넓히기 위한 실증이다. 산출물은 앱이 아니라 이 앱을 대상으로 한 QA 수행 기록 전체다.

#### 6. 문서 세트의 구성

번호는 원본과 같다. 각 문서가 ISTQB 7활동 가운데 어디의 산출물인지를 붙였다.

| 활동 | 문서 | 29119-3 산출물 |
| --- | --- | --- |
| 계획 | 00 배경, 04 전략 | 테스트 계획서 (맥락, 접근법, 종료 기준) |
| 모니터링과 제어 | 11 실행 원장, 12 스코어카드 | 테스트 진행 보고서 |
| 분석 | 01 대상 분석, 02 동작 정의서, 03 리스크맵 | 테스트 베이시스, 테스트 조건, 리스크 레지스터 |
| 설계 | 05 테스트케이스, 09 케이스 마스터, 16 테스트 차터 | 테스트 케이스, 커버리지 아이템, 테스트 차터 |
| 구현 | 08 도구 비교, 13 자동화 스위트 | 자동화 스크립트, 테스트 환경 |
| 실행 | 06 수동 실행, 07 API와 네트워크, 10 결함 카탈로그 | 테스트 로그, 인시던트 리포트 |
| 완료 | 14 관찰, 15 릴리즈 판정 | 테스트 완료 보고서, 교훈 |

16 테스트 차터는 원본에 없던 문서다. 06의 탐색 관찰이 세션 기반이었는데 차터 형식으로 남기지 않았고, 이번 재정립에서 당시 관찰 로그를 차터로 정리해 신설한다.
