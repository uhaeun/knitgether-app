# 00_프로젝트 배경

> 원본: Notion `00_프로젝트 배경` (최종 갱신 2026-08-03) / repo 이관 2026-08-27

#### 한눈에

- 이 문서가 보여주는 것: QA의 객관성 확보(셀프 QA 편향 통제), 자기주도적 QA 수행
- 세 줄 요약: DBMS QA 경력을 앱 QA로 확장하기 위한 실증 프로젝트다. 산출물은 앱이 아니라 QA 수행 기록 전체다. 자기 제품을 검증하는 편향은 5가지 원칙으로 통제한다.

#### 목적

이 프로젝트는 DBMS QA 경력(4년 이상, 데이터 정합성, 장애 복구, 동시성 검증)을 앱과 웹 서비스 QA로 확장하기 위한 실증 프로젝트다. 기획, 개발 검토, QA 전 과정을 직접 수행했으며, 최종 산출물은 앱이 아니라 이 앱을 대상으로 한 QA 수행 기록 전체다.

#### 대상 제품, 뜨개더(KnitGether)

KnitGether(Knit + Together)는 뜨개질 초보자를 위한 iOS 작업 관리 앱이다.

해결하려는 문제는 이렇다. 뜨개질 중에는 도안을 보다가 모르는 기술이 나오면 유튜브나 검색을 오가야 하고, 실, 바늘, 도구 같은 재료는 따로 흩어져 관리된다. 이 왕복과 분산을 한 앱 안에서 없애는 것이 목표다.

핵심 구조는 사용자가 진행하는 뜨개 프로젝트를 중심에 두고, 창고(실, 바늘, 도구, 스킬)와 라이브러리를 프로젝트에 연결하는 것이다. 도안, 단수카운터, 스킬 학습을 작업 화면 하나에서 오가도록 설계했다.

#### 역할

기획과 QA를 담당했다. 구현은 AI 기반 바이브코딩으로 진행했다. 기획 명세를 프롬프트로 작성해 AI의 피드백과 검토를 거쳐 확정하고, 그 명세에 따라 개발된 MVP를 QA 대상으로 삼는다. 따라서 이 QA는 AI가 생성한 코드를 검증 대상으로 삼는 실전 기록이기도 하다. 사람이 리뷰하지 않은 코드에서 무엇이 깨지는지를 기준선과 실측으로 확인한다.

#### 셀프 QA 편향 통제

기획자가 자기 제품을 검증하는 구조이므로, 아는 경로만 테스트하는 편향을 막기 위해 다음 다섯 원칙을 세웠다. 아래는 1차 사이클 시작 전의 계획이다.

- 판정 기준의 외부화: 합격/불합격 판정은 기억이나 의도가 아니라 02 기능 동작 정의서에 문서화된 기준으로만 한다.
- 근거의 실측화: 판단 근거는 코드와 DB 실측으로 남긴다. 실측되지 않은 숫자는 쓰지 않는다.
- 결함의 공개 관리: 발견한 결함은 GitHub Issue로 공개 관리한다.
- 기준 커밋 고정: QA는 커밋 `bf2b001`(QA 인수인계 문서 커밋 시점) 기준으로 수행하며, QA 사이클 중 코드를 수정하지 않는다.
- 시점의 구분: 발견 시점을 "개발 중 발견 / 핸드오프 known issue / QA에서 신규 발견" 세 범주로 구분해 기록한다.

실행에서는 결함 공개 관리와 기준 커밋 동결 원칙을 온전히 지키지 못했다. 1차 사이클 중에는 시트로 결함을 추적하고 GitHub 이슈 #18~#39를 8/30에 사후 등록했다. 이후 발견한 DEF-24~29는 당일 등록했지만 DEF-22는 대장에만 남아 있다(10의 4-2~4-3절). QA 중 UX 개편도 병행돼 DEF-15 회귀가 발생했다(06). `bf2b001`은 최초 판정의 비교 기준으로 유지하고, 변경 후 실행의 빌드와 결과는 11에 별도로 기록했다.

#### 이 포트폴리오의 범위

문서는 준비와 분석(00~01), 설계(02~05), 실행과 자동화(06~13), 관찰과 릴리즈 판정(14~15)으로 구성된다.

포함하지 않는 것도 있다. 실기기 다수 매트릭스 검증은 시뮬레이터 중심으로 대신했고, 성능과 부하 테스트는 1인 QA 리소스에서 데이터 정합성 리스크 검증을 우선하기로 판단해 제외했다. 각 항목의 판단 근거는 04 테스트전략에서 다룬다.
