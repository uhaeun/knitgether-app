# QA 산출물 작성 가이드

> 쓰는 사람: 유하. 이 가이드는 "무엇을 어떤 순서로 생각해서 쓰는지"만 알려준다.
> 내용 자체는 직접 판단해서 쓴다. 다 쓰면 Claude에게 리뷰 요청.

## 공통 원칙 3가지

1. **사실과 판단을 분리한다.** "실제 결과"에는 본 것만 쓴다. 해석("아마 서버 문제인 듯")은 별도 칸에.
2. **모든 판단에는 근거 한 줄.** P0라고 쓰면 왜 P0인지 한 줄. severity High면 왜 High인지 한 줄. 근거 없는 판단은 면접에서 방어 불가.
3. **숨기지 않는다.** 못 한 것, 애매한 것, 미해결 결함은 그대로 적는다. "다 PASS"인 포트폴리오보다 "잔여 리스크를 아는" 포트폴리오가 신뢰받는다.

## 1. 리스크/우선순위 매기기 (7/20 오후)

### 생각하는 순서
기능마다 세 가지를 자문한다:
1. **틀어지면 데이터가 상하는가?** (유실되면 복구 불가능한가) — 가장 무거운 축
2. **사용자가 얼마나 자주 지나가는 길인가?** (핵심 흐름 위에 있는가)
3. **최근에 코드가 많이 바뀌었는가?** (회귀 위험 — git log가 근거)

### 등급 기준 (예시 — 본인 기준으로 조정 가능, 단 기준을 문서에 명시할 것)
- **P0**: 데이터 생성/수정/삭제/동기화/계정. 실패 시 데이터 유실 또는 앱 사용 불가
- **P1**: 주요 기능이지만 우회로가 있거나 재시도로 복구 가능
- **P2**: 표시/편의 기능. 틀려도 데이터는 안전

### 나쁜 예 / 좋은 예
- ❌ `Workspace | P0` (근거 없음)
- ⭕ `Workspace 세션 기록 | P0 — 작업시간이 유실되면 사용자가 복구할 방법이 없고, offline-sync 코드가 최근 2주 집중 변경됨(ff4066c 등)`

### 스스로 점검 (꼬리질문)
- "왜 온보딩은 P0가 아닌가요?" 에 한 문장으로 답할 수 있는가
- P0가 전체의 절반을 넘으면 우선순위가 아니다 — 다시 줄일 것

## 2. 테스트 케이스 (7/21)

### TC 한 건의 구조
`ID | 화면 | 우선순위 | 설계기법 | 전제조건 | 단계 | 기대결과 | DB확인(해당 시) | 결과 | 결함링크`

### 기대 결과 쓰는 법 — TC의 심장
"무엇이 어떻게 되는지"를 **관찰 가능한 형태**로. 화면에 보이는 것 + 데이터에 남는 것.

- ❌ "정상적으로 저장된다"
- ❌ "에러가 발생하지 않는다"
- ⭕ "저장 버튼 탭 → 목록 화면으로 복귀, 최상단에 'OO' 프로젝트 카드 표시(상태 배지 '진행중'), 서버 DB Project 테이블에 row 1건 생성(name='OO', status=WIP)"

체크: 이 기대 결과만 읽고 **다른 사람이 PASS/FAIL을 판정할 수 있는가?** 판정에 내 머릿속 지식이 필요하면 다시 쓴다.

### 단계 쓰는 법
- 번호 붙여서, 처음 보는 사람이 그대로 따라 할 수 있게
- 입력값은 구체적으로: ❌ "이름 입력" ⭕ "이름에 '테스트목도리' 입력"
- TC 하나는 하나만 검증. "생성하고 수정하고 삭제한다"는 3개로 쪼갠다

### 설계 기법 적용법 (태그 달 때)
- **동등분할**: 입력을 유효/무효 그룹으로 나눠 각 그룹 대표 1개 (예: 이메일 형식 유효/무효)
- **경계값**: 제한이 있는 곳의 양끝 (글자수 max라면: max-1, max, max+1 / 개수 0, 1, 다수)
- **상태전이**: 상태가 있는 것의 전환 (프로젝트 진행중→완료, 온라인→오프라인→복구)
- **결정테이블**: 조건 조합 (로그인여부 × 네트워크여부 × 캐시유무 같은 것)

기법을 억지로 다 쓰지 말 것. 그 기능에 맞는 기법을 골랐다는 게 포인트.

### 스스로 점검
- 이 TC 시트를 나 없이 다른 QA에게 주면 같은 결과가 나오는가
- P0 기능에 오류/오프라인/재실행 케이스가 있는가 (정상 케이스만 있으면 미완성)

## 3. 수동 E2E 실행 기록 (7/22)

### 기록 형식 (케이스마다)
`TC-ID | 기대 결과 | 실제 결과 | 분류 | 증거 파일명 | 결함번호(있으면)`

### 실제 결과 쓰는 법
본 것을 그대로. 시점·화면·문구까지.
- ❌ "저장이 안 됨"
- ⭕ "저장 탭 시 버튼이 눌리는 애니메이션은 있으나 화면 전환 없음, 토스트 미노출, 목록 재진입 시 항목 없음"

### 분류 판단
- 기대와 다르고 재현됨 → `FAIL` (결함 후보)
- 기대 자체가 정의 안 돼 있었음 → `NEED_SPEC_CONFIRM` (스펙 이슈 — 이것도 소중한 산출물)
- 환경 탓(서버 안 켬, 시뮬레이터 문제) → `ENV_ISSUE` (결함 아님, 섞이면 신뢰도 하락)
- 간헐 재현 → `RETRY_REQUIRED` + 재현율 기록 (예: 5회 중 2회)

### 증거 규칙
실행 **중간에** 찍는다. 끝나고 재현해서 찍으려면 두 배로 힘들다.
파일명: `0722_TC-P0-03_workspace_FAIL.png` → `evidence/` 폴더

## 4. 버그 리포트 (GitHub Issues, 7/25)

### 제목 공식
`[화면] 조건 → 증상` — 목록만 훑어도 뭔지 알게.
- ❌ "저장 버그"
- ⭕ "[Workspace] 오프라인에서 단수 변경 후 앱 재실행 → 변경 내용 유실"

### 본문 순서
1. **환경**: 앱 빌드(커밋 해시), iOS 버전, 기기/시뮬레이터, 서버 상태, 계정
2. **재현 절차**: 번호. 그대로 따라 하면 100% 재현되게. 재현율 명시 (예: 3/3)
3. **기대 결과 / 실제 결과**: 각 한 줄씩, 관찰 가능한 형태
4. **증거**: 스크린샷/영상/로그
5. **Severity + 근거 한 줄**: 예) `High — 사용자 데이터 유실, 복구 불가`
6. (알면) **추정 원인**: "실제"와 구분해서 "추정"이라고 명시

### Severity vs Priority 구분 (면접 단골)
- Severity = 얼마나 심각한가 (데이터 유실 > 기능 불가 > 오동작 > 표시 오류)
- Priority = 얼마나 빨리 고쳐야 하는가 (심각해도 극단 케이스면 Priority 낮을 수 있음)

### 스스로 점검
- 이 리포트만 보고 내가 아닌 사람이 재현할 수 있는가
- 기대 결과의 근거(요구사항/스펙)가 있는가 — 없으면 NEED_SPEC_CONFIRM일 수도

## 5. 테스트 결과서 + 릴리즈 판정 (7/25~26)

### 구조
1. 실행 수치: 총 TC / 분류별 건수 / P0 실행률 (표)
2. 결함 요약: 총 N건, severity 분포, 수정 M건/잔여 K건
3. 잔여 리스크: 미수행 케이스와 이유, 미해결 결함의 영향
4. **판정**: exit criteria 항목별 충족 여부 표 → Go / No-Go / 조건부 Go + 근거

### 핵심
수치는 반드시 실제 실행 결과와 일치. 판정은 "느낌"이 아니라 exit criteria 대조표에서 나온다.
No-Go여도 괜찮다 — "이 기준 미달로 No-Go 판단"이 오히려 QA다운 결론.

## 리뷰 요청하는 법

문서 하나 완성할 때마다: "GUIDE 기준으로 리뷰해줘. 특히 [기대결과/근거/재현절차] 봐줘."
리뷰 후 수정도 직접. 고칠 수 없게 애매한 지적이면 다시 물어볼 것.
