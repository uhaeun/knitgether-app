## 8. 3차 회귀 (2026-09-01, 기능정의서 수정분 검증)

기능정의서의 정의 없음 15건을 앱과 서버에서 수정한 뒤(`f93aacc`) Appium 전량을 재실행했다. UI 케이스 ID 78개, pytest 실행 항목 80건이다(2026-09-19 정정). 수정 범위가 입력 검증, 안내 문구, 동기화 충돌 처리라 화면 전반에 걸쳐 있어 부분 실행 대신 전량으로 돌렸다.

| 단계 | 결과 |
| --- | --- |
| 1회차 전량 실행 (55분) | 65 passed, 14 failed, 1 skipped |
| 실패 14건 격리 재실행 | 12 passed, 1 failed, 1 error |
| 실패 재현 확인 (UI-25, UI-31 각 3회) | UI-25는 3회 전부 재현, UI-31은 3회 전부 통과 |
| 원인 수정 후 14건 재실행 | 14 passed (13분) |

판정은 10의 6절 기준을 그대로 적용했다. 진짜 결함은 0건이다.

- 재현되지 않은 13건은 인프라 실패로 분류했다. 근거는 격리 실행에서 전부 통과했고, 실패 형태가 `InvalidSessionIdException`과 `socket hang up`처럼 러너 계층 오류였다는 점이다. 55분 연속 실행에서 WebDriverAgent 세션이 저하되는 것으로 보이며, 이 부채는 08의 숙제에 함께 둔다
- 재현된 1건(UI-25)은 앱이 아니라 테스트 코드의 결함이었다. `set_target_date`가 달 이동 횟수를 오늘 기준으로 계산했는데, 실제 날짜 피커는 현재 선택된 목표일의 달로 열린다. 연속으로 날짜를 바꾸는 경로를 자동화가 처음 실행하면서 드러났다. 피커의 현재 값을 파싱해 기준으로 삼도록 고쳤다(`1785c12`)

## 9. 5차 회귀와 세션 저하의 원인 규명 (2026-09-06)

| 케이스 | 유형 | 증상 |

UI-25는 6절 기준 3번(error vs failed)으로 바로 갈렸다. 픽스처에서 터졌으므로 본문이
실행되지 않았다.

UI-20과 UI-24는 실패 스크린샷이 판정했다. **두 장이 바이트 단위로 같았고(md5

없었다. 서로 다른 두 케이스가 서로 다른 시각에 찍었는데 픽셀이 동일하다는 것은 앱이
아니라 화면 쪽이 멈춰 있었다는 뜻이다.

### 9-2. 원인과 수정

8절에서 "WebDriverAgent 세션이 저하되는 것으로 보이며"라고 적고 부채로 넘겼던 것의
원인을 찾았다.

`DriverPool`은 `_alive()`가 참이면 세션을 계속 재사용하는데, `_alive()`는
`get_window_size()`만 본다. 이 호출은 **앱이 죽어 검은 화면만 남아도 성공한다.**
그래서 화면이 죽은 세션을 멀쩡한 것으로 판정해 계속 물려주었고, 실패는 테스트 본문의
"요소를 못 찾음"으로 둔갑했다. 원인을 앱에서 찾게 만드는 형태다.

두 가지를 더했다(`ce4d8c0`).

- `_expired()`: 20분 넘게 쓴 세션은 멀쩡해 보여도 버린다
- `_restore_foreground()`: 재사용 전에 앱이 화면 앞에 있는지 보고, 아니면 다시 띄운다

시간을 기준으로 삼은 이유는 그것이 실측에서 갈린 유일한 변수이기 때문이다. 실패한
케이스는 회차마다 달랐고(8/27 `InvalidSessionIdException`, 9/5 검은 화면) 증상도
달랐지만, 긴 실행이라는 조건은 두 번 다 같았다.
