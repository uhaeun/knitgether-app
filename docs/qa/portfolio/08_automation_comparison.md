# 08_UI 자동화 — XCUITest와 Appium 비교

> 같은 앱을 두 프레임워크로 짜고 비교한 기록이다. 2026-08-27 허브 리포지토리(`qa-portfolio/automation/`)에서 이관했다.
> 이 문서는 "왜 이 도구인가"를 다룬다. 내가 만든 스위트의 규모와 구성은 [13_automation_showcase](13_automation_showcase.md)가 담당한다.

> 대상: KnitGether (SwiftUI + NestJS, offline-first 동기화 iOS 앱)
> 기간: 2026-07 ~ 2026-08

## 1. 왜 두 개를 다 했나

**하나를 고르기 전에 둘 다 겪어보려고 했다.**

시작점은 도구의 사정거리 차이였다. XCUITest는 애플이 제공하고 iOS만 된다. Appium은 iOS와
안드로이드를 같은 러너로 다룬다. 모바일 QA로 넘어가는 입장에서 "안드로이드까지 가는 길"이
있는 쪽을 알아야 했다.

순서는 XCUITest가 먼저였다. DEF-15(카운터 하한) 회귀를 XCUITest로 못 박고, **같은 시나리오를
Appium으로 다시 짜서** 둘을 같은 조건에 놓았다. 그다음 Appium 쪽만 TC01~TC16, 78건까지
확장했다. 확장하면서 나온 문제들이 3절이고, 그게 실제 선택 근거가 됐다.

한 가지는 미리 적어둔다. **Appium의 iOS 드라이버는 내부적으로 XCUITest를 쓴다.** 둘 사이에
WebDriverAgent라는 앱이 하나 더 끼는 구조다. 즉 이 비교는 "다른 두 도구"가 아니라
**"같은 엔진을 직접 쓰느냐, 한 겹 위에서 쓰느냐"** 의 비교에 가깝다. 3절의 문제 다섯 개가
전부 그 한 겹에서 나온 것도 그래서다.

## 2. 규모

| 항목 | XCUITest | Appium |
|---|---|---|
| 테스트 함수 | 1건 (`testDEF15`) <sup>※</sup> | 78개 (TC01~TC16, 파일 18개) |
| 실행 케이스 | 1건 | 80건 (UI-04~06이 `parametrize` 3분기) |
| 페이지 오브젝트 | 3종 (Workspace / MyKnitting / CounterSheet) | 12종 |
| 지원 모듈 | 없음 | 6종 (simctl / netgate / seed / server_api / paths / texts) |
| 언어·러너 | Swift + XCTest | Python + pytest |

<sup>※</sup> `KnitGetherQAUITests.swift`, `…LaunchTests.swift` 의 3개 함수는 Xcode 기본 템플릿이라 세지 않았다.

동일 시나리오(DEF-15) 1건의 수행 시간은 두 도구가 같은 자릿수(30초대)였다. 측정 조건을 기록하지 않아 숫자는 싣지 않는다. 이 비교의 결론은 속도가 아니다.

## 3. 실제로 갈린 지점

### 세션을 몇 개 열 수 있나 — 설계를 바꾼 제약

Appium XCUITest 드라이버는 **같은 시뮬레이터에 두 세션을 동시에 두지 못한다.** 새 세션을 열면
앞 세션이 조용히 죽고, 나중에 그 드라이버를 다시 쓰는 케이스가 통째로 에러가 난다.

실측: 세션 **생성 7.0초** vs `terminate` + `activate` **재활성화 5.4초**. 케이스마다 세션을 새로 열면
78건짜리 스위트가 못 쓸 만큼 느려진다. 그래서 `DriverPool` 을 두고 **세션 종류(local / server /
offline / onboarding)가 바뀔 때만** 새로 연다.

XCUITest는 이 문제가 없다. 러너가 프로세스를 직접 잡고 돌려서 세션이라는 개념 자체가 없다.

### 타임아웃 — 기본값이 조용히 스위트를 깨뜨린다

두 개를 명시적으로 올려야 했다.

- `wdaLaunchTimeout` 180초 — 시뮬레이터 재부팅 직후가 굼떠 기본 60초를 넘기면 세션이 죽는다
- `newCommandTimeout` 3600초 — 서버 세션은 로컬 케이스가 도는 **30분 넘게 놀고 있게 된다.**
  기본 60초면 그동안 Appium이 세션을 정리해 버려서 뒤쪽 서버 케이스가 전부 에러가 난다

둘 다 "테스트가 틀려서" 나는 실패가 아니라 **도구 기본값 때문에 나는 실패**다. 원인이 테스트 코드
바깥에 있어서, 로그를 안 읽으면 앱 결함으로 오진하기 쉽다.

### 테스트 격리 — 문서에 있는 방법이 안 먹었다

앱이 제공하는 `KNITGETHER_LOCAL_CACHE_DIRECTORY` 는 **서버 모드 전용**이라 로컬 모드 케이스에는
효과가 없었다(`AppRepositoryContainer.swift:295-327`). 그래서 격리를 `xcrun simctl` 로
**컨테이너의 저장 파일 10종을 직접 지우고 다시 심는** 방식으로 바꿨다.

계정 케이스는 한 겹 더 필요했다. **토큰이 파일이 아니라 Keychain에 있어서** 저장 파일만 지우면
이전 계정의 로그인 상태가 다음 케이스로 넘어온다 → `reset_keychain()` 추가.

온보딩 케이스에도 함정이 있었다. 런치 인자로 `onboardingCompleted NO` 를 박으면 **인자 도메인이
앱이 저장한 값을 계속 덮어써서**, 온보딩을 끝내도 다시 온보딩으로 돌아온다. 초기화 전용
환경변수를 따로 만들어 해결했다.

### 어떤 빌드를 상대로 도는지 — 아무도 알려주지 않는다

DerivedData 폴더 이름의 해시는 **프로젝트 경로**에서 나온다. 레포를 옮기거나 폴더 이름을 바꾸면
새 폴더가 생기고 옛 폴더는 남는다. 후보를 알파벳순으로 고르면 **그 순간부터 낡은 빌드를 상대로
테스트가 도는데 경고가 하나도 없다.** 빌드 시각이 가장 늦은 것을 고르고, 후보가 둘 이상이면
어떤 걸 골랐는지 출력하게 했다.

### 네트워크 제어 — Appium만 할 수 있었던 것

TC16(오프라인 생성 후 복구 동기화)은 **완전 단절**이 필요하다. 서버 프로세스를 죽였다 살리면
다른 케이스가 쓰는 서버 상태까지 건드린다. 그래서 앱과 서버 사이에 **TCP 프록시(`netgate.py`)** 를
두고, 프록시만 닫아 서버는 살아 있는 채로 앱만 끊었다.

복구 검증에 한 줄을 더 넣었다 — 복구 직후 **프록시가 실제로 다시 통하는지** 먼저 확인한다.
이걸 안 보면 뒤따르는 실패가 앱 문제인지 관문 문제인지 가릴 수 없다.

## 4. 테스트가 진짜 잡는지 검증했다

**전건 PASS는 두 가지를 뜻할 수 있다. "제품이 정상"이거나, "테스트가 아무것도 안 보고 있거나."**
그 둘을 가르려고 두 가지를 만들었다.

**① `--empty-given` (음성 대조)** — Given 주입을 건너뛴다. 전제가 사라지면 테스트는 FAIL해야
정상이고, 그래도 PASS하는 테스트는 검출력이 없는 것이다. pytest 옵션 한 줄로 스위트 전체에 건다.

**② 결함 주입 6종 (`qa/mutation/`)** — 제품 코드에 고장을 하나씩 심고 빌드해서, 지정한 케이스만
정확히 빨개지는지 본다. 두 축을 함께 본다.

| 축 | 판정 |
|---|---|
| 기대 FAIL | 심은 고장을 잡아야 하는 케이스. 하나라도 PASS하면 **검출력 없음** |
| 통제군 | 그 고장과 무관해야 하는 케이스. 같이 터지면 **과잉 결합**, 분리 대상 |

주입 6종: `counter-lower-bound` / `delete-without-confirm` / `sort-reversed` /
`favorite-not-pinned` / `counter-not-saved` / `no-owner-filter`

`counter-lower-bound` 는 DEF-15를 그대로 재현한다. 여기서 걸린 게 있다 — 카운터 하한이
**뷰의 버튼 비활성화와 ViewModel의 0 하한, 두 층으로 이중 방어**되어 있어서 **한쪽만 무너뜨리면
결함이 드러나지 않는다.** 주입을 두 층 모두에 넣어야 케이스가 빨개졌다.
이중 방어는 제품에는 좋지만, **테스트 입장에서는 검출력을 가리는 요인**이다.

### 결과

| 대조 | 결과 |
|---|---|
| `--empty-given` 음성 대조 | 53건 FAIL. **검출력 없음 0건** |
| 결함 주입 6종 | **6종 전건 검출. 과잉 결합 0건** |

음성 대조에서 PASS로 남은 20건은 Given이 원래 비어 있는 케이스이거나 계정을 API로 만드는 서버
케이스였다. 이 스위치는 **파일 시딩만 끄기 때문에 서버 케이스 14건에는 아무 신호도 주지 못한다.**
이 층의 한계다.

실제 검출력 공백은 음성 대조가 아니라 결함 주입에서 **UI-64 한 건**으로 드러났다. Given을 파일
시딩으로 처리하는 바람에 제품의 저장 경로를 건너뛰고 있었다. 케이스가 틀린 게 아니라 **설계가
틀렸다.**

### 검증 도구가 세 번 거짓말을 했다

여기까지 오는 동안 결과를 세 번 잘못 읽었다. 세 번 다 "스위트에 검출력이 없다"는 방향이었다.

| # | 증상 | 실제 원인 | 조치 |
|---|---|---|---|
| 1 | 6종 전부 미검출 | 실패 스크린샷 훅이 `FAILED` 를 다른 줄로 밀어내 콘솔 파싱이 실패를 전부 놓침 | junit XML 파싱으로 교체 |
| 2 | `counter-lower-bound` 미검출 | 하한이 뷰·ViewModel 두 층 방어라 한쪽만 무너뜨리면 안 드러남 | 두 층 모두에 주입 |
| 3 | 서버 결함 미검출 | 3000 포트를 쥔 것은 `node dist/src/main.js` 인데 `pkill -f 'nest start'` 로는 안 잡힘. 새 서버가 `EADDRINUSE` 로 죽고 **원본이 계속 응답** | 프로세스 매칭 수정 + dist 재빌드 |

첫 결과를 그대로 믿었으면 **6종 전부 거짓 놓침**으로 보고할 뻔했다.
검출력을 재는 도구도 검증 대상이라는 게 이 절의 진짜 결론이다.

### 덤으로 알게 된 제품 사실

주입을 하다 보니 방어 층이 드러났다.

- **카운터 하한 — 2층.** 뷰의 버튼 비활성화 + ViewModel의 0 하한
- **서버 계정 격리 — 3층.** 목록 `where` 절, 자식 레코드 필터, 응답 변환의 소유자 확인이 각각
  독립으로 막는다. 단일 지점 결함으로는 뚫리지 않는다. 서버 로그의 `Skipped project` 기록이
  3층이 실제로 작동한 증거다

## 5. 결론 — 이 앱에는 어느 쪽인가

**단건 회귀는 XCUITest, 스위트는 Appium.** 이 앱 기준으로는 그렇다.

XCUITest는 시나리오 하나를 재현하는 데 붙는 비용이 거의 없다. DEF-15 회귀는 45줄이고
설정이랄 게 없다. 결함 하나를 잡아 회귀로 못 박는 용도라면 이쪽이 빠르다.

Appium을 고른 이유는 셋이다. 첫째는 **제어권**이다. 78건을 굴리려면 세션 재사용, 컨테이너 단위
격리, Keychain 초기화, 네트워크 단절이 전부 필요했고, 그 네 개가 모두 러너 바깥에서
`simctl`·프록시·환경변수로 이뤄진다. XCTest 안에서는 손이 닿지 않는 층이다.
둘째는 **모바일 QA에서 Appium이 표준**이라는 것. 이 스위트는 나 혼자 쓰고 끝낼 게 아니라
다른 팀에서도 읽힐 형태여야 했다. 셋째는 **Python이 익숙**해서다. 앞의 두 이유가 없었어도
Python으로 쓸 수 있는 쪽을 골랐을 것이다. 세 번째 이유를 숨기면 앞의 둘이 과장된다.

대신 대가가 있다 — 3절의 문제 다섯 개는 **전부 Appium 쪽에서만 생겼다.**

### 돌려본 뒤

이 결론은 80건을 돌리기 전에 세웠고, 돌린 뒤에도 바뀌지 않았다.
최고 기록 76 pass / 3 fail / 1 skip. 남은 3건은 케이스 문제가 아니라 SwiftUI 오버레이 메뉴
조작이 확률적으로 유실되는 문제고, 15회 시도 중 3회 실패로 실측해 뒀다. 50분 연속 실행에서
WebDriverAgent가 죽는 문제는 파일 단위로 나눠 돌리는 것으로 끝났다.
검출력은 음성 대조에서 검출력 없는 테스트 0건, 결함 주입 6종 전건 검출로 확인됐다.

지금 시점에서 도구를 바꿀 이유는 없다. 남은 숙제는 세 곳에 있다.
하나는 **앱 쪽** — 오버레이 메뉴 항목에 접근성 식별자를 붙이면 좌표 탭이 사라지고 20%짜리
유실도 같이 사라진다. 앱 코드 수정이라 오너 판단이 필요하다.
다른 하나는 **음성 대조의 사각** — 파일 시딩만 끄기 때문에 서버 케이스 14건에는 신호를
주지 못한다. 서버 시딩까지 끄는 스위치가 있어야 이 층이 완성된다.
마지막은 **프레임워크 쪽** — Appium의 `fullReset`은 앱 재설치가 아니라 `simctl erase`라
시뮬레이터를 통째로 지우고 WebDriverAgent까지 없앤다. 지금은 재시도에서 `full_reset=False`로
떨어뜨리는 우회로 버티고 있고, 온보딩 케이스 하나만 아직 fullReset을 쓴다. 앱만 지우고 다시 까는
방식으로 바꾸는 게 근본 수정이다. 이 문제를 잡는 데 진단이 두 번 바뀌었다(세션 복구 부재 →
권한 부여가 범인 → fullReset). 두 번째 오진은 코드 주석을 원인으로 믿어서 생겼다.

한 줄로: **XCUITest는 앱 안에서 보고, Appium은 앱 밖에서 본다.** 오프라인 동기화처럼
"앱과 서버 사이"가 시험 대상이면 밖에서 보는 도구가 필요했다.
