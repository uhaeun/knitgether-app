# 08_자동화 도구 비교

> 2026-09-18 재작성, 2026-09-19 원본 9/15 갱신분(3절 세션 생존 판정) 반영. 실측값과 결론은 원본(`docs/qa/portfolio/08`, 2026-09-15 갱신분까지)과 `docs/qa/appium_suite_worklog_2026-08-27.md`에서 옮겼다. 바뀐 것은 배치다. 도구가 갈린 지점을 선정 기준별로 묶고, 결론 뒤의 경과를 환경 부채 표로 모았다.

#### 이 문서의 위치

ISTQB 4.0 테스트 프로세스의 구현 활동 산출물이다. 구현 활동은 설계된 테스트를 실행할 수 있는 상태로 만드는 일이고, 자동화 스크립트 작성, 테스트 스위트 조립, 테스트 환경 구축과 준비 확인이 여기에 든다. 이 문서는 그중 도구 선정과 테스트 환경을 맡는다. 29119-3에는 도구 선정만 다루는 산출물이 없다. 여기서 세운 실행 환경의 조건(세션, 타임아웃, 격리, 빌드 특정, 네트워크 제어)이 테스트 환경 요구사항에 해당하고, 4절의 검출력 확인이 테스트 환경 준비 확인에 해당한다. 스위트의 구성과 규모는 13이 맡는다.

#### 1. 비교의 전제

대상은 KnitGether(SwiftUI 클라이언트, NestJS 서버, offline-first 동기화)이고 기간은 2026-07에서 2026-08이다.

하나를 고르기 전에 둘 다 겪어 보기로 했다. 출발점은 도구의 사정거리였다. XCUITest는 애플이 제공하고 iOS만 다룬다. Appium은 iOS와 안드로이드를 같은 러너로 다룬다. 모바일 QA로 넘어가는 입장에서 안드로이드까지 가는 길이 있는 쪽을 알아야 했다.

순서는 XCUITest가 먼저였다. DEF-15(카운터 하한) 회귀를 XCUITest로 고정하고, 같은 시나리오를 Appium으로 다시 짜서 둘을 같은 조건에 놓았다. 그다음 Appium 쪽만 TC01~TC16, 78건까지 확장했다. 확장하면서 나온 문제들이 3절이고, 그것이 실제 선택 근거가 됐다.

비교의 성격도 미리 적는다. Appium의 iOS 드라이버는 내부적으로 XCUITest를 쓰고, 둘 사이에 WebDriverAgent라는 앱이 하나 더 낀다. 이 비교는 서로 다른 두 도구의 비교가 아니다. **같은 엔진을 직접 쓰느냐, 한 겹 위에서 쓰느냐의 비교다.** 3절의 문제 여섯 개가 전부 그 한 겹에서 나온 것도 그래서다.

#### 2. 비교 대상의 규모

| 항목 | XCUITest | Appium |
| --- | --- | --- |
| 테스트 함수 | 1건 (`testDEF15`) | 78개 (TC01~TC16, 파일 18개) |
| 실행 케이스 | 1건 | 80건 (UI-04~06이 `parametrize` 3분기) |
| 페이지 오브젝트 | 3종 (Workspace, MyKnitting, CounterSheet) | 12종 |
| 지원 모듈 | 없음 | 6종 (simctl, netgate, seed, server_api, paths, texts) |
| 언어와 러너 | Swift, XCTest | Python, pytest |

`KnitGetherQAUITests.swift`와 `…LaunchTests.swift`의 함수 3개는 Xcode 기본 템플릿이라 세지 않았다.

Appium 규모는 2026-08-27(`f1d4a4c`) 소스 기준이다. 시트 78건에서 UI-04~06을 한 함수로 합치고 UI-42와 UI-51을 둘로 나눠 함수는 78개다. 이후 `test_def23_background_session.py` 2개와 `test_skill_cache_pruning.py` 1개가 더해져 2026-09-15(`1362481`) 기준 함수 81개, 실행 83건이다.

같은 시나리오(DEF-15) 1건의 수행 시간은 두 도구가 같은 자릿수(30초대)였다. 측정 조건을 기록하지 않아 숫자는 싣지 않는다. 이 비교의 결론은 속도에서 나오지 않는다.

#### 3. 선정 기준별로 갈린 지점

| 기준 | XCUITest | Appium | 환경 요구사항으로 남긴 것 |
| --- | --- | --- | --- |
| 세션 모델 | 러너가 프로세스를 직접 잡아 세션 개념이 없다 | 같은 시뮬레이터에 세션 둘을 동시에 두지 못한다 | `DriverPool`, 세션 종류가 바뀔 때만 새로 연다 |
| 세션 생존 판정 | 러너가 앱 프로세스 안에서 돌아 앱이 죽으면 러너도 죽는다 | "응답한다"와 "화면이 있다"가 다른 사건이다 | 세션 수명 20분 제한과 전면 복귀 확인 (6절 4번) |
| 타임아웃 기본값 | 해당 없음 | 기본값이 긴 스위트를 조용히 깨뜨린다 | `wdaLaunchTimeout` 180초, `newCommandTimeout` 3600초 |
| 테스트 격리 | 해당 없음 | 앱이 제공하는 격리 수단이 로컬 모드에 안 먹는다 | `simctl`로 저장 파일 10종 삭제와 재주입, Keychain 초기화 |
| 빌드 특정 | 해당 없음 | 어떤 빌드를 상대로 도는지 알려 주지 않는다 | 빌드 시각이 가장 늦은 DerivedData 선택과 출력 |
| 네트워크 제어 | 러너 안에서 손이 닿지 않는다 | 러너 밖 프록시로 완전 단절 가능 | TCP 프록시 `netgate.py` |

세션 모델. Appium XCUITest 드라이버는 새 세션을 열면 앞 세션이 조용히 죽고, 나중에 그 드라이버를 다시 쓰는 케이스가 통째로 에러가 난다. 실측으로 세션 생성은 7.0초, `terminate`와 `activate`로 재활성화하는 데는 5.4초가 걸렸다. 케이스마다 세션을 새로 열면 78건짜리 스위트가 못 쓸 만큼 느려진다. 그래서 `DriverPool`을 두고 세션 종류(local, server, offline, onboarding)가 바뀔 때만 새로 연다.

세션 생존 판정. 세션을 재사용하려면 그 세션이 멀쩡한지 물어야 한다. WebDriver에서 그것을 묻는 표준 방법은 `get_window_size()` 같은 가벼운 명령을 하나 보내 보는 것이고 `DriverPool`도 그렇게 했다. 그 호출은 앱이 죽어 검은 화면만 남아도 성공한다. WebDriverAgent가 살아 있으면 창 크기는 답할 수 있기 때문이다. 화면이 죽은 세션이 멀쩡한 것으로 판정돼 계속 재사용됐고 실패는 테스트 본문의 "요소를 못 찾음"으로 나타났다. 원인을 앱에서 찾게 만드는 형태다. 2026-09-05 전량 실행(69분)에서 세 건이 실패했고, 판정을 가른 것은 바이트 단위로 같은 검은 화면 스크린샷 두 장이었다. 요소를 못 찾은 것이 아니라 찾을 화면이 없었다. Appium은 앱 밖에서 프로토콜 너머로 보므로 두 사건을 따로 확인해야 한다. XCUITest는 앱이 죽으면 러너도 함께 죽어 멀쩡한 척할 방법이 없다. 5절이 말하는 "Appium은 앱 밖에서 본다"의 반대편이 여기에 있다. 밖에서 보기 때문에 앱과 서버 사이를 볼 수 있고, 같은 이유로 앱이 죽은 것을 모를 수 있다. 수정 경위는 6절 4번, 검증은 11의 8절에 있다.

타임아웃. 두 값을 명시적으로 올렸다. `wdaLaunchTimeout`은 시뮬레이터 재부팅 직후가 굼떠 기본 60초를 넘기면 세션이 죽어서 180초로 올렸다. `newCommandTimeout`은 3600초로 올렸다. 서버 세션은 로컬 케이스가 도는 30분 넘게 놀고 있게 된다. 기본 60초면 그동안 Appium이 세션을 정리해 뒤쪽 서버 케이스가 전부 에러가 난다. 둘 다 테스트가 틀려서 나는 실패가 아니라 도구 기본값 때문에 나는 실패다. 원인이 테스트 코드 바깥에 있어 로그를 읽지 않으면 앱 결함으로 오진하기 쉽다.

테스트 격리. 앱이 제공하는 `KNITGETHER_LOCAL_CACHE_DIRECTORY`는 서버 모드 전용이라 로컬 모드 케이스에는 효과가 없었다(`AppRepositoryContainer.swift:295-327`). 격리를 `xcrun simctl`로 컨테이너의 저장 파일 10종을 직접 지우고 다시 심는 방식으로 바꿨다. 계정 케이스는 한 겹이 더 필요했다. 토큰이 파일이 아니라 Keychain에 있어 저장 파일만 지우면 이전 계정의 로그인 상태가 다음 케이스로 넘어온다. 그래서 `reset_keychain()`을 추가했다. 온보딩 케이스에도 함정이 있었다. 런치 인자로 `onboardingCompleted NO`를 박으면 인자 도메인이 앱이 저장한 값을 계속 덮어써서 온보딩을 끝내도 다시 온보딩으로 돌아온다. 초기화 전용 환경변수를 따로 만들어 해결했다.

빌드 특정. DerivedData 폴더 이름의 해시는 프로젝트 경로에서 나온다. 레포를 옮기거나 폴더 이름을 바꾸면 새 폴더가 생기고 옛 폴더는 남는다. 후보를 알파벳순으로 고르면 그 순간부터 낡은 빌드를 상대로 테스트가 도는데 경고가 하나도 없다. 빌드 시각이 가장 늦은 것을 고르고, 후보가 둘 이상이면 무엇을 골랐는지 출력하게 했다.

네트워크 제어. TC16(오프라인 생성 후 복구 동기화)은 완전 단절이 필요하다. 서버 프로세스를 죽였다 살리면 다른 케이스가 쓰는 서버 상태까지 건드린다. 앱과 서버 사이에 TCP 프록시(`netgate.py`)를 두고 프록시만 닫아, 서버는 살아 있는 채로 앱만 끊었다. 복구 검증에는 한 단계를 더 넣었다. 복구 직후 프록시가 실제로 다시 통하는지를 먼저 확인한다. 이것을 보지 않으면 뒤따르는 실패가 앱 문제인지 관문 문제인지 가릴 수 없다.

#### 4. 테스트웨어의 검출력 확인

전건 PASS는 제품이 정상이라는 뜻일 수도 있고 테스트가 아무것도 보지 않는다는 뜻일 수도 있다. 둘을 가르려고 장치를 두 개 만들었다. 장치의 구현은 13의 4절에 있고 여기에는 판정 기준과 결과만 둔다.

| 장치 | 방법 | 판정 기준 |
| --- | --- | --- |
| `--empty-given` 음성 대조 | Given 주입을 건너뛰고 전체 실행 | 전제가 사라져도 PASS하면 검출력 없음 |
| 결함 주입 6종 (`qa/mutation/`) | 제품 코드에 고장을 하나씩 심고 빌드 | 기대 FAIL 케이스가 하나라도 PASS하면 검출력 없음. 무관한 통제군이 같이 터지면 과잉 결합 |

| 대조 | 결과 |
| --- | --- |
| `--empty-given` 음성 대조 | 53건 FAIL. 검출력 없음 0건 |
| 결함 주입 6종 | 6종 전건 검출. 과잉 결합 0건 |

음성 대조에서 PASS로 남은 20건은 Given이 원래 비어 있는 케이스이거나 계정을 API로 만드는 서버 케이스였다. 이 스위치는 파일 시딩만 끄기 때문에 `kg` 세션을 쓰지 않는 14건(서버 세션 13건, 온보딩 1건)에는 아무 신호도 주지 못한다. 이 층의 한계다.

실제 검출력 공백은 음성 대조가 아니라 결함 주입에서 UI-64 한 건으로 드러났다. Given을 파일 시딩으로 처리하는 바람에 제품의 저장 경로를 건너뛰고 있었다. 케이스가 틀린 것이 아니라 설계가 틀렸다.

`counter-lower-bound` 주입은 DEF-15를 그대로 재현한다. 카운터 하한이 뷰의 버튼 비활성화와 ViewModel의 0 하한, 두 층으로 막혀 있어 한쪽만 무너뜨리면 결함이 드러나지 않았다. 주입을 두 층 모두에 넣어야 케이스가 실패했다. 이중 방어는 제품에는 좋지만 테스트 입장에서는 검출력을 가리는 요인이다.

검출력을 재는 도구 자체도 세 번 잘못된 답을 냈고, 세 번 모두 "스위트에 검출력이 없다"는 방향이었다.

| # | 증상 | 실제 원인 | 조치 |
| --- | --- | --- | --- |
| 1 | 6종 전부 미검출 | 실패 스크린샷 훅이 `FAILED`를 다른 줄로 밀어내 콘솔 파싱이 실패를 전부 놓쳤다 | junit XML 파싱으로 교체 |
| 2 | `counter-lower-bound` 미검출 | 하한이 뷰와 ViewModel 두 층 방어라 한쪽만 무너뜨리면 드러나지 않았다 | 두 층 모두에 주입 |
| 3 | 서버 결함 미검출 | 3000 포트를 쥔 것은 `node dist/src/main.js`인데 `pkill -f 'nest start'`로는 잡히지 않았다. 새 서버가 `EADDRINUSE`로 죽고 원본이 계속 응답했다 | 프로세스 매칭 수정, dist 재빌드 |

첫 결과를 그대로 믿었으면 6종 전부 거짓 놓침으로 보고할 뻔했다. 검출력을 재는 도구도 검증 대상이다.

주입 과정에서 제품의 방어 층도 드러났다. 카운터 하한은 뷰의 버튼 비활성화와 ViewModel의 0 하한으로 2층이다. 서버 계정 격리는 목록 `where` 절, 자식 레코드 필터, 응답 변환의 소유자 확인이 각각 독립으로 막는 3층이고, 단일 지점 결함으로는 뚫리지 않는다. 서버 로그의 `Skipped project` 기록이 3층이 실제로 작동한 증거다.

#### 5. 선정 결론

이 앱 기준으로 **단건 회귀는 XCUITest, 스위트는 Appium**으로 정했다.

XCUITest는 시나리오 하나를 재현하는 데 붙는 비용이 거의 없다. DEF-15 회귀는 45줄이고 설정이랄 것이 없다. 결함 하나를 잡아 회귀로 고정하는 용도라면 이쪽이 빠르다.

Appium을 고른 이유는 셋이다.

| 순서 | 이유 | 내용 |
| --- | --- | --- |
| 1 | 제어권 | 78건을 굴리려면 세션 재사용, 컨테이너 단위 격리, Keychain 초기화, 네트워크 단절이 전부 필요했다. 넷 모두 러너 바깥에서 `simctl`, 프록시, 환경변수로 이뤄진다. XCTest 안에서는 손이 닿지 않는 층이다 |
| 2 | 표준성 | 모바일 QA에서 Appium이 표준이다. 이 스위트는 혼자 쓰고 끝낼 것이 아니라 다른 팀에서도 읽힐 형태여야 했다 |
| 3 | 언어 숙련 | Python이 익숙하다. 앞의 두 이유가 없었어도 Python으로 쓸 수 있는 쪽을 골랐을 것이다. 이 이유를 숨기면 앞의 둘이 과장된다 |

대가도 있다. 3절의 문제 여섯 개는 전부 Appium 쪽에서만 생겼다.

XCUITest는 앱 안에서 보고, Appium은 앱 밖에서 본다. 오프라인 동기화처럼 앱과 서버 사이가 시험 대상이면 밖에서 보는 도구가 필요했다. 같은 이유로 앱이 죽은 것을 모를 수 있다는 것이 밖에서 보는 대가다(3절 세션 생존 판정).

#### 6. 결론 이후의 실행과 환경 부채

결론은 80건을 돌리기 전에 세웠고 돌린 뒤에도 바뀌지 않았다. 통합 실행 최고 기록은 76 pass, 3 fail, 1 skip이었다. 남은 3건은 SwiftUI 오버레이 메뉴 조작이 확률적으로 유실되는 문제였고 15회 시도 중 3회 실패로 실측했다. 50분 연속 실행에서 WebDriverAgent가 죽는 문제는 파일 단위로 나눠 돌리는 것으로 넘겼다. 오버레이 문제를 고친 뒤 2026-08-29 분할 실행 3회(정방향 2회, 역순 1회)는 세 회차 모두 79 passed, 1 skipped, 0 failed였다(appium 워크로그 2절, 5절).

지금 시점에서 도구를 바꿀 이유는 없다. 결론 당시 남긴 숙제 네 개의 경과다.

| # | 부채 | 층 | 경과 |
| --- | --- | --- | --- |
| 1 | 오버레이 메뉴 항목의 좌표 탭과 20% 유실 | 앱 | 접근성 식별자 추가(04의 테스트 가능성 예외)를 올려 오너 승인까지 받았으나 쓰지 않았다. 원인이 식별자 부재가 아니라 드라이버 바인딩 설정과 좌표 계산이었고, 자동화 코드 수정(`a784be7`, `04095bd`)만으로 해소됐다. `bf2b001` 코드 동결 원칙이 유지된다 (appium 워크로그 5절) |
| 2 | 음성 대조의 사각 | 테스트웨어 | 파일 시딩만 끄므로 서버 세션 13건과 온보딩 1건에는 신호를 주지 못한다. 서버 시딩까지 끄는 스위치가 있어야 이 층이 완성된다. 미해소 |
| 3 | `fullReset` | 프레임워크 | Appium의 `fullReset`은 앱 재설치가 아니라 `simctl erase`라 시뮬레이터를 통째로 지우고 WebDriverAgent까지 없앤다. 재시도에서 `full_reset=False`로 떨어뜨리는 우회로 버티고, 온보딩 케이스 하나만 아직 fullReset을 쓴다. 앱만 지우고 다시 까는 방식이 근본 수정이다 |
| 4 | 장시간 실행의 세션 저하 | 러너 | 2026-09-06 `ce4d8c0`으로 닫았다. 아래에 경위를 둔다 |

3번은 진단이 두 번 바뀌었다(세션 복구 부재, 권한 부여가 범인, fullReset 순). 두 번째 오진은 코드 주석을 원인으로 믿어서 생겼다. `full_reset=False` 우회에는 파생 부채가 하나 따라왔다. 이 설정에서는 스위트가 앱을 설치하지 않아 시뮬레이터에 예전에 설치된 바이너리가 계속 검증 대상이 됐다. 9/3에 시작한 수정 사이클에서 로그인 케이스(UI-08) 실패를 추적하다 드러났고, 최신 빌드를 `simctl install`한 뒤에만 통과했다(fix_cycle 워크로그 4절). 이후 스위트가 검증할 바이너리를 특정하게 바꿨다(`a1dcc18`, 9/5). 같은 날 돌린 4차 회귀가 앱 설치가 보장된 첫 회차다(fix_cycle 워크로그 5-5절).

4번 세션 저하의 경위다. 증상은 두 번 나왔다.

| 날짜 | 실행 | 실패 | 격리 재실행 | 실패 형태 |
| --- | --- | --- | --- | --- |
| 9/1 | 78건, 55분 | 14건 | 13건 통과 | `InvalidSessionIdException`, `socket hang up` |
| 9/5 | 69분 | 3건 | 10건 통과 | `NoSuchElement`에서 `Timeout` |

두 회차 모두 앱 결함은 0건인데 실패 형태는 서로 달랐다. 원인은 `DriverPool`의 생존 판정이었다. `_alive()`가 `get_window_size()`만 보는데, 이 호출은 앱이 죽어 검은 화면만 남아도 성공한다. 그래서 화면이 죽은 세션을 멀쩡한 것으로 판정해 계속 물려주었다. 실패가 테스트 본문의 "요소를 못 찾음"으로 둔갑하니 원인을 앱에서 찾게 된다. 9/5 실패 스크린샷 두 장이 바이트 단위로 같고 완전히 검었던 것이 결정적 증거였다.

수정은 두 가지다. 20분 넘게 쓴 세션은 멀쩡해 보여도 버리고(`_expired`), 재사용 전에 앱이 화면 앞에 있는지 확인해 아니면 다시 띄운다(`_restore_foreground`). 시간을 기준으로 삼은 이유는 그것이 두 회차에서 갈린 유일한 공통 변수이기 때문이다. 실패한 케이스와 증상은 달랐지만 긴 실행이라는 조건은 같았다.

비용은 재활용 1회당 약 12초다. 69분 실행이면 3회로 36초다. 스위트를 쪼개거나 CI에서 분할하는 방향도 검토했다. 원인이 세션 수명이라면 쪼개는 것은 같은 효과를 더 비싸게 얻는 방법이라 택하지 않았다. 판정과 검증은 11의 8절에 있다.
