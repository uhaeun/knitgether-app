# 1. 프로젝트 개요와 QA 목표 - 2026-07-19

## 프로젝트 소개

KnitGether는 뜨개 작업을 하는 사용자가 프로젝트, 도안, 실/바늘, 작업 시간, 단수, 게이지 기록을 한 곳에서 관리하는 iOS 앱이다. 앱은 SwiftUI 기반 클라이언트와 NestJS/Prisma 서버로 구성되어 있고, API 모드에서는 로컬 JSON cache와 서버 동기화를 함께 사용하는 offline-first 구조를 목표로 한다. 핵심 품질 기준은 사용자가 저장한 뜨개 데이터가 앱 재실행, 서버 장애, 계정 전환 상황에서도 사라지거나 섞이지 않는 것이다.

## 내 역할

기획, iOS 앱 구현, 서버 구현, 테스트 자동화, QA 문서화를 모두 직접 수행했다. 이 포트폴리오에서는 개발자 역할보다 QA 관점에 집중한다. DB QA 경험을 살려 UI에서 발생한 액션이 API 요청과 DB 모델 상태까지 올바르게 이어지는지 확인하고, 앱 QA에서 중요한 모바일 화면 흐름, 네트워크 장애, 오프라인 cache, 재실행 후 데이터 유지까지 검증 범위를 넓힌다.

## 이 QA의 목적

직접 개발한 앱을 실무 QA 프로세스에 맞춰 검증한다. 흐름은 요구사항/화면 정의 -> 리스크 기반 테스트 계획 -> TC 설계 -> API/DB 검증 -> 수동 탐색 QA -> XCUITest POM 자동화 -> 결함 리포트 -> 릴리즈 Go/No-Go 판단 순서로 진행한다. 목표는 단순히 테스트를 통과시키는 것이 아니라, 사용자가 실제로 앱을 쓰는 과정에서 데이터 유실과 동기화 실패를 발견하고 재현 가능한 결함으로 관리하는 것이다.

## 테스트 목표 (측정 가능하게)

- [ ] P0 기능 TC 실행률 100%
- [ ] 발견 결함 전건 GitHub Issues 리포트화 (severity 부여)
- [ ] 대표 결함 ≥ 3건: 재현 증거 + 원인 추적 + 재검증 기록
- [ ] API 핵심 엔드포인트 검증 + DB 상태 확인
- [ ] XCUITest 자동화 스모크 우선 대상 5개 흐름
- [ ] 릴리즈 Go/No-Go 판정 리포트 1건

## 완료 기준

- 포트폴리오 문서가 실제 실행 결과와 맞아야 한다.
- 테스트 케이스에는 우선순위, 설계 기법, 기대 UI/API/DB 결과가 있어야 한다.
- P0 실패가 남아 있으면 릴리즈 판단은 No-Go로 처리한다.
- 자동화되지 않은 영역은 수동 QA 또는 알려진 제한으로 명시한다.
- 개인 토큰, 실제 비밀번호, 민감한 계정 정보는 문서와 로그에서 제거한다.
