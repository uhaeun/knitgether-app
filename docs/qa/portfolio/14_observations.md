# 14_관찰과 개선 제안

> 2026-09-18 재작성, 2026-09-19 원본 9/15 갱신분(OBS-4-01 승격) 반영. 관찰 분류, OBS ID, 승격 이력, 오탐 정정은 원본(`docs/qa/portfolio/14`)의 판정을 그대로 옮겼다. 바뀐 것은 배치다. 관찰 대장을 뒤로 보내고, 그 관찰에서 나온 교훈을 "한계와 그 뒤의 결정" 형식으로 앞에 세웠다. 2절의 교훈 가운데 원본 14에 없던 두 줄은 `docs/qa/fix_cycle_worklog_2026-09-03.md` 5-7절과 원본 10의 7-3절에서 가져왔다.

#### 이 문서의 위치

ISTQB 4.0 테스트 프로세스의 완료 활동 산출물이다. 완료 활동은 종료 기준 충족을 확인하고 잔존 결함을 정리한 뒤, 다음 사이클에 넘길 교훈(lessons learned)을 남기는 일이다. 이 문서는 그중 교훈을 맡는다. 29119-3에서는 테스트 완료 보고서의 교훈 절에 해당한다. 종료 판정과 잔존 리스크는 15, 결함 자체는 10이 맡는다.

원천은 06(1차 39건), 구글시트 `KnitGether 관찰과 개선 제안 대장 (3차, 자동화 준비)` (2026-08-23), 02 문서 이력이다. 1차 39건의 시각과 근거 원문은 06 부록과 노션 관찰 로그가 정본이다.

#### 1. 관찰과 결함을 나누는 기준

테스트 중 눈에 띈 것을 전부 결함이라 부르지 않는다. 02에 판정 기준이 있어야 결함이고, 없으면 명세 공백이다. 이 구분이 무너지면 테스터의 취향이 결함으로 올라가고 리포트 신뢰도가 떨어진다.

| 분류 | 정의 | 처리 |
| --- | --- | --- |
| 결함 | 02에 SPEC이 있고 코드가 그와 어긋남 | 10 결함 카탈로그로 |
| 명세 공백 관찰 | 02에 판정 기준이 없어 옳고 그름을 말할 수 없음 | 기록만. 스펙 결정 후 재판정 |
| UX 개선 제안 | 동작은 명세대로이나 사용성이 아쉬움 | 기획 백로그. 결함 아님 |
| 기능 부재 | 기대한 기능 자체가 없음 | 기획 판단 후 스펙 신설 여부 결정 |

보류가 판단 회피가 아니라는 근거는 3절의 승격 이력이다. 1차 관찰에서 보류한 것 중 8건이 실제로 스펙이 됐고, 그중 4건은 결함으로 확정됐다.

2. 무제한 허용의 리스크를 나열했다. 표시 붕괴, 동기화 비용, 악용, 연계 시스템 영향
3. 기존 데이터를 psql로 실측했다. 30자 초과가 없어 마이그레이션이 필요 없었다
4. 1~30자로 스펙을 신설하고 클라이언트 폼과 서버 검증 2층에 적용하기로 정했다
5. UI-17을 FAIL 예상으로 설계했다. 구현 전이므로 실패하는 것이 맞다
6. 구현은 `834876f` (8/26)이다. 8/30 회귀 재판정에서 UI-17을 포함한 UI 회귀 6건이 전건 PASS했다(12의 4절)

케이스를 쓰는 행위가 명세 공백을 드러내고, 공백이 스펙이 되고, 스펙이 결함 판정 기준이 됐다. 테스트 설계가 검출 활동이라는 것을 보여주는 경로다.
