## 0. 관찰을 결함과 나누는 기준

테스트 중 눈에 띈 것을 전부 결함이라 부르지 않는다. 02에 판정 기준이 있어야 결함이고, 없으면 명세 공백이다. 이 구분이 무너지면 "내 취향과 다른 것"이 결함으로 올라가고 리포트 신뢰도가 떨어진다.

| 분류 | 정의 | 처리 |
| --- | --- | --- |
| 결함 | 02에 SPEC이 있고 코드가 그와 어긋남 | 10 결함 카탈로그로 |
| 명세 공백 관찰 | 02에 판정 기준이 없어 옳고 그름을 말할 수 없음 | 기록만. 스펙 결정 후 재판정 |
| UX 개선 제안 | 동작은 명세대로이나 사용성이 아쉬움 | 기획 백로그. 결함 아님 |
| 기능 부재 | 기대한 기능 자체가 없음 | 기획 판단 후 스펙 신설 여부 결정 |

**결함으로 단정하지 않고 보류한 것이 이 문서의 내용이다.** 보류가 판단 회피가 아니라는 근거는 3절의 승격 이력이다. 보류한 것 중 8건이 실제로 스펙이 됐고, 그중 4건은 결함으로 확정됐다.

Appium 케이스를 설계하면서 나온 것이다. 케이스를 쓰려면 기대 결과를 문장으로 확정해야 하는데, 그 과정에서 명세가 없는 지점이 드러났다.

**1차 관찰 39건 중 명세 공백 승격이 4건, 기능 부재 승격이 4건이다.** 나머지는 UX 제안이나 기획 백로그로 남았다.

### SPEC-PROJ-01의 발견 경위 (승격의 대표 사례)

UI-17(프로젝트 이름 길이 경계값) 케이스를 설계하려는데 기대 결과를 쓸 수가 없었다. 상한이 몇 자인지 아무 데도 없었기 때문이다.

1. 코드 3층을 확인했다 — 폼 `canSave`, 서버 DTO, 스키마. **셋 다 길이 제한이 없었다**
2. 무제한 허용의 리스크를 나열했다 — 표시 붕괴, 동기화 비용, 악용, 연계 시스템 영향
3. 기존 데이터를 실측했다 — psql로 확인한 결과 30자 초과 없음. 마이그레이션 불요
4. 1~30자로 스펙을 신설하고 클라이언트 폼과 서버 검증 2층에 적용하기로 정했다
5. UI-17을 **FAIL 예상**으로 설계했다. 구현 전이므로 실패하는 것이 맞다
6. 구현 `834876f` (8/26). 회귀 재판정 대기

케이스를 쓰는 행위가 명세 공백을 드러내고, 공백이 스펙이 되고, 스펙이 결함 판정 기준이 됐다. 테스트 설계가 검출 활동이라는 것을 보여주는 경로다.

## 4. 오탐 정정

QA의 정직성을 위해 틀린 판정도 남긴다.

**"타입 검증 자동 변환 우회" (결함 33 후보) — 재현 실패**

8/8 관찰에서 숫자 필드에 문자열을 보냈는데 200이 떨어져 서버 검증이 뚫린 것으로 봤다. 다시 확인하니 Charles로 본문을 편집할 때 따옴표가 남아 문자열로 전송된 것이었다. `curl`로 순수 숫자를 보내니 400이 정상 반환됐다. **서버 검증은 정상이었고 도구 사용이 틀렸다.** 수정 불필요.

**DEF-16 초기 오판**

로그인 후 홈 로드 실패를 처음에는 테스트 환경(다중 서버) 탓으로 판단하고 닫았다. 재발 보고를 받고 재수사해 서버 계측으로 원인을 특정했다. 경합 조건이라 간헐 재현이었던 것이 오판의 원인이다. 10의 대장에 이 이력을 남겼다.
