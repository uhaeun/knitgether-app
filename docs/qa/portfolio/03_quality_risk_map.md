#### 한눈에

- 이 문서가 보여주는 것: 영향도와 발생가능성 기반의 리스크 정량화, 실패의 뿌리가 같은 것을 묶는 결함 클래스 판단
- 세 줄 요약: 02의 실측 결과를 실패의 근본 원인이 같은 결함 클래스 7개로 묶고, 영향도(01 치명도)와 발생가능성(3단계)으로 등급화했다. P1 2클래스는 데이터 유실과 계정 격리에 걸려 있으며 악조건 심층 시나리오로 검증한다. 등급이 05의 설계 순서와 06의 투입 순서를 결정한다.

#### 평가 방법

리스크 행의 단위는 개별 SPEC이 아니라 결함 클래스다. 실패의 뿌리가 같은 SPEC들을 한 행으로 묶고 관련 SPEC ID를 병기한다. 클래스 안에서 SPEC별 발생가능성이 다르면 클래스에는 가장 높은 값을 적고 차이는 근거에서 구분한다.

영향도는 01의 치명도 순위(1위 데이터 유실 ~ 5위 도안 열람 불가)를 그대로 쓴다. 발생가능성은 3단계다.

- 상: 설계된 주 사용 흐름 안에서 발생 경로가 열려 있다. 오프라인 수정 후 복귀는 offline-first 앱의 주 흐름이므로 포함된다.
- 중: 특정 조건의 조합(서버 거부, 계정 전환, 타이밍 경합)이 필요하나 구조적으로 막혀 있지 않다.
- 하: 비정상 상태나 외부 개입(서버 데이터 직접 조작 등)이 있어야 발생한다.

등급은 P1(악조건 심층 시나리오 필수), P2(표준 TC와 실측 대상), P3(회귀 확인 수준)이다. 발생가능성이 미상(미대조)인 클래스는 실측 확정 전까지 보수적으로 P2 이상을 유지한다.

| RC-07 | FK 제약조건 부재 참조의 죽은 ID 표시 | LINK-03, LINK-04 | 2위 (정합성) | 하 | P3 | 코드상 방어(교집합 필터, 스냅샷 대체)가 존재해 일치로 판정된 클래스. 회귀 확인 수준으로 검증한다 |
| RC-08 | 연결 해제 시 서버 파일 고아화 | PAT-04 후단 | 치명도 축 밖 (운영 리스크) | 상 (해제 시 상시) | 별도 관리 | 사용자 데이터 훼손이 없어 치명도 축에 올리지 않는다. 07에서 psql과 server/storage 대조로 실증하고, 개선 권고는 뿌리가 같은(하드 삭제) RC-01과 묶는다 |

치명도 5위(도안 열람 불가)는 대응 리스크 클래스가 없다. 관련 SPEC(PAT-02 복사본 로컬 캐시)이 일치로 판정돼 구조적 위험 경로가 확인되지 않았기 때문이며, CUJ 실행에서 회귀 수준으로만 확인한다.

#### 등급별 검증 계획

- P1 (RC-01, RC-02): 06의 악조건 심층 시나리오로 검증한다. 두 기기 오프라인 충돌, Charles 4xx 주입, 계정 전환이며 전건 psql로 서버 상태를 실측한다. 이 2클래스의 판정 확정 없이는 QA 사이클을 종료하지 않는다.
- P2 (RC-03, RC-04, RC-05): 05의 표준 TC로 설계하고 06에서 실행한다. RC-04는 psql 주입, RC-05는 CUJ-1 실행과 등록 경로 대조를 같은 세션으로 묶어 실측한다.
- P3 (RC-06, RC-07): CUJ와 표준 TC 실행 중 함께 확인하는 회귀 수준으로 다룬다. 별도 심층 시나리오는 배정하지 않는다.
- RC-08: 07에서 실증한다.
