# 03_품질리스크맵

> 2026-09-18 재작성. 결함 클래스 8개의 영향도, 발생가능성, 등급은 원본(`docs/qa/portfolio/03`, v1.0 판정, v1.1 표기 정리)의 판정을 그대로 옮겼다. 8개는 치명도 축 안 7개와 축 밖 운영 리스크 1개(RC-08)다. 바뀐 것은 배치다. 리스크 레지스터 형식으로 식별, 평가, 대응을 나누고 실행 후 대조 절을 붙였다. 대조 절의 숫자는 12와 10에서 옮겼다.

#### 이 문서의 위치

ISTQB 4.0 분석 활동에서 테스트 조건에 우선순위를 매기는 부분이다. ISTQB는 리스크 기반 테스팅을 리스크 분석(식별과 평가)과 리스크 통제(완화와 모니터링)로 나누고, 리스크 수준을 발생가능성과 영향도의 조합으로 정한다. 이 문서는 29119-3 테스트 계획서가 참조하는 리스크 레지스터다. 다루는 것은 제품 리스크뿐이다. 영향도 축은 01의 치명도 순위, 리스크가 걸리는 테스트 조건은 02의 SPEC이다. 04가 이 등급으로 테스트의 순서와 깊이를 정한다.

#### 1. 식별 단위

레지스터의 행은 개별 SPEC이 아니라 결함 클래스다. 실패의 뿌리가 같은 SPEC을 한 행으로 묶고 관련 SPEC ID를 병기한다. 클래스 안에서 SPEC별 발생가능성이 다르면 클래스에는 가장 높은 값을 적고 차이는 근거 열에서 구분한다.

#### 2. 평가 척도

영향도는 01의 치명도 순위를 그대로 쓴다. 1위 데이터 유실, 2위 연결 정합성, 3위 계정 간 노출, 4위 카운트 부정확, 5위 도안 열람 불가다.

발생가능성은 3단계다.

| 단계 | 기준 |
| --- | --- |
| 상 | 설계된 주 사용 흐름 안에서 발생 경로가 열려 있다. offline-first 앱에서 오프라인 수정 후 복귀는 주 흐름이므로 여기 든다 |
| 중 | 서버 거부, 계정 전환, 타이밍 경합 같은 조건의 조합이 필요하지만 구조적으로 막혀 있지 않다 |
| 하 | 서버 데이터 직접 조작 같은 비정상 상태나 외부 개입이 있어야 발생한다 |

두 축을 합친 등급이 리스크 수준이다. P1은 악조건 심층 시나리오 필수, P2는 표준 TC와 실측 대상, P3는 회귀 확인 수준이다. 발생가능성이 미상(미대조)인 클래스는 실측으로 확정하기 전까지 보수적으로 P2 이상을 유지한다.

#### 3. 리스크 레지스터

| ID | 결함 클래스 | 관련 SPEC | 영향도 | 발생가능성 | 등급 | 평가 근거 |
| --- | --- | --- | --- | --- | --- | --- |
| RC-01 | 동기화 경로의 무이력 데이터 유실 | SYNC-08, 09, 10, 11 | 1위 | 상 | P1 | 뿌리는 서버의 하드 삭제와 클라이언트의 무통보 폐기다. SYNC-08은 노출면이 넓고(폼 수정, 도안 연결과 해제, 드로잉, 메모, 완성 처리) 다중 기기 오프라인 복귀와 단일 기기 재시도 경합 두 경로가 코드로 확인돼 상이다. SYNC-09와 10은 서버 거부가 전제라 중이지만 SYNC-09는 서버 사본이 없어 복구가 불가능하다 |
| RC-02 | 계정 간 데이터 격리 실패 | AUTH-04, 05, 06 | 3위 | 중 | P1 | 뿌리는 계정 무구분 단일 캐시 파일이다(AUTH-06 불일치 확정). 전환이 일어나면 노출(AUTH-04)은 구조상 확실하다. 교차 업로드(AUTH-05)는 pending 잔존이 겹쳐야 해 조건이 하나 더 붙는다. AUTH-05가 재현되면 노출을 넘어 오염이므로 심각도를 올린다 |
| RC-03 | 참조 항목의 표시 정합성 붕괴 | LINK-05 | 2위 | 상 | P2 | 뿌리는 표시 기준(원본 최신값 대 스냅샷)이 화면마다 다른 것이다. 창고 원본 수정은 일상 조작이라 상이다. 데이터 파손은 아니지만 사용자는 정합성 붕괴로 인식한다 |
| RC-04 | 클라이언트와 서버의 데이터 계약 불일치 | CNT-03 | 5위 준용 | 하 | P2 | 뿌리는 스키마 계약 불일치(서버 옵셔널 대 클라 필수)다. 정상 클라이언트 경로로는 발생하지 않아 하다. 발생하면 반경이 목록 전체(배열 단위 디코딩)일 우려가 코드로 확인됐다. 목록 전체 실패가 실측되면 영향도를 1위 준용으로 올린다는 상향 조건을 달았다. psql 주입으로 실측한다 |
| RC-05 | 생성 경로 간 결과 불일치 | PAT-01 후단, CUJ-1 경로 동등성 | 2위 | 미상 | P2 | 같은 목표 상태로 가는 복수 경로(도안 등록 입구 5개, 프로젝트 생성 1a와 1b)가 같은 결과를 보장하는지 확인되지 않았다. 06에서 CUJ-1 실행과 등록 경로 대조를 같은 세션으로 실측해 확정한다 |
| RC-06 | 삭제 중간 상태의 원격 잔존 | SYNC-06, 07 | 1위 하위 (지연, 유실 아님) | 하 | P3 | pending 재개가 조회 시점에만 일어나 삭제 후 앱을 쓰지 않는 동안 원격에 남는다. 유실이 아니라 지연이고 재개 메커니즘은 코드로 확인됐다 |
| RC-07 | FK 제약조건 부재 참조의 죽은 ID 표시 | LINK-03, 04 | 2위 | 하 | P3 | 코드에 방어(교집합 필터, 스냅샷 대체)가 있어 일치로 판정된 클래스다 |
| RC-08 | 연결 해제 시 서버 파일 고아화 | PAT-04 후단 | 치명도 축 밖 (운영 리스크) | 상 (해제 시 상시) | 별도 관리 | 사용자 데이터 훼손이 없어 치명도 축에 올리지 않는다. 뿌리가 RC-01과 같은 하드 삭제라 개선 권고는 RC-01과 묶는다 |

치명도 4위(카운트 부정확)와 5위(도안 열람 불가)는 대응 클래스가 없다. 5위의 관련 SPEC인 PAT-02(복사본 로컬 캐시)가 일치로 판정돼 구조적 위험 경로가 확인되지 않았기 때문이다. 5위는 CUJ 실행에서 회귀 수준으로만 확인한다.

#### 4. 리스크 대응

테스트로 리스크를 줄이는 방법을 등급별로 정했다. 05의 커버 열은 05의 RTM 집계에서 옮겼다.

| 등급 | 클래스 | 대응 | 05 커버 |
| --- | --- | --- | --- |
| P1 | RC-01, RC-02 | 06의 악조건 심층 시나리오. 두 기기 오프라인 충돌, Charles 4xx 주입, 계정 전환을 만들고 전건 psql로 서버 상태를 실측한다 | RC-01 4TC, RC-02 2TC |
| P2 | RC-03, RC-04, RC-05 | 05의 표준 TC로 설계해 06에서 실행한다. RC-04는 psql 주입, RC-05는 CUJ-1 실행과 등록 경로 대조를 한 세션으로 묶는다 | RC-03 1TC와 CUJ 관찰, RC-04 1TC, RC-05 CUJ-1 |
| P3 | RC-06, RC-07 | CUJ와 표준 TC 실행 중 함께 확인한다. 별도 심층 시나리오는 배정하지 않는다 | RC-06 1TC, RC-07 TC-CUJ3-01(연결의 생애주기, 정합성 심층)과 TC-LINK03-01 경유 |
| 별도 | RC-08 | 07에서 psql과 server/storage 대조로 실증한다 | 07 이관 |

**P1 2클래스의 판정 확정 없이는 QA 사이클을 종료하지 않는다.** 이 조건은 04의 종료 기준 첫 항목이 된다.

#### 5. 모니터링: 실행 후 대조

1차 실행 뒤 발견 결함을 레지스터에 다시 대 봤다. 12의 4절(2026-08-30, 22건) 분포다.

나머지는 클래스 밖 계열로 각 1건이다. 캐시 갱신 전략(DEF-11), 세션 정합성(DEF-16), UX 개편 유발 회귀(DEF-15), 검증 공백(DEF-20), 스펙 신설(SPEC-PROJ-01)이다. 12의 분포표에 RC-05와 RC-06 행은 없다.

P1 두 클래스가 22건 중 10건, 45%다. 등급이 실제 발견 분포와 맞았고 리스크 기반 설계가 헛돌지 않았다는 근거로 12가 인용한다.

대조에서 레지스터와 어긋난 곳이 둘 있다.

- DEF-10(도안 교체 시 확인창 없이 드로잉 삭제)은 처음 RC-03으로 분류했다. 8/29에 경고 없는 드로잉 소멸이 데이터 유실이라고 보고 RC-01로 재분류했다(10의 3절).
- RC-04는 등급 P2인데 DEF-08(RowCounter 없는 프로젝트가 목록 전체 500)이 Critical로 판정됐다. 레지스터에 적어 둔 상향 조건(목록 전체 실패)이 실측으로 확인된 경우다. 12는 이 차이를 축의 차이로 설명한다. 클래스는 어떤 정합성이 깨졌는지를 보고 심각도는 결과가 얼마나 나쁜지를 본다.

RC-08의 DEF-13과 14는 8/29 심각도 판정에서 축 제외로 두었다. 03의 운영 리스크 분리를 대장에서 뒤집지 않기 위해서다. 8/31 이후 추가된 결함(DEF-22~29)의 클래스는 10의 대장에 있고, RC-02 3건은 2026-09-06 `9ba16c9`로 수정됐다(15의 4절).
