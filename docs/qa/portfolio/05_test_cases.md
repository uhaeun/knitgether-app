## TC 상세
공통 사전 조건: 기준 커밋 bf2b001 빌드. PostgreSQL은 Docker Compose로 기동하고 NestJS API는 호스트에서 `npm run start:dev`로 실행하며, DB는 사이클 시작 시 초기화한다. API만 중단할 때는 NestJS 프로세스를 `Ctrl+C`로 종료하고 PostgreSQL 컨테이너는 유지한다. psql 접속은 `docker exec -it <postgres 컨테이너> psql -U <user> -d <db>` 기준. 로컬 파일 경로는 `xcrun simctl get_app_container booted <번들ID> data` 결과 아래 `Library/Application Support/KnitGether/projects.json`. `projects.json`의 `syncStatus` rawValue는 `Local Only`, `Pending Upload`, `Synced`, `Pending Delete` 문자열이다. Charles 기반 TC 실행 전 Local Simulator 스킴의 base URL을 `http://<맥 LAN IP>:3000/api/v1`로 설정하고 Charles GUI에서 요청 캡처를 1회 확인한다. 통신은 HTTP 평문이므로 SSL Proxying 설정은 필요 없다. Wi-Fi 재연결 또는 네트워크 변경 후에는 `ipconfig getifaddr en0`으로 맥 LAN IP를 재확인하고, 주소가 달라졌으면 스킴 환경값도 갱신한다.

```sql
SELECT ua."email", p."name", p."yarnNameSnapshot", p."needleSizeSnapshot",
       pc."titleSnapshot"
FROM "Project" p
JOIN "UserAccount" ua ON ua."id" = p."ownerId"
LEFT JOIN "ProjectPatternCopy" pc ON pc."projectId" = p."id" AND pc."deletedAt" IS NULL
WHERE ua."email" IN ('cuj1a@test.local','cuj1b@test.local') AND p."deletedAt" IS NULL;

SELECT ua."email", count(*) AS tool_links
FROM "ProjectToolLink" l JOIN "UserAccount" ua ON ua."id" = l."ownerId"
WHERE l."deletedAt" IS NULL GROUP BY ua."email";
```

#### TC-CUJ3-01 연결의 생애주기
- 관련 SPEC: LINK-02, LINK-04, LINK-05, PAT-04 전단
- 검증 목적: 창고 원본을 여러 프로젝트가 재사용하더라도 각 프로젝트가 연결 시점의 실 정보를 독립적인 작업 기록으로 유지하고, 원본 수정·삭제와 도안 연결 해제가 다른 데이터에 예상하지 않은 영향을 주지 않는지 확인
- 기법: 시나리오
- 사전 조건: 계정 1개, 프로젝트 A와 B 생성. 창고에 실 Y 등록, A의 대표 실로 지정하고 사용 기록 2건 작성. A에 도안 연결
- 절차:
	1. A의 작업 화면, 프로젝트 카드, 사용 기록 패널에 실 이름 "Y"가 동일하게 표시되는지 확인
	2. 창고에서 실 Y의 이름을 "Y수정"으로 변경
	3. A의 작업 화면, 프로젝트 카드, 사용 기록 패널이 모두 연결 당시 스냅샷 "Y"를 유지하는지 확인
	4. 수정된 동일 실 "Y수정"을 B의 대표 실로 지정하고, B의 작업 화면과 프로젝트 카드에 "Y수정"이 표시되는지 확인
	5. A에서 도안 연결을 해제하고, A 프로젝트에서는 도안이 더 이상 표시되지 않으며 창고의 도안 원본은 남아 있는지 확인

- 검증 위치·도구:

#### TC-SYNC10-01 pendingUpload 거부 시 무통보 덮어쓰기
- 관련 SPEC: SYNC-10 (RC-01)
- 기법: 에러 기대, Charles Breakpoint
- 용어 설명: `pendingUpload`는 서버에 이미 존재하는 데이터를 기기에서 수정했지만, 그 수정본이 아직 서버에 반영되지 않은 상태다. 이 TC에서는 서버와 로컬 모두 메모가 "원본"인 synced 프로젝트 P를 오프라인에서 "수정본"으로 변경해 pendingUpload 상태를 만든다.
- 검증 목적: 서버가 수정 PATCH를 거부하더라도 사용자가 입력한 로컬 수정본을 자동 폐기하지 않고, 동기화 실패 상태와 재시도 가능성을 사용자에게 알려주는지 확인
- 사전 조건: 프로젝트 P가 서버와 로컬에 synced 상태로 존재하고 메모는 모두 "원본"이다. Local Simulator가 맥 LAN IP base URL을 사용하며 시뮬레이터 요청이 Charles에 캡처된다. HTTP 평문이므로 SSL Proxying은 필요 없고 Breakpoint만 설정한다. PostgreSQL은 유지한 채 NestJS API만 중단·재개할 수 있다.
- 절차:
	1. psql과 `projects.json`에서 프로젝트 P의 ID와 메모 "원본", 로컬 `syncStatus = "Synced"`를 확인해 기록한다.
	2. NestJS API만 중단하고 PostgreSQL은 유지한다.
	3. 앱에서 P의 메모를 "수정본"으로 변경한다.
	4. `projects.json`에서 같은 프로젝트 ID의 메모가 "수정본"이고 `syncStatus = "Pending Upload"`인지 확인한다.
	5. psql에서 서버 DB의 메모는 여전히 "원본"인지 확인한다.
	6. NestJS API를 재개하고 Charles에서 `PATCH /api/v1/projects/<P의 id>` 요청을 중단한다.
	7. PATCH가 서버에 정상 반영되지 않도록 요청 본문을 서버가 거부할 값으로 변조하거나, 요청을 서버에 전달하지 않고 HTTP 400 응답을 반환한다. 단, 정상 PATCH를 서버에 전달한 뒤 응답 코드만 400으로 바꾸는 방식은 사용하지 않는다.
	8. Charles에서 PATCH 요청과 HTTP 400 응답을 저장한다.
	9. 앱에서 P의 메모 값, 동기화 실패 표시, 재시도 또는 수정 안내를 확인한다.
	10. `projects.json`에서 같은 프로젝트 ID의 메모가 "수정본"으로 유지되고 재시도 가능한 동기화 상태인지 확인한다.
	11. psql에서 서버 DB의 메모가 "원본"으로 유지되는지 확인한다.
- 기대 결과:
	1. HTTP 400 이후 서버 DB의 메모는 "원본"으로 유지되어야 한다.
	2. 앱과 `projects.json`에는 사용자가 입력한 "수정본"이 동일한 프로젝트 ID로 보존되어야 한다.
	3. 프로젝트는 열람·수정할 수 있어야 하며, 앱은 동기화 실패 사실과 재시도 또는 수정 가능성을 안내해야 한다.
	4. 앱이 안내 없이 메모를 "원본"으로 복원하거나 로컬 수정본을 삭제하면 `FAIL`이다.
	5. 수정본은 남지만 동기화 실패 안내가 전혀 없으면 무통보 실패 `FAIL`이다.
	6. 서버 DB까지 "수정본"으로 변경됐다면 실제 서버 거부 시나리오가 성립하지 않은 것이므로 `PASS`로 판정하지 않고 `RETRY_REQUIRED`로 처리한다.
	7. PATCH 요청과 HTTP 400 응답을 증명하지 못하거나, 4번에서 pendingUpload 상태를 확인하지 못하면 `RETRY_REQUIRED` 또는 전제 미성립으로 분리 기록한다.
- 검증 위치·도구:
	1. iOS 시뮬레이터 앱 화면 — 로컬 `수정본` 유지, 프로젝트 접근 가능 여부, 실패·재시도 안내 확인
	2. Charles — P 수정 PATCH와 실제 HTTP 400 거부 확인
	3. 로컬 `projects.json` — 같은 프로젝트 ID의 메모 `수정본`과 `pendingUpload` 보존 확인
	4. PostgreSQL `psql` — 서버 메모가 `원본`으로 유지되는지 확인
- 실측 방법: Charles의 PATCH 요청·400 응답 증적 + 앱 화면 + `projects.json` 전후 비교 + psql. 서버 메모는 `"Project"."memo"` 컬럼(기본값 빈 문자열)으로 확인한다. 예: `SELECT "id", "name", "memo" FROM "Project" WHERE "id" = '<P의 id>';`. 동기화 실패 UI의 실제 명칭만 기준 빌드에서 확인해 기록한다. `[확인 필요]`

#### TC-AUTH05-01 이전 계정 localOnly의 교차 업로드
- 관련 SPEC: AUTH-05, AUTH-06 (RC-02)
- 기법: 에러 기대, 상태 전이, 계정 격리
- 용어 설명: `localOnly`는 기기에는 저장됐지만 서버에는 한 번도 생성되지 않은 신규 데이터다. `교차 업로드`는 A가 만든 이 데이터를 B 로그인 세션의 Authorization 토큰으로 서버에 전송하여 B 소유 데이터로 만들거나, 전송을 시도하는 계정 오염을 뜻한다. `ownerId`는 서버 DB에서 데이터의 소유 계정을 식별하는 값이다.
- 검증 목적: A 로그인 중 생성된 localOnly 프로젝트가 A의 로컬 영역에 보존되고, B 로그인 상태에서는 화면에 노출되지 않을 뿐 아니라 B 세션으로 업로드 요청조차 전송되지 않는지 확인

	1. 계정 A와 B의 가입·온보딩을 완료하고 각 계정의 서버 user ID를 기록한다. B의 프로젝트는 0건이다.
	2. 시뮬레이터가 Charles 프록시를 경유하며 프로젝트 POST 요청의 URL, Authorization 헤더와 요청 본문을 확인할 수 있다.
	3. PostgreSQL은 유지한 채 NestJS API만 중단·재개할 수 있다.
- 절차:
	1. A로 로그인한 상태에서 NestJS API만 중단하고 PostgreSQL은 유지한다.
	2. 프로젝트 `R계정검증`을 생성한다.
	3. `projects.json`에서 R의 프로젝트 ID와 `syncStatus = "Local Only"`를 기록하고, psql에서 같은 ID 또는 이름의 서버 행이 0건인지 확인한다.
	4. A에서 로그아웃한다. 로그아웃 후에도 R이 A의 로컬 캐시에 남아 있는지 확인한다.
	5. NestJS API를 재기동하고 Charles 기록을 초기화한 뒤 B로 로그인한다.
	6. B의 My Knitting 목록을 조회해 pending 재시도 경로를 실행한다. B의 프로젝트 목록에 R이 보이는지도 함께 확인한다.
	7. Charles에서 B 로그인 이후 발생한 요청 중 R의 ID 또는 이름이 포함된 `POST /api/v1/projects`가 있는지 확인한다. 요청이 있다면 Authorization이 B 세션인지 기록한다.
	8. psql에서 R의 존재 여부와 ownerId·소유 계정 이메일을 확인한다.
	9. B에서 로그아웃하고 A로 다시 로그인해 목록을 조회한다. R이 A에게 복구되고 업로드가 수행된다면 Charles 요청과 psql로 A 소유 생성 여부를 확인한다.
- 기대 결과:

#### TC-CNT03-01 RowCounter 누락 시 프로젝트 단위 격리
- 관련 SPEC: CNT-03 (RC-04) \| 기법: 에러 기대, 상태 분리
- 검증 목적: 서버 응답에서 P1의 RowCounter만 누락됐을 때 P1 오류가 P2와 목록 전체로 전파되지 않는지 확인한다. 기존 로컬 캐시가 원격 디코딩 실패를 가리는 거짓 PASS를 막기 위해 warm cache와 cold cache를 분리한다.
- 사전 조건:
	1. 동일 계정에 고유한 이름의 synced 프로젝트 P1과 P2를 생성한다.
	2. P1 카운터는 11, P2 카운터는 22로 저장하고 서버 반영을 확인한다.
	3. P1_ID와 P2_ID를 기록한다.
	4. A 구간용 기존 시뮬레이터에는 P1·P2 로컬 캐시가 있다.
	5. B 구간용 신규 시뮬레이터에는 해당 계정의 프로젝트 캐시가 없어야 한다.
- 조건 생성:
	1. psql에서 P1의 RowCounter만 ID 기준으로 삭제한다.
	2. P1 RowCounter는 0건, P2 RowCounter는 `currentRow=22`로 남았는지 확인한다.
```sql
DELETE FROM "RowCounter"
WHERE "projectId" = '<P1_ID>';

SELECT "projectId", "currentRow"
FROM "RowCounter"
WHERE "projectId" IN ('<P1_ID>', '<P2_ID>')
ORDER BY "projectId";
```
- 절차 A — warm cache:
	1. 기존 캐시가 있는 시뮬레이터에서 Charles 기록을 초기화한다.
	2. 앱을 재실행하고 프로젝트 목록을 명시적으로 새로고침한다.
	3. 프로젝트 목록 GET이 실제로 실행되고 HTTP 200을 반환했는지 확인한다.
	4. 응답에 P1과 P2가 모두 포함되며 P1의 `rowCounter`만 null 또는 누락됐는지 확인한다.
	5. 앱 목록의 P1·P2 표시 상태와 공통 오류 안내 여부를 확인한다.
	6. P2 상세에 진입해 카운터 22가 표시되고 조작 가능한지 확인한다.
	7. Xcode 콘솔에서 디코딩 오류와 로컬 캐시 fallback 여부를 확인한다.
- 절차 B — cold cache:
	1. 앱을 새로 설치한 별도 시뮬레이터를 사용한다.
	2. 같은 계정으로 로그인하고 프로젝트 캐시가 없는 상태임을 확인한다.
	3. Charles 기록을 초기화하고 최초 프로젝트 목록 조회를 수행한다.
	4. GET 200 응답에 P1·P2가 포함되고 P1의 `rowCounter`만 누락됐는지 확인한다.
	5. P2가 목록에 표시되는지 확인하고 상세에 진입해 카운터 22를 확인한다.
	6. P1은 단독 오류 상태 또는 목록 제외로 격리되는지 확인한다. 정확한 UI 표현은 기준 빌드에서 `[확인 필요]`로 기록한다.
- 기대 결과 및 판정:
	1. A와 B 모두에서 P2가 표시되고 상세·카운터 22가 정상 동작하면 핵심 격리 조건을 충족한다.
	2. P1만 오류 상태로 표시되거나 제외되고 P2와 목록이 정상이라면 `PASS`다.
	3. P1에 존재하지 않는 카운터 값 0을 정상값처럼 생성해 표시하면 데이터 왜곡 `FAIL`이다.
	4. 목록 전체가 비거나 공통 오류 화면으로 전환되면 `CNT-03 FAIL`이다.
	5. P2가 보이지 않거나 상세 진입·카운터 사용이 불가능하면 격리 실패 `FAIL`이다.
	6. A에서 서버 응답 전체를 버리고 이전 캐시만 표시하면 프로젝트 단위 격리가 아니라 전체 fetch 실패이므로 `FAIL`이다.
	7. GET 응답에 P1이 포함되지 않거나 P1의 RowCounter가 실제로 존재하면 조건 미성립 `RETRY_REQUIRED`다.
	8. B 시뮬레이터에 기존 프로젝트 캐시가 남아 있거나 응답 본문·디코딩 경로를 확인하지 못하면 `RETRY_REQUIRED`다.
- 검증 위치·도구:
	1. iOS 시뮬레이터 앱 화면 — 목록 전체 유지, P1 격리 표시, P2 상세·카운터 22 동작 확인
	2. Charles — GET 실행 여부, HTTP 200, P1·P2 포함 여부와 P1 `rowCounter` 누락 확인
	3. Xcode 콘솔 — 배열 디코딩 오류와 로컬 캐시 fallback 경로 확인

#### TC-AUTH02-01 실제 토큰 만료 401 후 세션 제거·로컬 보존·재로그인 복구
- 관련 SPEC: AUTH-02 \| 기법: 에러 기대, 상태 전이
- 검증 목적: 실제로 만료된 access token으로 보호 API에서 401을 수신했을 때 인증 세션만 제거되고 로컬 프로젝트 데이터는 유지되는지 확인한다. 콜드 런치 후에도 로그아웃 상태가 유지되고, 같은 계정으로 재로그인하면 보존된 프로젝트에 다시 접근할 수 있는지도 검증한다.
- 사전 조건:
	1. 서버 `.env`의 `AUTH_JWT_EXPIRES_IN_SECONDS=60`을 설정하고 API를 재기동한다.
	2. 신규 로그인해 새 access token을 발급받는다.
	3. Charles에서 로그인 응답을 확인할 수 있어야 한다.
	4. 로컬 파일 경로는 공통 사전 조건의 `Library/Application Support/KnitGether/projects.json`을 사용한다.
- 절차 A — 실제 만료와 401 증명:
	1. 로그인 응답의 access token을 확보하고 JWT payload의 `iat`, `exp`를 디코딩한다. 전체 토큰은 증적에 남기지 않고 앞뒤를 마스킹한다.
	2. `exp - iat`가 약 60초인지 확인한다.
	3. 고유 프로젝트 `AUTH02_P_<실행시각>`을 생성하고 서버 동기화 성공을 확인한다.
	4. 프로젝트 ID를 기록하고 `projects.json`에서 해당 ID와 이름이 존재하는지 확인한다.
	5. 401 전 로컬 파일 또는 대상 프로젝트 JSON 레코드를 별도 증적으로 저장한다. 파일 해시는 보조 증적으로 사용할 수 있다.
	6. 만료 전 프로젝트 목록 GET을 실행해 HTTP 200을 확인한다.
	7. JWT의 `exp` 시각이 지난 뒤 동일한 보호 API를 다시 요청한다.
	8. Charles에서 응답이 HTTP 401인지 확인한다.
	9. 가능하면 서버 로그에서 원인이 만료 토큰인지 확인한다.
- 절차 B — 세션 제거와 로컬 보존·복구:
	1. 401 수신 직후 앱이 로그인 화면 또는 인증이 필요한 초기 화면으로 전환되는지 확인한다.
	2. 이전 인증 상태로 프로젝트 화면에 계속 접근할 수 없는지 확인한다.
	3. `projects.json`에서 `AUTH02_P_<실행시각>`의 ID·이름·프로젝트 데이터가 유지되는지 확인한다.
	4. 앱 프로세스를 완전히 종료하고 콜드 런치한다.
	5. 만료 토큰으로 자동 로그인되지 않고 로그아웃 상태가 유지되는지 확인한다.
	6. 콜드 런치 후에도 `projects.json`의 대상 프로젝트 레코드가 유지되는지 다시 확인한다.
	7. 동일 계정으로 재로그인한다.
	8. 프로젝트 목록에서 `AUTH02_P_<실행시각>`이 다시 표시되는지 확인한다.
	9. 프로젝트 상세에 진입해 주요 데이터가 정상인지 확인한다.
- 기대 결과 및 판정:
	1. 만료 전 동일 보호 API는 200, `exp` 이후에는 401이어야 테스트 조건이 성립한다.
	2. 401 후 인증 세션이 제거되고 콜드 런치 후에도 로그아웃 상태가 유지돼야 한다.
	3. 401 전후와 콜드 런치 후 모두 로컬 프로젝트 레코드가 유지돼야 한다.
	4. 같은 계정으로 재로그인하면 대상 프로젝트가 다시 표시되고 정상 진입돼야 한다.
	5. 401 후에도 인증이 필요한 화면에 계속 접근하거나, 앱 재실행 후 만료 토큰으로 자동 로그인되면 세션 제거 `FAIL`이다.
	6. 로컬 프로젝트 레코드가 삭제·초기화되거나 대상 프로젝트 주요 값이 유실되면 `AUTH-02 FAIL`이다.
	7. 401 대신 네트워크 오류·500이 발생하거나 `exp - iat`가 60초로 적용되지 않으면 조건 미성립 `RETRY_REQUIRED`다.
	8. 401 전 로컬 파일 존재를 확인하지 못했거나 실제 401 응답을 증명하지 못하면 `RETRY_REQUIRED`다.
- 만료 안내 UX 관찰:
	1. `세션이 만료되었습니다. 다시 로그인해 주세요.`와 같이 원인을 안내하면 UX 양호로 기록한다.
	2. 안내 없이 로그인 화면으로 이동하더라도 AUTH-02의 세션 제거·로컬 보존이 충족되면 기능 판정은 가능하되 UX 개선사항으로 기록한다.
	3. 만료를 일반 네트워크 오류로 표시하면 원인 안내 부정확 결함 후보로 기록한다.
- 검증 위치·도구:
	1. Charles — 로그인 응답, 만료 전 200, 만료 후 401, 요청·응답 시각 확인
	2. JWT payload — `iat`, `exp`, 60초 만료 적용 확인
	3. iOS 시뮬레이터 앱 화면 — 401 후 인증 전환, 콜드 런치 로그아웃, 재로그인 복구 확인
	4. 로컬 `projects.json` — 401 전후·콜드 런치 후 대상 프로젝트 레코드 보존 확인
	5. 서버 로그 — 가능하면 401 원인이 token expired인지 확인
- 실측 방법: 마스킹한 JWT payload, Charles 200·401 캡처, 401 전후와 콜드 런치 후 `projects.json` 대상 레코드, 로그아웃 화면, 재로그인 후 프로젝트 복구 화면을 증적으로 남긴다.
- 정리: 실측 후 `.env`의 `AUTH_JWT_EXPIRES_IN_SECONDS`를 원래 값으로 복구하고 API를 재기동한다.
#### TC-PAT02-01 외부 PDF의 앱 내부 복사·콜드 런치·원본 및 서버 부재 시 재열람
- 관련 SPEC: PAT-02 \| 기법: 회귀, 상태 전이
- 검증 목적: 파일 앱에서 가져온 PDF가 외부 원본 URL을 계속 참조하지 않고 앱 데이터 컨테이너 내부에 독립 복사되는지 확인한다. 콜드 런치 후에도 복사본을 열 수 있고, 외부 원본과 서버가 모두 없는 상태에서도 로컬 복사본만으로 재열람 가능한지 검증한다.
- 사전 조건:
	1. 파일 앱에 고유한 이름의 2페이지 이상 PDF `PAT02_SOURCE_<실행시각>.pdf`를 준비한다.
	2. 첫 페이지에 `PAT02-ORIGINAL` 식별 문구를 넣는다.
	3. 프로젝트 `PAT02_P_<실행시각>`을 생성하고 프로젝트 ID를 기록한다.
	4. 가져오기 전 앱 데이터 컨테이너의 PDF 목록을 저장한다.
```bash
APP_DATA=$(xcrun simctl get_app_container booted <번들ID> data)
find "$APP_DATA" -type f -iname "*.pdf" -print
```
- 절차 A — 앱 내부 복사본 생성:
	1. 파일 앱에서 준비한 PDF를 직접 가져와 프로젝트에 연결한다.
	2. PDF의 페이지 수와 `PAT02-ORIGINAL` 문구를 확인한다.
	3. Charles 또는 서버 로그에서 도안 저장·업로드 요청 성공을 확인한다.
	4. 앱 데이터 컨테이너의 PDF 목록을 다시 조회해 새 PDF가 생성됐는지 확인한다.
	5. 새 파일의 경로가 외부 원본 경로가 아니라 앱 데이터 컨테이너 내부인지 확인한다.
	6. 원본과 앱 내부 복사본의 파일 크기와 SHA-256을 비교한다.
	7. `ProjectPatternCopy`의 파일 참조 필드를 확인한다. 정확한 컬럼명은 실행 전 `\\d "ProjectPatternCopy"`로 확인해 실제 결과에 기록한다.
```bash
find "$APP_DATA" -type f -iname "*.pdf" -exec ls -l {} \;
shasum -a 256 "<원본 PDF>" "<앱 내부 PDF>"
```
- 절차 B — 일반 콜드 런치 재열람:
	1. 앱을 앱 전환기에서 완전히 종료한다.
	2. 앱을 다시 실행하고 프로젝트 도안 화면에 진입한다.
	3. 같은 PDF의 페이지 수와 `PAT02-ORIGINAL` 문구가 유지되는지 확인한다.
	4. 앱 내부 PDF가 계속 존재하는지 확인한다.
	5. Xcode 콘솔에서 외부 원본 URL 접근 오류가 없는지 확인한다.
- 절차 C — 원본과 서버가 모두 없는 상태:
	1. 앱을 다시 완전히 종료한다.
	2. 파일 앱에서 외부 원본 PDF를 삭제하거나 앱이 접근할 수 없는 위치로 이동한다.
	3. 원본 경로에서 파일이 실제로 사라졌는지 확인한다.
	4. NestJS API를 중단하거나 시뮬레이터 네트워크를 차단한다.
	5. Charles 기록을 초기화한 뒤 앱을 콜드 런치한다.
	6. 프로젝트 도안을 다시 연다.
	7. PDF 페이지 수와 `PAT02-ORIGINAL` 문구가 그대로 표시되는지 확인한다.
	8. 앱 내부 PDF 파일이 계속 존재하는지 확인한다.
	9. 서버에서 PDF를 다시 받은 성공 요청이 없었는지 확인한다.
- 기대 결과 및 판정:
	1. 가져오기 후 앱 데이터 컨테이너 내부에 독립 PDF가 생성되고 원본과 파일 정합성이 일치해야 한다.
	2. 일반 콜드 런치 후 정상 열람되고, 원본 삭제·API 중단 후에도 앱 내부 복사본만으로 정상 열람되면 `PASS`다.
	3. 온라인 상태에서는 열리지만 API 중단 후 열리지 않으면 로컬 캐시 누락 `FAIL`이다.
	4. 원본 삭제 후 파일 없음 또는 외부 URL 접근 오류가 발생하면 외부 파일 참조 회귀 `FAIL`이다.
	5. 앱 내부 파일은 있으나 다른 PDF가 열리거나 페이지·내용이 누락되면 파일 정합성 `FAIL`이다.
	6. 외부 원본이 실제로 남아 있거나 서버 다운로드가 성공하면 독립성 조건 미성립 `RETRY_REQUIRED`다.
	7. 가져오기 전후 앱 컨테이너 파일 목록을 비교하지 못했거나 내부 파일 경로를 확인하지 못하면 `RETRY_REQUIRED`다.
- 검증 위치·도구:
	1. iOS 시뮬레이터 앱 화면 — 페이지 수, 식별 문구, 세 조건의 재열람 확인
	2. 앱 데이터 컨테이너 — PDF 생성 경로·파일 크기·SHA-256 확인
	3. Charles 또는 서버 로그 — 저장 성공과 C 구간의 재다운로드 부재 확인
	4. Xcode 콘솔 — 외부 URL 접근 오류와 로컬 파일 로딩 경로 확인
	5. PostgreSQL `psql` — `ProjectPatternCopy` 파일 참조 필드 확인
- 실측 방법: 가져오기 전후 앱 컨테이너 PDF 목록, 원본·복사본 해시, 최초 열람·콜드 런치·원본 및 서버 부재 재열람 화면, Charles 기록과 Xcode 콘솔을 증적으로 남긴다.
- 정리: 실측 후 API와 네트워크를 복구하고 전용 프로젝트 및 테스트 PDF를 삭제한다.
#### TC-PAT05-01 직접 사전·스킬 검색 후 작업 맥락 복귀
- 관련 SPEC: PAT-05, CNT-02 \| 기법: 시나리오
- 사전 조건: 3페이지 이상의 PDF 도안이 연결된 프로젝트, 카운터 5, 검색 가능한 스킬 데이터 1건
- 절차: 1. 작업 화면에서 도안 3페이지와 카운터 5 확인 2. 앱 내부 사전·스킬 검색 화면으로 이동 3. 준비된 스킬을 검색해 상세 열람 4. 정상적인 UI 동작으로 기존 작업 화면 복귀 5. 카운터와 도안 페이지 번호 확인
- 기대 결과: 검색과 상세 열람이 가능하고 복귀 후 카운터 5와 도안 3페이지가 유지되어야 한다. 확대율과 페이지 내 스크롤 위치는 비교하지 않는다. 카운터가 달라지거나 도안이 닫히거나 다른 페이지로 복귀하면 FAIL이다.

- 검증 위치·도구:
	1. iOS 시뮬레이터 앱 화면 — 사전·스킬 검색, 상세 열람, 작업 화면 복귀와 카운터·PDF 페이지 보존 확인
	2. 화면 캡처 — 이탈 직전과 복귀 직후 상태 비교
