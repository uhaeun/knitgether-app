#### 이 문서는 무엇이고 무엇이 아닌가

이 문서는 기획자가 개발 전에 쓰는 전통적 기능명세서가 아니다. QA가 개발 완료 후에 수립한 검증 기준선(test basis)이며, 관찰 가능한 동작을 판정 가능한 문장으로 정의하고 테스트 케이스 도출의 근거로 쓴다. 코드에서 역산했으나 코드를 정답으로 삼지 않는다. 코드 동작과 기획 의도가 어긋나는 항목은 불일치로 기록하고, 코드에도 답이 없는 동작은 명세 공백으로 분리해 관리한다.

이 프로젝트의 문서 체계는 세 층이다. 사전 기획 문서가 개발에 선행해 의도와 요구사항을 정의했고 회차별 구현과 병행하며 갱신됐다. 그에 따라 MVP가 구현됐으며, 이 문서는 QA 단계에서 수립한 검증 기준선이다. 검증 기준선은 개별 동작을 판정 가능한 문장으로 정의하는 문서로, 의도 수준의 사전 문서보다 정밀도가 한 단계 깊다.

기준선의 원천은 QA 인수인계 문서와 현재 코드다. 인수인계 문서는 개발 완료 시점(기준 커밋 bf2b001)에 작성된 시스템 안내서로 아키텍처, 데이터 흐름, API 목록, 알려진 이슈(known issues)를 담는다. 사전 기획 문서는 구현 과정에서 데이터 구조가 전면 변경되어 현재 코드와 괴리가 있으므로 의도 참고용으로만 쓰고, 동작 정의는 코드 실측에서 역산했다. 코드 동작을 그대로 기준으로 승인할지, 기대와 어긋나 불일치로 기록할지는 기획자 관점에서 항목마다 판정해 확정했다. 근거 열의 파일:라인은 모두 기준 커밋 bf2b001 시점 기준이다.

이 문서는 요구사항 추적(RTM)의 가운데 층이다. 상위는 01의 CUJ와 치명도 축이고, 하위는 05의 테스트케이스다. 각 SPEC은 관련 CUJ를 부록에서 매핑하며, 05의 모든 TC는 SPEC ID를 참조한다. 요구사항부터 실행 결과까지의 전체 추적 매트릭스는 05에서 조립하고 06의 판정 결과와 연결한다.

이 기준선은 기능 동작에 한정한다. 비기능 요구사항(성능, 보안, 접근성)은 00에서 선언한 범위 판단에 따라 이번 사이클에서 다루지 않으며, 근거는 04 테스트전략에서 서술한다. 단 인증 관련 동작(SPEC-AUTH)은 보안 항목이 아니라 데이터 정합성 관점의 기능 동작으로 다룬다.

각 SPEC에는 코드 일치 여부를 함께 기록했다. **일치**는 코드 동작을 그대로 기준으로 채택한 항목, **조건부 일치**는 조건을 달아 채택한 항목, **불일치 의심**은 기획자가 정의한 SPEC과 코드가 어긋나는 것으로 보여 06 실행에서 확정할 항목, **불일치 확정**은 코드 구조만으로 어긋남이 확정된 항목이다. **미대조**는 기획자가 정의한 기대이나 코드 대조를 수행하지 않아 06 실행에서 확인할 항목이다. 여기서 일치는 코드를 정답(test oracle)으로 확정했다는 뜻이 아니다. 테스트 오라클은 코드 자체여서는 안 되므로, 관찰된 코드 동작을 기획 의도와 대조한 뒤에만 기준으로 채택했으며 대조에서 어긋난 것이 불일치 항목들이다. 합격/불합격 판정은 06 테스트 실행에서 한다. 각 항목의 치명도 연결과 우선순위는 03 품질리스크맵에서 매핑한다.
