# 테스트 설계

뜨개더는 도안과 재료를 연결하고 단수(뜬 줄 수)와 작업 메모를 기록하는 iOS 앱입니다. 기능별 정상 동작을 확인한 뒤, 실제 작업을 시작하고 이어 가는 흐름이 끊기지 않는지 테스트했습니다. 기록이 사라지거나 다른 계정에 보이는 문제는 복구 비용과 영향이 커 별도 실패 조건을 추가했습니다.

## 핵심 사용자 흐름

| 흐름 | 수행 경로 | 확인한 내용 | 원본 TC |
|---|---|---|---|
| 첫 사용 | 프로젝트 생성 후 자료 연결 / 창고(도안과 재료 보관함) 등록 후 프로젝트에 연결 | 경로가 달라도 프로젝트명, 도안, 실, 바늘, 도구의 연결 결과가 같은가 | TC-CUJ1-01 |
| 작업 재개 | 앱 종료 후 재진입 → 프로젝트 열기 → 단수 증가 | 로그인과 작업 상태가 유지되고 증가한 값이 서버에 저장되는가 | TC-CUJ2-01 |
| 모르는 기법 조회 | 도안의 기법 태그 → 설명 확인 → 작업 화면 복귀 | 조회 전 단수와 도안 페이지를 유지하는가 | TC-CUJ4-01 |

`TC-CUJ3-01`은 처음에는 사용자 흐름으로 분류했으나 연결 해제와 재연결의 정합성 심층 테스트로 재분류했습니다. 기존 ID는 바꾸지 않았습니다. 위 세 흐름의 실제 판정과 후속 실행 범위는 [테스트 결과](test-results.md)에서 구분합니다.

## 우선순위를 정한 이유

| 우선순위 | 대상 | 먼저 확인한 이유 | 추가한 조건 |
|---|---|---|---|
| P1 | 동기화 중 기록 유실, 계정 간 노출 | 단수와 메모는 작업을 되짚어 복원하기 어렵고 다른 계정의 기록은 보여서는 안 됨 | 실제 서버 거부, 통신 단절, 지연 요청, 두 기기 수정, 계정 전환 |
| P2 | 연결과 표시 정합성, 데이터 계약, 생성 경로 차이 | 작업은 계속할 수 있어도 잘못된 자료나 이전 값으로 작업할 수 있음 | 원본 수정 전후, 정상 빈 목록과 조회 실패, 캐시 유무, 필수 연관 데이터 누락 |
| P3 | 삭제 재시도와 삭제된 참조의 표시 | 재접속과 갱신 뒤에도 삭제 결과가 일관되어야 함 | 오프라인 삭제 후 조회, 재조회, 삭제된 기법 참조 |
| 별도 운영 위험 | 파일과 DB 참조 불일치 | 화면에 드러나지 않아도 파일 누적이나 재다운로드 실패로 이어질 수 있음 | 파일 키, 실제 파일, SQL 롤백 전후 대조 |

발생 가능성은 핵심 흐름에서 바로 도달하는 조건을 높게, 여러 상태의 조합을 중간으로 봤습니다. SQL로 연관 행을 제거한 데이터 결손은 발생 가능성을 낮게 두되, 한 항목 때문에 정상 목록까지 막히는 영향을 확인했습니다. P1의 판정을 확정하는 것과 발견 결함을 모두 수정하는 것은 구분했습니다.

## 기대 결과를 정한 기준

기능 구현 후 기존 기획과 코드를 대조해 관찰 가능한 기대 결과를 정리했습니다. 기획 의도와 다른 동작은 불일치로 남기고, 도안 교체의 취소 동작처럼 빠진 기준은 TC 설계 과정에서 구체화했습니다.

| 대상 | 판정 기준 |
|---|---|
| 단수 | 하한 0 유지, 한 번의 입력이 한 번만 반영, 재진입 후 화면과 저장값 일치. 별도 상한은 정하지 않음 |
| 도안 교체 | 삭제 안내 후 취소하면 기존 도안과 도안 위 표시선(드로잉) 보존. 승인하면 새 도안으로 전환하고 이전 드로잉 참조 제거 |
| 원격 목록과 캐시 | 실제 삭제와 조회 불가 항목을 구분. 정상 항목은 갱신하고 조회 불가 항목의 로컬 기록은 보존 |
| 계정 | API 응답뿐 아니라 화면, 로컬 폴더, 업로드 대상도 현재 계정 범위와 일치 |
| 동기화 충돌 | 선행 저장을 덮지 않고 충돌을 알림. 미저장 입력을 보존하고 사용자가 확인 후 재저장 |
| 미저장 메모 | 후속 보완에서는 계정과 프로젝트별 로컬 초안으로 재실행 후 복원. 저장 성공, 명시적 폐기, 프로젝트 삭제 시 정리 |
| 파일 변경 | DB 참조와 실제 파일을 함께 대조. 트랜잭션 실패 시 기존 참조와 파일을 유지 |

충돌 시 수정본을 폐기하던 초기 정책은 후속 검증에서 입력 보존으로 바뀌었습니다. 현재 기준을 과거 실행에 소급해 PASS로 바꾸지 않습니다. 개별 조회의 409와 목록 제외 ID 헤더는 후속에 정한 서비스 계약이며 [최신 근거](evidence/2026-10-31/README.md)에 조건을 남겼습니다.

## 설계를 실행 조건으로 옮긴 방법

| 방법 | 대표 조건 | 화면 외 판정 근거 |
|---|---|---|
| 사용자 시나리오 | 첫 생성부터 자료 연결, 작업 재개, 기법 조회 후 복귀까지 수행 | 요청과 응답, SQL의 연결 결과와 단수 |
| 경계값 | 0에서 감소, 연속 10회 입력, -1 입력, 9999 → 10000 | `currentRow`와 화면의 최종값 |
| 상태 전이 | Local Only, Pending Upload, Synced, Pending Delete 사이의 생성, 수정, 거부, 재시도 | 로컬 `projects.json`의 상태와 서버 저장 여부 |
| 의사결정 테이블 | 기존 드로잉 존재 확인 → 교체 안내 → 취소 / 승인 | 기존 도안과 드로잉, DB 파일 키, 재실행 후 상태 |
| 오류 주입 | 실제 POST / PATCH 400, 지연된 오래된 요청, 연관 행 누락 | 서버 거부 여부와 DB 미변경, 자식 행 ID, HTTP 상태 |
| 상태 분리 | 기존 캐시 / 빈 캐시, 정상 빈 결과 / 조회 실패 | 서버값을 바꾼 뒤 앱 갱신 여부와 캐시 파일 |

서버 거부는 정상 저장 뒤 응답 코드만 바꾸는 방법으로 대체하지 않았습니다. API만 중단할 때 DB는 유지했고, 통신 복구와 목록 조회도 별도 단계로 나눠 재시도 시점을 확인했습니다. 조건이 실제로 성립했음을 입증하지 못하면 `RETRY_REQUIRED`, 사전 상태가 다르면 `전제 미성립`으로 남겨 PASS에서 제외했습니다.
