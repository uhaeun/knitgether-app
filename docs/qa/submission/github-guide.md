## 기획 배경과 프로젝트 목표

뜨개질을 처음 접했을 때, 도안을 파일이나 종이로 따로 챙기고 모르는 용어나 스킬이 나오면 검색해야 하는 점이 번거로웠습니다. 편물을 어디까지 떴는지 잊지 않으려면 단수를 종이나 메모장에 일일이 적어두어야 했습니다.

도안 보기, 용어와 스킬 검색, 단수 기록, 작업 메모를 한 앱에서 이어서 사용할 수 있으면 좋겠다고 생각했습니다. 도안을 보다가 필요한 정보를 찾아보고 작업한 내용을 바로 기록할 수 있도록 기능을 연결해, 뜨개 초보자도 작업을 이어가기 쉽도록 뜨개더를 기획했습니다.

직접 느낀 불편함을 바탕으로 서비스를 기획하고, AI를 활용한 구현부터 테스트와 개선까지 이어지는 전체 과정을 경험해보고 싶었습니다. 기존 DB QA 경험을 살려, 데이터의 정확성뿐 아니라 사용 흐름과 예외 상황까지 검증하는 것을 목표로 했습니다.

## 프로젝트 진행 방식

테스트 실행 전에 기능별 기대 동작을 정리하고, 기획 의도와 구현의 차이를 검토해 테스트 케이스에 반영했습니다. 단수와 메모 등 작업 기록의 보존을 우선적으로 확인했으며, 동시 수정 시 먼저 저장한 데이터와 미저장 입력을 모두 보존하고 사용자가 직접 재저장해야 한다는 기준을 정했습니다.

앱을 직접 조작해 사용 흐름과 예외 상황을 확인하고, Postman 컬렉션과 SQL로 API 응답과 DB 저장값을 대조했습니다. 반복 검증에는 Appium을 활용한 UI 자동화와 pytest 기반 API 및 DB 자동화를 활용했습니다. 발견한 문제는 재현 절차와 기대 결과, 실제 결과를 기록하고 수정 후 관련 기능을 다시 검증했습니다.

AI는 코드 분석, 앱과 서버 구현, 후속 코드 수정과 자동화 테스트 구현 및 실행에 활용했습니다. 기대 동작과 검증 기준은 직접 정했으며, 직접 수행한 테스트와 AI가 실행한 검증은 구분해 기록했습니다.

### 도안 교체 시 드로잉 유실

**문제 발견**

기존 도안에 드로잉을 남긴 뒤 다른 도안으로 교체하는 수동 테스트를 진행했습니다. 교체 자체는 성공했지만, 삭제 안내나 확인창 없이 기존 드로잉이 사라졌습니다. 확인창이 없어 교체를 취소했을 때 기록이 유지되는지도 검증할 수 없었습니다.

**검증 기준**

도안 교체가 성공했더라도 사용자가 남긴 기록이 안내 없이 삭제된다면 정상 동작으로 볼 수 없다고 판단했습니다. 교체 전에 드로잉이 삭제된다는 사실을 안내하고, 취소하면 기존 도안과 드로잉을 유지하며, 사용자가 승인했을 때만 교체하는 것을 검증 기준으로 삼았습니다.

**수정과 결과 확인**

교체 전에 드로잉 삭제 안내와 확인창을 표시하도록 수정됐습니다. 수정 후 Appium 자동화 결과와 촬영 화면에서는 교체 취소 시 기존 도안과 드로잉이 유지되고, 승인 시 새 도안으로 교체되면서 기존 드로잉이 제거되는 동작이 확인됐습니다.

자동화는 ‘그리기 삭제’ 메뉴의 표시 여부로 드로잉 상태를 간접 검사했고, 실제 선의 유지와 제거는 촬영 화면으로 보완했습니다.

### 단수 정보 누락으로 전체 프로젝트 목록 조회 실패

**문제 발견**

프로젝트 하나의 데이터에 문제가 생겼을 때 다른 프로젝트도 조회하지 못하는지 확인했습니다. SQL로 특정 프로젝트의 단수 정보만 제거하자, 목록 API가 HTTP 500을 반환했습니다. 앱에는 이전 목록이 그대로 표시돼 화면만 보면 정상처럼 보였습니다.

**확인 과정과 판단**

정상 프로젝트의 서버 단수를 22에서 99로 바꾼 뒤 앱을 새로고침했지만 화면에는 계속 22가 표시됐습니다. API 응답과 DB 저장값을 대조해, 앱이 최신 데이터를 받아온 것이 아니라 이전에 저장한 값을 보여주고 있음을 확인했습니다.

처음에는 앱의 데이터 해석 과정에서 문제가 생길 것으로 예상했지만, 실제로는 서버가 응답을 만드는 단계에서 실패했습니다. 한 프로젝트의 오류가 정상 프로젝트의 조회까지 막지 않도록, 오류 항목을 제외하고 정상 항목은 반환해야 한다고 판단했습니다.

**수정과 결과**

서버가 프로젝트별로 오류를 처리하도록 수정됐습니다. 같은 오류 조건에서 목록 API는 HTTP 200과 정상 프로젝트를 반환했고, 앱에도 변경된 단수가 표시됐습니다. 이후 pytest 자동화에서는 SQL로 단수 정보를 삭제 상태로 만든 뒤 정상 항목의 포함과 오류 항목의 제외를 검사했습니다.

| 확인 지점 | 수정 전 | 수정 후 |
|---|---|---|
| 목록 API | HTTP 500 | HTTP 200, 정상 항목 반환 |
| 정상 프로젝트의 화면 단수 | 서버는 99, 화면은 이전 값 22 | 변경된 값 99 표시 |
| 오류 프로젝트의 개별 조회 | HTTP 500 | 당시 HTTP 500 유지 |

목록 조회는 복구됐지만, 오류 프로젝트의 개별 조회에는 HTTP 500이 남았습니다. 해당 항목의 복구와 오류 안내는 별도 개선 범위로 기록했습니다.

*최초 재현은 단수 행 제거, 회귀 자동화는 삭제 상태 변경 조건입니다. 표의 값은 당시 실행 기록이며 이번 문서 정리에서 재실행한 결과가 아닙니다.*

### 동시 수정 시 작업 기록 보존

**문제와 검증 범위**

같은 계정으로 두 기기에서 하나의 프로젝트를 수정하면, 오래된 내용을 가진 기기의 저장이 먼저 저장한 내용을 덮어쓸 수 있습니다. 충돌로 저장을 거절하더라도 작성 중인 메모가 사라진다면 작업 기록을 보호했다고 보기 어렵습니다.

**검증 기준**

먼저 저장한 데이터는 서버에 유지하고, 나중에 저장하는 기기에는 충돌 안내와 미저장 입력을 함께 남겨야 한다고 정했습니다. 자동으로 재저장하면 다른 기기의 변경을 다시 덮을 수 있으므로, 사용자가 직접 저장하도록 했습니다.

앱을 종료해도 초안을 복구할 수 있도록 계정과 프로젝트별로 기기에 보관하고, 저장에 성공하거나 사용자가 명시적으로 삭제했을 때 제거하는 정책도 정했습니다.

**검증 과정**

검증 환경은 독립된 iOS 시뮬레이터 두 개를 동일한 서버와 계정에 연결해 구성했습니다. 같은 프로젝트에서 기기 B에 미저장 메모를 남기고, 기기 A가 먼저 저장한 뒤 B가 저장을 시도하는 순서로 충돌 상황을 만들었습니다.

A의 선행 저장으로 버전이 달라져 B의 저장이 거절됐을 때(HTTP 409), 서버에 A의 내용이 유지되고 B에는 입력과 충돌 안내가 남는지 검증했습니다. 이후 B에서 직접 재저장한 뒤 DB의 최종값을 확인했습니다. 자동 재저장 여부와 재충돌 시 초안 보존, 다른 필드가 의도치 않게 변경되는지도 검증에 포함했습니다.

**결과와 확인 범위**

수정 후 실행 기록에서 서버의 선행 저장과 B의 미저장 입력 보존, 직접 재저장 후 최종 DB 값이 확인됐습니다. 자동 재저장이 발생하지 않는지는 300초 동안 관찰했습니다.

검증 근거는 화면과 HTTP 요청 및 응답, SQL 결과로 남겼습니다. 실행별 빌드와 확인 범위를 구분해, 서로 다른 시점의 결과를 최종 버전의 전체 재검증으로 합산하지 않았습니다.

### 보완 사례: 화면 이동 후 도안 페이지 유지

두 경로 모두 잠시 다른 화면을 확인한 뒤 작업을 이어가는 흐름이라고 보고, 홈 탭에서 복귀할 때도 보던 페이지를 유지하도록 요구사항의 범위를 확대했습니다. 페이지 번호를 보존 대상으로 정하되, 확대율과 페이지 안의 스크롤 위치, 앱 재실행 후 복원은 당시 범위에서 제외했습니다.

수정 후 Appium 검증에서는 실제 페이지 이동과 페이지별 고유 표시를 확인해, 홈 탭과 사전 조회 경로 모두 같은 페이지로 복귀하는 결과가 확인됐습니다. 사용 흐름을 기준으로 보존 범위를 구체화하고, 이를 자동화의 판정 조건에 연결한 사례입니다.

## 결과와 회고

뜨개더는 도안과 기록을 한곳에서 관리하며 작업을 편하게 이어가기 위해 기획했습니다. 테스트를 진행하면서 기능을 한 앱에 모으는 것만으로는 이 목적을 충족할 수 없다는 점을 알게 됐습니다. 도안 교체가 성공해도 드로잉이 사라질 수 있었고, 목록이 표시돼도 최신 데이터가 아닐 수 있었습니다.

검증 기준도 기능의 실행 여부에서 작업을 이어갈 수 있는지로 구체화했습니다. 교체를 취소하면 기존 기록이 남아야 하고, 저장이 충돌하면 작성 중인 메모를 잃지 않아야 하며, 다른 화면에서 돌아오면 보던 페이지를 유지해야 했습니다.

화면에 값이 보이는 것만으로 저장과 조회가 정상이라고 판단할 수는 없었습니다. API 응답과 DB 저장값을 함께 확인하면서, 화면에 나타난 현상과 실제 데이터 상태를 구분해 검증할 수 있었습니다.
