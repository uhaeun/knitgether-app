## 02 목록은 보이는데 값이 갱신되지 않는 문제

**DEF-08 | 화면의 22와 DB의 99**

프로젝트 하나의 단수 정보만 SQL로 지우자 목록 API 전체가 HTTP 500으로 실패했습니다. 앱에는 이전 목록이 남아 정상처럼 보였습니다.

정상 프로젝트의 단수를 DB에서 22에서 99로 바꾸고 새로고침해도 화면은 22였습니다. 요청·응답과 SQL을 대조해, 한 항목의 응답 변환 오류가 목록 전체를 실패시키는 것을 확인했습니다.

### 정상 항목과 오류 항목을 나눠 확인했습니다

| 확인한 곳 | 수정 전 | 수정·재검증 결과 |
|---|---|---|
| 목록 API | 전체 HTTP 500 | 200, 정상 항목과 제외 ID 반환 |
| 오류 항목 개별 조회 | HTTP 500 | 409, 오류 코드로 원인 구분 |
| 오류 항목의 기기 캐시 | 삭제된 항목으로 보고 지울 수 있음 | 캐시 유지, 최신 조회 불가 안내 |

10월 29일에는 단수 행 삭제·삭제 상태 변경의 두 조건에서 정상 단수 99의 반환을 확인했습니다. 이 회차에는 앱 화면을 새로 실행하지 않았습니다.

10월 31일 후속 자동화에서는 개별 조회의 단수 행 삭제·삭제 표시·소유자 불일치를 확인했습니다. 다른 계정에는 404를 유지하고, 조회 전후 단수·메모·작업 세션이 바뀌지 않는지도 비교했습니다. 시험 전에 확보한 사본으로 복원한 뒤 200 응답을 확인했습니다.

Swift 테스트에서는 제외된 항목의 캐시와 미저장 메모가 남고, 실제 삭제 항목은 정리되며 정상 단수 99는 갱신되는지 확인했습니다. 디스크에서 다시 읽은 뒤에도 같은 상태인지 확인했습니다.

## 03 두 기기에서 같은 메모를 수정할 때

**SYNC-11 | 먼저 저장한 값과 작성 중인 메모**

같은 계정의 A·B 기기에서 같은 프로젝트를 열었습니다. B에 메모를 입력해 두고 A에서 먼저 저장한 뒤, B의 내용을 저장하는 순서로 확인했습니다.

서버에는 A의 값을 남기고 B에는 충돌 안내와 미저장 메모를 유지하도록 정했습니다. B는 다시 조회한 뒤 직접 저장하며 자동 재저장은 하지 않습니다. 초안은 계정·프로젝트별로 기기에 남기고, 저장 성공이나 명시적 삭제 때 지웁니다.

| 순서 | 확인한 결과 |
|---|---|
| B 입력 → A 저장 → B 저장 | HTTP 409, DB의 A 메모 유지 |
| B의 충돌 화면 | 안내와 B 입력 유지 |
| B에서 직접 재저장 | DB에 B 메모 저장, 시험한 다른 필드 유지 |
| 앱 종료·재실행 | 초안 복구, 버리기 후 미복구 |

### 추가 확인과 남은 범위

연관 기록·파일 변경 뒤의 오래된 전체 저장, 동시 요청과 롤백도 후속 자동화로 확인했습니다. 실제 HTTP·PostgreSQL 테스트 40개가 통과했고, 10월 29일 새 전용 DB 재실행에서도 통과했습니다.

iPhone 16 Pro에서는 비로그인 단수의 종료·복귀 유지와 카메라 권한 거부 후 안내·복귀, 두 흐름이 각각 최종 재실행에서 통과했습니다. 가입·서버 동기화는 로컬 네트워크 차단으로 미완료이며 원인은 미확정입니다. 장시간 부하는 실행하지 않았습니다.
