### 1-1. 진짜 회귀 2건 (test_07, API-25)

`f93aacc`가 작업 세션 교차 필드 검증(`assertWorkSessionTimes`)을 배선하면서 서버가
`endedAt <= startedAt`을 400으로 거부하게 됐다. 8/29에 작성한 API-25 케이스 두 건이
세션 시각을 `started_at`과 `ended_at` 같은 값으로 쓰고 있어 생성 단계에서 400을 받았다.

두 케이스의 판정 대상은 세션 길이가 아니라 `lastWorkedAt`이므로 종료 시각을 10분 뒤로
옮겨 고쳤다. 실행 코드 기준 커밋은 `1637acc`다.

확인이 필요한 것이 하나 있다. GitHub 이슈 #15는 시간 역전(`endedAt < startedAt`)을
다뤘는데, `f93aacc`는 등호까지 막아 **0초 세션도 거부**한다. 이슈 범위 밖의 계약 결정이며
`docs/spec/spec_drift_f93aacc.md` 5절이 지적한 "수정 커밋이 스펙을 먼저 정함" 패턴과
같은 형태다. 0초 세션 거부가 의도한 계약인지는 판정되지 않았다.

### 1-2. 이슈 #15는 이미 서버에서 수정돼 있다

`projects.service.ts`의 `assertWorkSessionTimes` 주석이 "GitHub #15 서버측 수정"이라고
명시한다. 이슈는 OPEN 상태로 남아 있다.

## 2. DEF-20 가드 범위 판정

9/2 미커밋 상태의 `assertStoredRowCounterIdentity`는 본문의 rowCounter id가 저장된 id와
다르면 행 지시 유무와 무관하게 400으로 막았다. 이 가드가 회귀 감시 7건을 깨뜨렸고
그중 2건이 `test_11_sync_loss_regression`, 곧 DEF-01 회귀 감시였다.

서버는 카운터를 `projectId` 기준 upsert로 1:1 유지하므로 본문이 보낸 새 id는 저장되지
않는다. 실제로 500이 나던 경로는 행 지시가 그 저장되지 않은 id를 참조할 때뿐이다.

| 요청 | 수정 전 | 넓은 가드 | 채택한 가드 |
| --- | --- | --- | --- |
| 카운터 id 그대로 | 200 | 200 | 200 |
| 새 id, 행 지시 없음 | 200 | 400 | 200 |
| 새 id + 행 지시 | 500 (DEF-20) | 400 | 400 |

넓은 가드를 택하지 않은 근거는 유실 경로다. 로컬 id가 어긋난 기기는 저장이 영구히 400이
되고, 앱은 서버 거부를 SYNC-10대로 무통보 폐기한다. Major 한 건을 고치려고 유실 경로를
여는 교환이 된다. `helpers.project_payload`가 호출마다 새 카운터 id를 만들기 때문에
회귀 감시 7건이 전부 가운데 줄을 밟고 있었다는 점이 이 판단의 실측 근거다.

DEF-22는 `@IsDefined()` 추가로 닫았다. 두 회귀 테스트는 결함을 고정하던 단언에서 수정을
지키는 단언으로 뒤집었고, 거부가 원자적인지를 psql로 함께 확인한다.

## 3. DEF-23 수정과 재현

### 3-1. 수정

세션 종료 지점이 `ProjectWorkspaceView`의 `onDisappear` 하나뿐이었고 앱 타깃 전체에
`scenePhase` 참조가 0건이라는 9/1 대조가 그대로 사실이었다. 작업 화면에 `scenePhase`를
연결해 `.background`에서 세션을 끊고 `.active`에서 새로 연다. 시각 주입이 가능하도록
세션 API에 `at:` 파라미터를 붙였다.

단위 테스트는 `ProjectWorkspaceViewModelTests` 80건 통과다. 커밋은 `4dea734`다.

빌드에서 두 번 막혔고 둘 다 기록해 둔다. 모디파이어를 하나 추가하자 뷰 body의 타입 체크가
상한을 넘겨 body를 둘로 나눠야 했고, 2인자 `onChange`는 iOS 17 전용이라 배포 타깃
(iOS 16)에 맞춰 단일 인자 형태를 썼다.

### 3-2. 재현 케이스와 두 빌드 대조

10 대장이 적어둔 검증 방법(작업 공간 진입, 홈, 대기, 복귀, 이탈)을 Appium
`background_app`으로 자동화했다. 파일은 `appium-tests/tests/test_def23_background_session.py`
이며 UI 번호는 배정하지 않았다.

| 빌드 | 결과 |
| --- | --- |
| 수정 후 `4dea734` | PASS. 백그라운드 65초가 빠진 세션 하나가 저장된다 |
| 수정 전 `efae837` | FAIL. 30초를 기다려도 세션이 하나도 저장되지 않는다 |

**수정 전이 과다 기록이 아니라 세션 소멸로 실패했다.** 65초 백그라운드에서 iOS가 앱을
정지시키고, 그러면 메모리에만 있던 시작 시각이 사라진다. 이것은 DEF-23이 아니라 10 대장이
DEF-23과 분리해 둔 명세 공백(02의 4번, 강제 종료 시 세션 소멸)이다.

따라서 이 케이스가 실측으로 보인 것은 "수정 후에는 백그라운드 진입 시점에 세션이 끊겨
저장된다"까지다. DEF-23의 원래 증상인 4시간 미만 방치의 과다 기록은 이 시나리오에서
재현되지 않았다. 그 증상을 보려면 앱이 정지되지 않는 짧은 백그라운드로 별도 케이스가 필요하다.

### 3-3. 오라클을 한 번 고쳤다

처음 작성한 판정은 화면 이탈 후 3초만 기다리고 세션을 조회했다. 그 상태에서 수정 전 빌드를
돌리면 "저장된 작업 세션이 없다"로 실패하는데, 이 실패는 업로드가 아직 안 됐다는 뜻과
길이가 틀렸다는 뜻을 구분하지 못한다. 두 빌드를 가르기는 하지만 주장한 이유로 가른 것이
아니다.

세션이 올라올 때까지 30초를 폴링한 뒤 길이를 판정하도록 고쳤다. 그러고 나서야 3-2의 사실이
드러났다. 07의 6-3절 "공허한 판정 네 건을 작성 중에 잡았다"와 같은 계열이다.

## 4. Appium 스위트가 앱을 설치하지 않는다

이 세션의 Appium 실패는 전부 이 원인이었다. `conftest._options()`는 `full_reset=False`일 때
`o.bundle_id`만 지정하고 앱을 설치하지 않는다. `_default_app_path()`는 `full_reset=True`
에서만 쓰인다. 그래서 시뮬레이터에 예전에 설치된 바이너리가 계속 검증 대상이 된다.

확인 경로는 다음과 같다.

| 조치 | 결과 |
| --- | --- |
| `test_ui_08_login_success` 실행 | FAIL |
| 시뮬레이터 키체인 초기화 후 재실행 | FAIL |
| **`simctl install`로 최신 빌드 설치 후 재실행** | **PASS** |

증상은 로그인 실패였다. 서버 로그에는 `POST /auth/login 200`이 남는데 앱은
"로그인하지 못했어요"를 띄웠고, 성공 시 이어져야 할 `GET /auth/me`가 호출되지 않았다.
9/1 3차 회귀 기록에서는 같은 케이스가 PASS였다.

이 부채의 무게는 검출력과 다른 축에 있다. 어느 바이너리를 검증했는지 스위트가 보장하지
못하면 회귀 판정의 대상이 특정되지 않는다. 9/1 3차 회귀의 "진짜 회귀 0건"도 같은 조건에서
나온 판정이다.

## 5. RC-02 재현 확인

`test_tc15_logout.py`(UI-77)를 최신 빌드로 실행해 통과했다. 로그인, 로그아웃, 재실행을
거친 뒤 앱 컨테이너의 캐시 디렉토리는 아래와 같았다.

```
RemoteCaches/http-127-0-0-1-3000--api-v1/<계정 UUID>
RemoteCaches/http-127-0-0-1-3000--api-v1/<계정 UUID>
```

`anonymous` 디렉토리는 생성되지 않았다. DEF-06이 8월에 실측한 "로그아웃 시 계정 캐시
전체가 익명 영역으로 복사됨"은 이 빌드에서 재현되지 않는다. 남아 있는 것은 로그아웃 후에도
이전 계정의 캐시가 디스크에 그대로 있다는 사실이며, 이는 15가 적어둔 "기기 물리 접근 전제"와
일치한다.

RC-02의 심각도를 유지할지, 로그아웃 시 해당 계정 캐시를 삭제할지 오프라인 재로그인을 위해
남길지는 판정되지 않았다.
