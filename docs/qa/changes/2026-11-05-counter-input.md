# 단수 직접 입력 정책 변경

2026-11-05 MVP 재검토에서 정한 정책이다. 이전 실행 결과를 새 정책의 PASS로 바꾸지 않는다.

## 변경 이유

25단까지 뜬 기록이 있는데 -1을 잘못 입력했다고 0단으로 바뀌면 작업 위치를 잃는다.
기존 구현은 음수를 0으로 보정했다. 새 기준은 잘못된 입력을 거절하고 저장된 단수를 보존하는 것이다.

| 조건 | 기대 결과 |
| --- | --- |
| 현재 25단에서 -1 입력 | 입력창에 오류 안내, 저장 비활성화, 기존 25단 유지 |
| 잘못된 입력 후 취소·앱 재실행 | 25단 유지 |
| 같은 입력창에서 -1을 26으로 수정 | 오류 해제, 저장 가능, 재실행 후 26단 |
| 0 입력 | 정상 저장, `시작 전` 표시 |
| 1 입력 | 정상 저장, `현재 1단` 표시 |
| 빈 값·정수가 아닌 값·정수 표현 범위를 넘는 값 | 저장 차단, 기존 값 유지 |
| 총 단수 100에서 -1 입력 | 총 단수 100 유지 |
| 총 단수에 0 입력 | 기존 정책대로 총 단수 미설정 |

현재 단수와 총 단수는 같은 입력창을 사용한다. 총 단수도 음수 입력으로 설정이 지워지지 않게 한다.
카운터의 감소 버튼을 0에서 누르는 기존 동작은 그대로 유지한다.

## 검증 설계

- 기존 Appium UI-55는 0을 저장한 다음 음수를 넣고 0을 기대했다. 이 전제로는 '0 보정'과 '기존 값 보존'을 구분할 수 없다.
- 음수 거절 테스트는 UI에서 25단을 저장한 뒤 시작한다. 오류 안내·저장 버튼 상태·취소 후 값·재실행 후 값을 확인한다.
- Swift 단위 테스트는 음수에서 저장소 호출이 발생하지 않는 것과 값·카운터 ID·총 단수 보존, 정상 입력으로 복구되는 것을 확인한다.
- iOS UI 회귀 3건을 CI 대상에 추가한다: 음수 거절과 수정, 0·1 저장, 총 단수 보존과 0 미설정.
- Appium 테스트는 별도 로컬 실행 대상이다. CI의 XCTest 결과로 Appium 실행까지 PASS라고 기록하지 않는다.

## 실행 상태

구현과 테스트를 작성했다. 실행 결과는 해당 변경의 CI 및 개별 실행 기록으로 확인한다.
이번 변경은 전체 MVP 완료 또는 실제 iPhone 검증 완료를 의미하지 않는다.
