## C. 여기부터는 판단 — QA(유하은)가 채운다

`GUIDE_how_to_write.md` §1의 3자문을 A표의 각 항목에 적용할 것:
1. 틀어지면 **데이터가 상하는가** (복구 불가능한가)
2. 사용자가 **자주 지나가는 길**인가
3. **최근에 코드가 많이 바뀌었는가** (회귀 위험 — git log가 근거)

### 채울 표

| # | 리스크 | 등급 (P0/P1/P2) | 등급 근거 한 줄 | 설계 기법 | 테스트 조건 | 판정 기준(관찰 가능하게) |
|---|---|---|---|---|---|---|
| 1 | 전체 저장 fallback | | | | | |
| 2 | 캐시 경로 계정 미분리 | | | | | |
| 3 | 삭제 404 = synced | | | | | |
| 4 | 백업 import 병합 정책 | | | | | |

### 각 항목에 대한 꼬리질문 (막힘없이 답할 수 있어야 통과)

**2번 (캐시 경로)**
- 이 변수는 개발·테스트 편의용이라고 감사 문서가 명시했다. 그럼에도 리스크인가? 아니라면 왜 표에 남기는가?
- 실제로 이 변수가 설정된 채 배포될 경로가 있는가 — 그걸 무엇으로 확인할 수 있는가?
- 이게 결함이라면 severity와 priority가 갈리는가? (GUIDE §4 참조)

**3번 (삭제 404)**
- "이미 서버에서 지워졌으니 로컬도 지운 걸로 친다"는 합리적이다. 그럼 **어떤 경우에** 이게 위험해지는가?
- 서버가 **잘못** 404를 준 경우와 **정말** 없는 경우를 클라이언트가 구분할 수 있는가?
- 이 케이스를 재현하려면 무엇이 필요한가 — Charles? 서버 스텁? 이미 있는 도구로 되는가?

**1번 (전체 저장 fallback)**
- SYNC-08(`d0a753a`)에서 작업 세션은 이미 증분으로 고쳤다. 행안내는 왜 남았는가 — 아직 안 고친 것인가, 고칠 필요가 없는 것인가?
- 전체 저장이 위험해지는 조건은 무엇인가? (동시 편집? 오프라인 중 부분 실패?)

### 그리고 문서 전체에 대한 질문 하나

> 감사 문서는 "자동 검증 전부 통과"로 끝났고, 그 뒤 fix 커밋이 30건 나왔다.
> **QA로서 이 감사 문서를 받았다면, 무엇을 근거로 "이 통과를 신뢰할 수 없다"고 말하겠는가?**
